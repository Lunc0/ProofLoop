## 生成顺序与数据流

```text
创建 run 目录
  → 写入 environment.json、run.json
  → 对每道题：创建临时数据库与只读服务
      → 物化 agent-workspace/<case>/
      → 启动 DSH
      → 写入 raw/dsh/<case>.* 证据
  → 汇总 raw/runner-output.json 与 trajectory.json
  → 独立 evaluator 评分
  → 写入 evaluation.json、attribution.json、result.json、report.md
```

DSH 只看见相应 case 的 `agent-workspace` 内容和临时只读查询能力。Gold SQL、评分数据库连接信息和
评测中间结果都不会写进 agent workspace 或 DSH session。

## 根目录文件

| 文件 | 如何产生 | 用途 |
|---|---|---|
| `run.json` | run 创建时写入 | 最小的 run 身份信息：schema 版本、benchmark、请求的 suite 和初始 phase。|
| `environment.json` | 启动 DSH 前写入 | 环境快照：模型、DSH 配置（本次 `timeout_ms: 300000`）、公开题目摘要、评测器版本，以及所有输入文件的 SHA-256。它不保存凭据或 Gold SQL 内容。|
| `raw/runner-output.json` | 五题都处理完后写入 | 五道题的合并 `RunnerOutput`。通过题含候选 SQL 与标准化 trajectory；超时题只含 `runner_error`。|
| `trajectory.json` | 五题都处理完后写入 | 面向分析的公共 trajectory 汇总。其内容来自 runner output，不含 Gold SQL；对三道超时题只记录 timeout。|
| `evaluation.json` | 独立 evaluator 完成后写入 | 每题的公开判分结果、候选 SQL、usage 和错误详情；不保存 expected SQL 或 expected result。|

| `report.md` | 最终写入 | `result.json` 的人类可读摘要。|

## `agent-workspace/`：模型当时看到了什么

每道题都有一个隔离工作区。它在启动该题 DSH 前由 runner 创建；文件是公开 benchmark 材料的副本，
不会被下一题共享。

| 文件模式 | 来源/生成方式 | 用途与限制 |
|---|---|---|
| `<case>/schema.sql` | 从 `data/livesqlbench/base-lite/public/<database>/<database>_schema.txt` 复制并重命名 | 让模型阅读该数据库的表、列和关系。它不是数据库 dump，也不含 Gold SQL。|
| `<case>/context/01-<database>_kb.jsonl` | 从公开知识库复制 | 提供题目可能涉及的业务指标、公式和定义。|
| `<case>/context/02-<database>_column_meaning_base.json` | 从公开列含义文件复制 | 提供字段语义，辅助将自然语言指标映射成 SQL。|
| `<case>/TASK.md` | runner 生成 | 明确只有 schema/context 可作为任务上下文，expected query 与 evaluator 输入不会出现。|
| `<case>/sql-readonly.ps1` | runner 生成 | 指向本题临时的本机只读查询 HTTP 服务。DSH 可用它探索 fixture 数据；run 结束后服务关闭，因此现在执行该脚本不会成功。|

## `raw/dsh/`：每道题的 DSH 证据

### 文件类型

| 文件模式 | 如何产生 | 作用 |
|---|---|---|
| `<case>.invocation.json` | runner 在 DSH 调用结束后写入 | 保存实际可执行 argv（不含最后的题目 prompt）和 timeout。用于核对 profile、Node/DSH entry 与预算。|
| `<case>.stdout.log` | `subprocess.run` 捕获并脱敏 | DSH CLI 的标准输出。正常完成时主要是最终回答；超时前没有最终回答时通常为空。|
| `<case>.stderr.log` | `subprocess.run` 捕获并脱敏 | DSH CLI 的进程级错误输出。五题均为 0 B，表示 DSH 没有输出进程级错误；timeout 是 runner 产生的状态，不会写到这里。|
| `<case>.runner-output.json` | runner 为该单题序列化 | 该题的结构化状态。通过题包括提取的候选 SQL、usage 和标准化 trajectory；失败题记录 `DSH timed out after 300000 ms`。|
| `<case>.session.jsonl` | DSH append-only session 解压、逐事件脱敏后归档 | 最详细的模型行为证据：session header、提示、step、推理 chunk、工具调用/结果、消息和 turn end。它是分析模型为何超时的主要文件。|

### 为什么 session 与 runner output 都存在

两者层级不同，不能互相替代：

- `session.jsonl` 是 DSH 的细粒度事件轨迹，适合复盘模型花时间在哪里、读了哪些文件、调用了哪些工具。
- `runner-output.json` 是 harness 认定的结构化输出，适合评分和汇总。
- 对未完成 session，harness 不会从它提取候选 SQL 或 usage 来参与评分；它只作为可审计的失败证据。

## 超时 session 的补填说明

最初的 runner 只在 DSH 正常退出后归档 session。三题超时后，DSH 原始压缩日志仍保留在本机
`C:\Users\丁鸿伦\.dsh\sessions`，但未被复制到 run 目录。

本次检查中，三份原始日志均已通过现有 session loader 解压、逐事件脱敏，并确认 header 的 `cwd` 与
对应 `agent-workspace/<case>` 精确匹配后，才写入 `raw/dsh/<case>.session.jsonl`。因此：

- 文件创建时间晚于 run 完成时间是正常的补填痕迹；
- 内容代表原始运行时轨迹，不是重新执行 DSH 的结果；
- 它们没有 completed turn，不能改写 `evaluation.json`、`result.json` 或原有 `runner_error` 判定。

之后的 runner 已修复：超时或 DSH 非零退出时，也会归档可读取的脱敏 session；若 session 捕获本身失败，
会额外写入 `<case>.session-capture-error.log`，而不掩盖原始进程错误。

## 推荐查看顺序

1. 先看 `report.md` 或 `result.json`，了解总体结论。
2. 看 `evaluation.json`，了解每题判分与候选 SQL。
3. 对通过题看 `<case>.runner-output.json`；对超时题优先看 `<case>.session.jsonl`。
4. 需要复现模型可见上下文时，查看 `agent-workspace/<case>/`。
5. 需要核对执行环境是否相同时，比较 `environment.json` 中的 fingerprint、模型、DSH profile 和 timeout。
