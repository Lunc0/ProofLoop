# 实施计划：DSH Submit Spill 安全解析与语义判分

> **阶段：**34 · **版本：**v0.32 · **状态：**已完成

## 关联规格

[阶段 34 v0.32 规格](../specs/34-v0.32-dsh-submit-spill-safe-evaluation.md)。

## 实施方案

在 `dsh_session.py` 中把 tool result 的结构提取与 JSON transport 解析分开。解析器先使用
`json.JSONDecoder.raw_decode` 确定第一个完整 JSON value 的边界；无尾部时保持现有行为，有尾部时只接受
DSH 当前固定的单行 spill notice。notice 仅作为展示包装被验证和丢弃，其绝对路径永不打开、返回或写入新
artifact。随后继续执行既有 object、`ok`、`intent`、`phase` 以及 final/submit SQL 绑定检查。

实现按测试先行：先增加合成 session 回归，证明合法 spill 可恢复且未知尾部失败关闭；再实现窄 helper；最后
补 runner 级回归，证明恢复后的候选 SQL 能形成 `completed` 输出。阶段完成后更新阶段 33 兼容说明，并新增
阶段 34 design record。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 宽松截断掩盖被注入的尾随文本 | 伪造成功 submit 证据 | 使用 JSON 边界解析加完整 notice pattern；额外 JSON 和任意尾部做负向测试。 |
| 解析器依赖临时 spill 文件 | 不可复现、越权读取或泄漏路径 | 绝不打开路径；内联 JSON 必须自身完整。 |
| notice 格式未来变化 | 新 DSH 再次出现 runner error | 对未知格式显式失败；通过版本固定和回归更新合同，不猜测接受。 |
| 修复绕过 final/submit 绑定 | 未执行 SQL 进入 evaluator | 只修复 transport 包装；保留 `isError`、成功 payload 和 SQL 一致性校验。 |
| 测试触碰 held-out 数据 | custody 泄漏 | 全部使用合成 session 和合成路径。 |

## 实施顺序与并行边界
