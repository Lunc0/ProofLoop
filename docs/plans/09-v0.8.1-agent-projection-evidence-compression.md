# 实施计划：Evolution 失败轨迹的依赖感知 Agent 投影压缩

> **阶段：**09 · **版本：**v0.8.1 · **状态：**已完成
>
> **依据规格：**[09-v0.8.1-agent-projection-evidence-compression](../specs/09-v0.8.1-agent-projection-evidence-compression.md)

## 1. 实施目标与边界

为既有 `dsh-trajectory-compressed-v1` 审计 artifact 新增独立的 `evolution-coding-agent-input-v2`。v1 继续承担 custody、配对、hash 与可复现审计；v2 只交给 Skill Optimizer，且仅投影 Evolution 中未通过 case 的高优先级结构证据。

不引入第三方 SQL parser、新 SQL dialect、模型、网络、真实 DSH/Docker 或自动 Skill 修改。v2 的选择规则固定、无业务实体硬编码，并在无法安全解析时保留有界 fallback，不推断不相关性。

## 2. 改动范围

| 区域 | 改动 |
| --- | --- |
| `trajectory/contracts.py` | 保留 v1 合同；新增严格、冻结的 v2 agent projection 合同，避免审计 metadata 混入。 |
| `trajectory/policy.py` | 增加 v2 projection 的固定版本、字段/样本上限和 token-aware 规则阈值。 |
| `trajectory/dependency.py` | 新增本地、fail-closed SQL token 化、直接 table/qualified-column 引用提取和有限 sample/aggregate 覆盖判断。 |
| `trajectory/projection.py` | 将 v1 custody trajectory 投影为 P0–P3 evidence：失败/纠错、SQL、workspace discovery、candidate/final attempt/evaluator；选择上下文直接引用片段或 fallback。 |
| `trajectory/agent_input.py` | 生成 v2，而不改变历史 v1 的读取能力；统一个案可信 context 和 session read 的选取结果。 |
| `benchmark/livesqlbench_rotation_run.py` | 输出 v2 manifest，继续只向 Optimizer 传递失败 Evolution case。 |
| `tests/` | 用合成 evidence 验证版本、字段隔离、引用选择、fallback、coverage、失败/纠错、final attempt 和 runner wiring。 |

## 3. 有序任务与检查点

1. 定义 v2 合同和 policy 常量，并让 v1 类型、canonical JSON 与 custody 压缩保持不变。
   - 检查点：v2 不含 seq、时间、event location、hash、绝对路径或 GT 字段；空 case 集合法。
2. 实现保守 SQL token extractor。
   - 检查点：引用提取覆盖 Query slice 所需的 `SELECT`/`WITH`/CTE/subquery/JOIN/window 等结构；sample 覆盖只接受扁平 `SELECT … FROM/JOIN … WHERE … LIMIT` 与同范围 `COUNT`/`MIN`/`MAX`/`SUM`/`AVG`。
3. 实现 evidence projection 和 context 选择。
   - 检查点：P0 的 evaluator、candidate/final attempt、失败与 corrective action 始终保留；glob/read 仅在安全时折叠；无直接命中时输出 fallback；SQL 不能同时输出等价 raw 和 summary。
4. 接入 rolling runner 的 artifact writer，并将 manifest 明确标为 v2。
   - 检查点：通过 case 不进入 `trajectories`，也不列为 omitted case；未提交的公开最终文本不伪装为 candidate。
5. 写定向单元/集成测试，运行静态检查，并记录实际实现与验证结果。
   - 检查点：只运行合成、无模型测试；测试不输出或落盘真实 benchmark/session/逐题结果。

## 4. 核心设计决策

- **双层 artifact：**不破坏 v1。v2 由 v1 的已配对受限 evidence 构建，因而不会把失去审计字段的内容伪装成 v1。
- **引用范围大、覆盖范围小：**SQL 引用提取可在多种只读查询结构上收集确定的表/限定列；sample 降级只在简单、同范围、可证明的查询对上发生。
- **直接依赖而非业务理解：**只依据规范化直接文本、SQL 与 DDL/JSON 结构的可解析连接选择 KB/schema。没有命中即 fallback。
- **提交状态分离：**`candidate_output` 只来自 runner；公开最终文本则单列 `final_submission_attempt` 与解析状态。
- **安全优先：**未知 SQL/上下文不产生猜测边；不可信 evidence 外层一次性标识，agent payload 不带逐项 audit/hash metadata。

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 轻量 SQL 解析误判 | token-aware、跳过 string/comment/dollar quote；未知结构不做覆盖或裁剪。 |
| 压缩遗漏失败证据 | P0 先选择，失败和 corrective link 由 status/direct failure 明确驱动。 |
| v2 与 v1 混淆 | 分离 Pydantic 模型和 schema version；writer/manifest 都标记 v2。 |
| 上下文无直接命中时误删 | 输出受限 fallback，绝不称为无关。 |
| 测试泄漏 benchmark 数据 | 仅使用合成 SQL、文本、stub runner 与临时目录。 |
