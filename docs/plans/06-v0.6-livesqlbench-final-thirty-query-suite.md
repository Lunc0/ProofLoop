# 实施计划：LiveSQLBench Base-Lite 三十题最终 Held-out 评测集

> **阶段：**06 · **版本：**v0.6 · **状态：**已完成；首次真实 baseline 待新的明确授权
>
> **依据规格：**[阶段 06 规格](../specs/06-v0.6-livesqlbench-final-thirty-query-suite.md)

## 1. 实施目标

建立一个独立于 Git、candidate store 和未来 optimizer 的 evaluator custody root；由它持有一个不可变的
LiveSQLBench Base-Lite Query-only 三十题 manifest。新增静态注册的 held-out adapter，复用既有 PostgreSQL
fixture、只读 SQL capability、DSH、Soft-EX 与候选注入机制，但把所有 case identity、prompt、逐题结果和
session artifacts 留在 custody root，CLI 仅返回分层聚合结果。

现有 `livesqlbench-base-lite` 五题 smoke adapter、旧 CLI 路径和它的完整公开 evidence 格式保持不变。

## 2. 架构决定

### 2.1 访问边界

```text
repository / optimizer workspace             evaluator custody root
--------------------------------             ----------------------
source code + smoke-suite IDs                held-out manifest (30 IDs)
candidate store                              held-out run artifacts
public CLI aggregate result       <--------- tier scores + macro average only
```

- `SKILL_EVOLVE_HELDOUT_ROOT` 是 evaluator 进程唯一读取的本地 root；其实际 ACL、容器挂载或机器隔离是
  维护者的运行前置条件，代码不伪造权限保证。
- manifest、run store、case prompt、DSH session、candidate SQL、逐题 evaluation 都写在该 root；它们不进入
  repo、`.local/skill-evolve/`、Git、标准 runs root 或 optimizer feedback。
- env var 和 manifest 都是不可信输入：路径须解析、拒绝 symlink/逃逸，manifest 以严格 Pydantic model 读取，
  不允许动态 import、命令、路径或 Gold 数据字段。

### 2.2 Manifest 与选题

- 一次 evaluator-owned 初始化操作从公共 Query 记录中选择并写入 manifest；对外只输出 suite ID 与
  manifest SHA-256，绝不输出 case ID。
- 固定约束：30 个唯一 ID；Simple/Moderate/Challenging 各 10；不含现有 smoke 五题；每 tier 10 个不同
  `selected_database`；全局覆盖 18 个数据库且任何数据库至多两题；尽量包含两种 `conditions.order`。
- 使用系统安全随机性完成可行解选择；初始化完成后 manifest 不得原地重写。审计和复跑以 custody 内的
  manifest bytes/hash 为准，而非随机 seed。
- manifest 记录 schema version、suite ID、case ID 顺序、每题公开类别/难度/数据库、public data digest 和
  manifest SHA-256；不含 prompt、Gold SQL、GT/test cases、dump 或凭据。

### 2.3 Adapter 与 evidence

- 静态 registry 增加 `livesqlbench-base-lite-query-final-v1`；它不从 data/candidate/manifest 动态加载代码。
- adapter 读取验证后的 manifest，构造既有 `LiveSQLBenchSuite`，并验证 public/GT/dump 完整性。旧五题 loader
  不改选题或公开 summary。
- held-out run 使用 custody 内的 `RunStore` 和 redacted report writer；不写 `environment.json` 中的 case list，
  不写标准的 public `evaluation.json`/trajectory 或 raw DSH 目录。完整 evidence 只在 custody 内以受限格式保存。
- 新的 held-out terminal contract 仅含 suite ID、manifest hash、candidate binding（或无 candidate）、状态、
  30 题总数、各 tier 的计数/成功率、macro-average、总耗时和可用成本字段；任何无法安全提供的成本字段保持
  缺失，不推断数值。

## 3. 有序任务

### 任务 1：定义严格 held-out manifest、root 与选题服务

**依赖：**无。

**实施：**在 benchmark 模块建立严格 manifest 类型、root resolver、原子写入和验证器；实现受限的
evaluator-only manifest 初始化。它只读取公开 JSONL，并求解三十题的分层、数据库覆盖与 smoke 排除约束。

**验收：**

- 缺失/非法 env root、symlink、路径逃逸、重复/篡改 manifest、非 Query、tier/database/digest 不匹配均在
  启动 Docker、DSH 或模型前失败。
- 初始化只输出 manifest SHA，不输出 case ID；初始化后的 manifest 不可覆盖。
- 测试 fixture 使用合成 ID，真实 held-out ID 不写入测试、源码或文档。

**验证：**manifest/root 单元测试、`uv run ruff check .`、`uv run mypy src`。

### 任务 2：接入静态 held-out adapter 与安全聚合合同

**依赖：**任务 1。

**实施：**扩展 trusted adapter registry 和 CLI，使 held-out adapter 从 custody manifest 加载 suite；为它引入
不含 case identity 的 suite/run summary、分层指标及宏平均。旧 adapter、legacy wrapper 与标准 run 输出不变。

**验收：**

- `benchmark validate`/`fixture-check`/`run` 可发现 adapter，却在 root 不可用时 fail closed。
- terminal stdout 无 case ID、prompt、candidate SQL、GT、路径、凭据或未脱敏 log。
- 相同 manifest/candidate/model/config 的 fingerprint 可比较；五题 fingerprint 与 held-out fingerprint 不混淆。

**验证：**adapter/CLI 测试、旧 benchmark CLI 回归测试。

### 任务 3：将 runner/evaluator evidence 写入 custody，并保留现有安全语义

**依赖：**任务 2。

**实施：**为 held-out run 使用受限的 custody run store 与 serializer，复用每题独立 PostgreSQL fixture、
只读角色、Soft-EX、timeout/nonzero-exit 的脱敏 session capture。必要时把共有 runner 函数参数化；不改
普通 adapter 的证据格式。

**验收：**

- held-out 的逐题 artifacts 不出现在 repo runs root 或 CLI stdout；缺失/歧义 evidence 仍为
  `runner_error`/`evaluator_invalid`，不会被当作通过。
- Gold SQL、GT case/result、私有 dump、DB 凭据和原始 session log 不跨越 evaluator custody。
- candidate 注入仍只复制已验证 `SKILL.md`；无 candidate baseline 不创建 candidate 文件。

**验证：**runner/evaluator 隔离测试、candidate injection 回归、负向泄漏测试。

### 检查点：任务 1--3 后

- [x] 新旧 adapter 的目标测试通过。
- [x] 静态检查通过。
- [x] 对 stdout、run roots 和 generated manifests 做负向泄漏检查。
- [x] 人工检查 dirty worktree 中既有 DSH model-selection 改动未被覆盖。

### 任务 4：完成文档、完整验证与运行前审计

**依赖：**任务 1--3。

**实施：**更新 specs/plans 索引，编写阶段 06 设计记录，记录实际 manifest contract、CLI、兼容边界与
测试证据。执行全量静态与测试验证；检查 Docker、DSH binary、模型 provider 凭据、data layout、独立 root
权限和成本可用性，但不调用模型。

**验收：**

- `uv run ruff check .`、`uv run mypy src`、`uv run pytest`、`git diff --check` 通过。
- 运行前审计只给出可安全公开的 readiness 状态，不泄漏 held-out manifest 内容。

### 任务 5：首次真实无 Skill baseline（人工操作，默认不执行）

**依赖：**任务 4、维护者新的明确运行授权。

**操作：**在 evaluator custody 已正确配置后，以已确认的 DSH manifest/model 运行：

```text
uv run skill-evolve benchmark run livesqlbench-base-lite-query-final-v1 <data-root> <dsh-manifest>
```

不传 `--candidate`。运行完成后只向维护者报告 aggregate tier scores、macro-average、总耗时、可取得的总成本、
run 状态和 manifest hash；不显示 case ID、题目、SQL、逐题结果、路径或 session 内容。运行后不以该结果改写
任何 Skill。

## 4. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 同一优化进程可读 custody root | held-out 失效 | 部署前以独立 OS ACL、container mount 或机器隔离；代码对缺失 root fail closed。 |
| 公开数据可被未来 agent 自行下载 | 无法获得密码学秘密 | 将 held-out 定义为优化流程的访问/反馈边界；不作“对互联网不可见”的错误承诺。 |
| 30 题串行运行耗时 60--150 分钟 | 模型费用和反馈延迟 | 仅在版本冻结/里程碑运行；日常保持五题 smoke；本阶段不引入并发或自动重试。 |
| 现有 DSH model-selection 未提交改动 | 集成冲突或回归 | 先保留和测试用户现有改动，最小化共享 runner 改动，发生重叠时暂停确认。 |
| 缺失 dumps/GT 或 session evidence | 错误地报告分数 | 开始前 fail closed；按现有语义记录 `eval_data`/`runner_error`，不把部分结果当正式结论。 |

## 5. 不在本轮执行的事项

阶段 06 的代码、合成 fixture 测试和设计记录已完成。评测器已在获得单独明确授权后，于仓库外创建真实
custody root 并初始化真实 manifest；其路径、hash 和 case list 均不写入仓库。尚未启动 Docker、真实 DSH
或模型，也没有运行 baseline。任务 5 仍尤其需要运行前的新一轮明确授权。
