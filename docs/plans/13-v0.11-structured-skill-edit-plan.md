# 实施计划：结构化 Skill 与行为导向修改计划

> **阶段：**13 · **版本：**v0.11 · **状态：**已完成
>
> **依据规格：**[阶段 13 v0.11 规格](../specs/13-v0.11-structured-skill-edit-plan.md)
>
> **实现记录：**[阶段 13 v0.11 实现记录](../design/13-v0.11-structured-skill-edit-plan.md)

## 1. 实施目标

在不修改 Skill、不创建 child candidate、不运行真实模型或 benchmark 的前提下，为已完成且有效的 Evolution run 增加一条
显式、可审计的 `optimizer plan <run-id>` 路径。该路径把当前 Skill、可信目标运行合同和
`evolution-coding-agent-input-v3` 转换为：

1. 确定性的 `skill-map-v1`；
2. 严格校验的缺陷簇与最多三个语义修改项；
3. 带本地 source binding 和行为断言的 `skill-edit-plan-v1`；
4. 独立的 receipt、Markdown 摘要和根 `result.json` 最小摘要。

现有 `optimizer advise`、rotation 自动 advice、v0.9 artifact 与 candidate 生命周期保持不变。

## 2. 实施范围

### 2.1 本阶段实现

- 新增 Skill map、目标运行合同、缺陷簇、语义修改项、行为断言和 receipt 的冻结 Pydantic 合同。
- 使用标准库实现确定性 Markdown 分块，不增加第三方 Markdown parser。
- 由仓库内受信任代码为当前 Evolution adapter 生成无机密目标运行合同。
- 从 v3 evidence 派生本地稳定的 case/evidence 引用，不修改 v3 持久化 schema。
- 使用现有无工具 optimizer client 完成一次模型调用，并对返回值做严格验证和本地 source binding。
- 增加显式 `optimizer plan <run-id>` CLI；失败时不留下部分计划。
- 使用合成 artifact 与 fake client 覆盖成功、拒绝和兼容性路径。

### 2.2 本阶段不实现

- 不生成或应用 Markdown patch，不修改原始或 materialized `SKILL.md`。
- 不创建、选择、晋级、回退或删除 candidate。
- 不自动触发 plan，不修改 rotation 的 v0.9 advice 行为。
- 不执行 Failure Replay、回归、消融、Smoke、Evolution 或 Final。
- 不调用真实 LLM、DSH、Docker、数据库或网络服务。
- 不处理 held-out/Final 的 identity、逐题结果、GT、Gold 或 session。
- 不实现后续阶段的 patch 或 child 创建；后续政策已确定为 guarded 不需要人工审批，仍保留机械校验。

## 3. 关键架构决策

### 3.1 新旧 optimizer 路径显式并存

保留现有 `optimizer advise` 和 rotation 自动 advice，不改变旧 manifest 的解释。阶段 13 新增显式命令：

```powershell
uv run skill-evolve optimizer plan <run-id>
```

该命令只接受已完成、准入有效的 Evolution run。它不会被 rotation 自动调用，因此不会静默增加模型成本，也不会让历史 run
因配置默认值变化而改变行为。

### 3.2 新合同与 v0.9 合同分离

新合同放在独立模块中，使用固定 schema version、枚举、冻结模型和 `extra="forbid"`。不扩展或重定义
`skill-optimization-advice-v1`。现有 optimizer client 继续只负责无工具文本调用；阶段 13 服务拥有独立 prompt 常量和
输出解析，不把 edit-plan prompt version 写入旧 manifest 配置。

### 3.3 Skill map 只做确定性结构识别

解析器识别 frontmatter、标题、段落、连续列表、fenced code block 和 Markdown 表格。它不执行 Skill、不读取引用文件，也不让
LLM 决定行号或 block ID。

权限按固定策略分配：

- frontmatter、可信 Runtime Contract 和安全边界为 `locked`；
- Purpose/Scope、Activation 及无法识别的旧章节为 `guarded`；
- Core Strategy 下已知策略章节为 `evolvable`；
- Heuristics/Examples 下内容为 `experimental`。

标题匹配只使用固定、版本化的规范标题集合；未匹配项 fail closed 到 `guarded`。block ID 由 Skill hash、规范化标题路径、块类型、
行号和内容 hash 派生，相同字节输入必须产生相同结果。

### 3.4 目标运行合同来自固定可信 provider

在 optimizer 内建立小型、封闭的 target-contract provider registry，只对当前受支持的 Evolution adapter ID 返回合同。合同内容
由受信任 Python 常量构造并计算 canonical SHA-256；不得从 Skill、trajectory、模型输出或 run artifact 反向推断。未知 adapter、
普通 benchmark、Smoke、Final 和 held-out 一律拒绝。

### 3.5 LLM 只提出语义内容，本地服务绑定事实

发送给模型的输入由本地服务构造，包含：

- 标记为不可信数据的 v3 optimizer-safe evidence；
- 当前 Skill 文本及其确定性 Skill map；
- 可信目标运行合同；
- 固定缺陷类型、语义操作、规则类型和输出 schema。

模型只能返回缺陷簇与语义修改内容，不能返回或覆盖父 candidate ID、任何 source hash、本地 ID、计划状态或 receipt。服务在验证
case/evidence/block 引用、修改权限、数量、重叠、类型最低证据和敏感文本规则后，才生成完整计划。

### 3.6 Evidence 引用在 optimizer 层派生

不修改 `evolution-coding-agent-input-v3`。服务按 canonical case 位置和投影 evidence 的稳定内容 hash 派生本地
`case_ref`/`evidence_ref`，只在当前 edit-plan 输入和产物中使用。模型返回的所有引用必须属于服务提供的集合。

### 3.7 产物隔离与原子发布

所有新文件写入：

```text
<run>/optimizer/edit-plan/
  skill-map.json
  edit-plan.json
  edit-plan.md
  receipt.json
```

先在临时目录完成四个文件的序列化、回读和 hash 校验，再原子发布目标目录。失败时保留旧的完整结果或无结果，不留下半套产物。
根 `result.json` 使用独立 `optimizer_edit_plan` 键记录状态、相对路径、hash 和计数；不覆盖原有 `optimizer` advice 摘要。

## 4. 预期代码边界

```text
src/skill_evolve/optimizer/
  edit_plan_contracts.py   # 新 schema、枚举和跨字段校验
  skill_map.py             # 确定性 Markdown 分块与权限映射
  target_contract.py       # 可信 target-contract provider
  evidence.py              # advice/plan 共用的 v3 与 subject 准入读取
  edit_plan_service.py     # prompt、模型输出验证、source binding 与持久化
  service.py               # 改为复用共用 evidence 准入，不改变 advice 行为

src/skill_evolve/cli.py    # 新增显式 optimizer plan 命令
tests/                     # 合同、解析器、service 与 CLI 定向测试

```

文件名可在实施中因现有模块职责做小幅调整，但不得把 edit-plan 合同塞入 v0.9 advice schema，也不得改变上述安全边界。

## 5. 有序实施任务

### 任务 1：定义严格合同和可信目标运行合同

**涉及文件：**

- `src/skill_evolve/optimizer/edit_plan_contracts.py`
- `src/skill_evolve/optimizer/target_contract.py`
- `tests/test_edit_plan_contracts.py`
- `tests/test_target_contract.py`

**实施内容：**

1. 定义 `skill-map-v1`、`skill-target-contract-v1`、模型候选输出、`skill-edit-plan-v1` 和 receipt/result 合同。
2. 固定功能模块、缺陷作用域、缺陷类型、语义操作、规则类型、修改权限和验证模式枚举。
3. 为不同缺陷类型实现最低引用规则；拒绝额外字段、空泛意图、超过三个修改项、无 cluster/evidence 绑定和重复 ID。
4. 让完整计划的父 candidate、Skill/v3/contract hash、状态和本地 ID 只能由服务构造。
5. 实现当前 Evolution adapter 的可信目标运行合同和 canonical hash；未知 adapter fail closed。

**验收：**合同 round-trip 字节稳定；模型不能注入 source binding；incorrect/contradiction/missing recovery 等缺少必要引用时被拒绝；合同不含 endpoint、凭据、路径和私有评测字段。

## 6. 合同与验证重点

### 6.1 类型特定最低证据

- `incorrect_guidance` 必须同时引用 Skill block 和可信合同字段。
- `contradiction`、`redundancy`、`priority_conflict` 至少引用两个不同 Skill block。
- `workflow_order_issue` 必须描述至少两个动作和有依据的顺序。
- `missing_recovery_strategy` 必须引用失败 episode、恢复观察和相关 block/缺口位置。
- `underspecified_guidance` 必须指出按规则类型缺失的必要行为要素。
- `missing_guidance` 只能作为待验证假设，不能声称已确认根因。
- `candidate_generalization` 在本阶段只能记录未来验证风险，不能作为已确认 defect scope。

### 6.2 修改权限

- `locked`：任何 edit 目标均拒绝；合同冲突只保留 finding。
- `guarded`：允许语义适配请求，但完整计划状态必须要求人工批准。
- `evolvable`：满足证据和行为断言后可进入普通计划。
- `experimental`：除普通校验外，必须填写泛化风险和 fresh regression 方案。

### 6.3 行为断言

每个 edit 必须具备触发事件、修改前行为、期望动作、提交前必须出现的动作/结果、禁止的提前行为以及成功或停止条件。
自动验证能力必须来自现有安全投影；无法客观观察的内容标记为 `review_only`。

## 7. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 旧 Skill 标题多样导致权限误判 | 固定标题表；未知内容默认 guarded；解析与权限策略版本化 |
| LLM 伪造引用或可信事实 | 只接受本地提供的 ID 闭集；source binding 全部由服务加入 |
| 新 plan 覆盖 v0.9 advice | 使用 `optimizer/edit-plan/` 独立目录和 `optimizer_edit_plan` 独立摘要键 |
| 自由文本夹带具体 case、路径或敏感内容 | 限长、字段白名单、已知引用/路径扫描；artifact 最小化；测试恶意输出 |
| 单 case 产生一条规则导致过拟合 | 先 cluster、最多三个 edit、要求泛化范围和 fresh regression 方案 |
| Markdown parser 对未闭合结构产生漂移 | 单遍状态机、输入上限、未闭合即 fail closed、字节稳定测试 |
| 共用 evidence 准入影响 v0.9 | 单独抽取任务、先跑旧 service 测试、保持 prompt 与 artifact 不变 |
| 显式命令被误用于 Final/held-out | adapter/run-mode 白名单和调用前拒绝测试 |
| 产物写到一半进程失败 | 临时目录完整生成并回读，再原子发布 |

## 9. 完成定义

只有同时满足以下条件，阶段 13 才可标记完成：

1. 任务 1—6 全部完成，检查点 A/B 均已人工核对。
2. 规格的 12 条验收标准都有对应自动测试或明确人工证据。
3. 新路径只通过显式 `optimizer plan` 触发，v0.9 advice 与 rotation 行为无回归。
4. 所有 artifact 完整、hash 绑定、原子发布，并且不进入 candidate store。
5. 定向测试、ruff、mypy 与 `git diff --check` 通过。
6. 已创建真实实现记录，规格和计划索引状态更新为已完成。
7. 未调用真实模型、DSH、Docker、数据库、benchmark，未创建 child，未推送远端。

## 10. 评审闸门

本计划获准前不修改源码。计划获准后按任务 1 → 2 → 检查点 A → 3 → 4 → 5 → 检查点 B → 6 的顺序实施。
若实施需要新增依赖、改变旧 manifest/rotation 行为、调用真实服务、自动修改 Skill 或扩大到 patch/child/replay，必须停止并重新
取得授权。
