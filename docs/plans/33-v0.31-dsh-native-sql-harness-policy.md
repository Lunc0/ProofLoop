## 实施方案

使用一个仓库内静态、无 npm 依赖的 JavaScript ESM Cordis 插件，把现有 loopback
`ReadOnlyQueryService` 注册为 DSH 原生 `sql_probe` 与 `sql_submit`。Python runner 为每个带数据库能力的
case 将该插件复制到 case 自己的 `dsh-runtime`，在同目录生成绑定 endpoint、resource list、allowlist 和
schema version 的 policy patch，再以额外 `--patch` 参数启动一次性 headless DSH。

插件在全局 tool registry 注册两个 SQL 工具，并在同步 `agent/created` 回调中通过 `agent.ctx.tools.restrict()`
收窄该 Agent 的继承工具目录，再注册 Agent-scoped monotonic guard。每个 Agent 的成功调用 cache 和
`EXPLORE/FINALIZE` 状态独立保存。工具 schema 在会话内不变化；成功 `sql_submit` 只切换 guard 状态，下一次
模型请求仍保留相同 schema，但所有工具执行均被拒绝。

Python 从已归档 DSH session 的成对 `tool/call`、`tool/result` 事件中取得最后一次成功 `sql_submit`，并与
最终 assistant SQL 做规范化、确定性绑定。不信任插件 stdout 或模型关于提交成功的陈述。历史
`pwsh -> sql-readonly` evidence 继续可读，新的 probe/submit intent 进入压缩和 optimizer-safe projection。

## 任务与依赖

### Task 1：实现并离线验证 DSH 插件内核

**工作：**新增静态 ESM 插件以及 Node 内建 test runner 测试。插件负责严格配置校验、两个工具的 JSON
schema、loopback POST、固定错误码、Agent scoped allowlist、成功调用 canonical cache 和 finalize guard。

**验收：**

- `sql_probe`/`sql_submit` 唯一模型参数为非空 `query`；endpoint 只来自插件配置。
- `agent/created` 时可见工具被限制为 `read`、`grep`、`sql_probe`、`sql_submit`。
- probe 成功不锁定，submit 失败不锁定，submit 成功锁定；精确重复成功调用被拒绝。

**验证：**`node --test tests/dsh/sql_harness_policy.test.mjs`

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Cordis 插件相对路径或加载生命周期理解错误 | patch 能生成但真实 DSH 无法启动 | Task 1 后立刻做无模型真实 load checkpoint，失败时先修加载边界。 |
| 工具限制注册晚于第一次 prompt | 模型仍看到完整工具集 | 使用同步 `agent/created`，并以 fake runtime 顺序断言及真实 load check 验证。 |
| `sql_submit` 执行成功被误当正确答案 | 错 SQL 被提前接受 | 只进入 FINALIZE；正确性仍由既有独立 evaluator 判断。 |
| 模型提交后输出另一条 SQL | Harness 与 runner 对候选理解不一致 | 从 session 绑定最后一次成功 submit，并在 evaluator 前严格比较最终 fence。 |
| deny 后模型循环调用工具 | token/超时不降反升 | 返回短、稳定拒绝原因并保留 timeout；后续 A/B 再决定是否增加 turn 终止。 |
| tool restriction 隐藏 SQL 插件自己的 scoped/global 工具 | Agent 看不到 native executor | 在限制前注册工具，allowlist 使用 registry 中已知精确名称，未知名称 fail loud。 |
| 插件错误泄漏 endpoint 或响应 | custody/环境信息暴露 | 固定错误码，不拼接 URL、异常或 response body；Python/Node 负向测试。 |
| 修改 trajectory 破坏历史证据 | 旧 run 无法进入 optimizer | 保留旧 adapter 映射，用历史 fixture 做回归，不做 schema 迁移。 |

## 实施顺序与非并行项

插件工具合同是 Python patch 和 session 绑定的前置；runner 绑定又是 trajectory intent 的证据来源；design
只能在真实验证后编写。任务共享 `dsh.py`、session 和 trajectory 合同，因此顺序实施，不使用并行 agent。

## 授权边界

本计划批准后可进行仓库内代码、测试、文档修改，运行 fake runtime、Node 单元测试、Python 定向检查以及
不发送 task 的 DSH load check。仍不授权真实 DSH task/model、Docker、数据库、benchmark、网络、commit
或 push。
