# 实施计划：LiveSQLBench 分层滚动评测器

> **阶段：**07 · **版本：**v0.7 · **状态：**已完成
>
> **依据规格：**[阶段 07 规格](../specs/07-v0.7-tiered-rolling-evaluator.md)

## 1. 实施目标

在不接入 coding agent、自动修改 Skill、promotion 或 rollback 的前提下，新增从同一开发题池抽题的
LiveSQLBench 滚动 Smoke 与 Evolution evaluator。Smoke 每份 manifest 为 5 题并按三轮难度配额轮换；
Evolution 每份 manifest 为 15 题、各 tier 5 题。两层允许 case 重叠，Final 的既有 30 题和每 tier 5 题
reserve 永不进入滚动 manifest。

实现将把 benchmark/runner 从 candidate store 的 `ResolvedCandidate` 解耦为中性的 `RunSubject`。CLI 的
`--candidate` 仅在边界处转换为 `RunSubject`；评测核心和运行器不导入 candidate 模块。真实 manifest、Docker、
DSH、模型和 baseline 均不在本计划或实现验证中执行。

## 2. 架构决定

### 2.1 通用被测对象

- 新增严格、不可变的 `RunSubject`：只含不透明 subject ID、内容 SHA-256、只读 bytes 和安全文件名。
- `RunInput`、DSH workspace、run evidence 与 benchmark result 只使用 subject binding，不保留 candidate
  类型或谱系。工作区将 subject 物化到固定只读文本位置，且不执行、import 或加载其引用内容。
- `candidate` 包和 CLI 保留 `--candidate` 的兼容入口；由边界适配器把已验证 `SKILL.md` 转换为 `RunSubject`。

### 2.2 滚动 custody、reserve 与 manifest

```text
repository / ordinary runs                  evaluator rotation custody
--------------------------------            --------------------------------
trusted adapter code + redacted run logs    private reserve manifest (5/tier)
rolling manifest receipt                    immutable rolling manifests
RunSubject binding + smoke outcome          Smoke gate receipts
```

- 新增仓库外、预先存在的 rotation custody root；它拒绝 repository、candidate store 与 held-out custody
  的路径重叠、symlink 和不可写路径。代码验证路径边界，不替代 OS ACL。
- 初始化只在 custody 内读取既有 Final manifest，选出并原子持久化每 tier 5 题 reserve；初始化和新 manifest
  创建均不允许覆写。测试只使用合成 data root、合成 Final manifest 和临时 custody。
- Smoke/Evolution manifest 是严格 typed、含 public-data digest、公开 metadata、manifest SHA-256 与
  随机 manifest ID 的 custody artifact。每份 manifest 内唯一；同层没有复用窗口或预算，跨层允许重叠。
- 新 manifest 选择只使用系统随机性，不提供 caller seed 或 case-ID 参数；开始 fixture/DSH 前校验 public、GT、
  dump、schema/context、tier 和 Final/reserve 排除条件。

### 2.3 运行、gate 与比较

- 新的 rolling runner 复用一题一 fixture、只读 SQL、Soft-EX 和现有脱敏 session-log 流程，但使用中性状态：
  `passed`、`task_failure`、`runner_invalid`、`evaluator_invalid`。它不生成 Skill 修改建议。
- Smoke 只有全部 5 题通过才在 custody 写入对应 subject SHA-256 的 gate receipt。任何 task/runner/evaluator
  失败都不写成功 gate；Evolution 在启动前检查这个 receipt。
- Evolution 在现有 run 目录证据上附每 tier 计数/通过率、macro-average 和不含 subject 的 comparison key。
  `incomparable` 只在比较两个不同 key 的 Evolution 结果时出现，不是对 subject 的归因。

### 2.4 CLI

- 新增 evaluator-only 的 rotation 初始化与 manifest 创建命令；成功 stdout 仅给出 adapter、manifest ID、
  manifest SHA-256 和 tier 计数，不列出 case ID、reserve 或 Final 信息。
- 对两个滚动 adapter，`validate`、`fixture-check` 和 `run` 都需要 manifest ID；静态五题与 Final adapter
  保持既有参数和行为。`run` 仍可接受 `--candidate`，但在 CLI 边界转换为 `RunSubject`。

## 3. 有序任务

### 任务 1：建立 `RunSubject` 边界并迁移已有运行路径

**依赖：**无。

**实施：**新增通用 subject 合同和 candidate 边界适配器；替换 benchmark protocol、普通/held-out run、
`RunInput`、DSH workspace 和 `RunDirectory` 中的 `ResolvedCandidate` 依赖。保留 CLI `--candidate`，但所有
benchmark 与 runner 导入图不再包含 candidate 模块。

**验收：**

- 普通五题和 Final 的 adapter ID、选题与安全输出语义保持兼容。
- agent workspace 仅得到 subject 的单个只读文本文件和公开上下文；GT、NOTICE 与可执行内容均不进入。
- 静态检查可证明 `src/skill_evolve/benchmark/` 与 `src/skill_evolve/runner/` 不直接导入 candidate。

**验证：**更新 subject、DSH、普通 run 和 held-out fake-run 测试；`ruff`、`mypy` 与相关 pytest 文件。

### 任务 2：实现 rotation custody、reserve 与严格 manifest 选择

**依赖：**任务 1。

**实施：**新增 rotation root resolver、reserve state、Smoke/Evolution manifest 类型、SHA-256、原子写入、
加载/篡改验证和选题服务。它以 existing Final manifest 为排除源，初始化 reserve 为每 tier 5，并为三轮
Smoke 配额和 Evolution 各 tier 5 题创建新 manifest。

**验收：**

- Final 或 reserve case、错 tier/category、缺材料、symlink、路径逃逸、digest 漂移、篡改或不足题数均在
  Docker/DSH 前 fail closed，且不留下部分文件。
- 两层可选择相同 case；单份 manifest 不重复；同层不额外施加复用窗口或预算。
- receipt/stdout/普通 run root 不泄露 Final 或 reserve identity。

**验证：**合成 data/custody 单元测试；不读取或创建真实 manifest。

### 任务 3：接入滚动 suite、执行器与 Smoke gate

**依赖：**任务 1、任务 2。

**实施：**新增两个静态 adapter 和 rolling suite loader；以 generic subject 执行串行、独立 fixture 的 run，
写现有 run 目录下的脱敏 session evidence。建立 custody gate receipt，Smoke 结果决定 Evolution 是否允许启动；
Evolution 输出 tier 指标、macro-average 与 comparison key。

**验收：**

- Smoke 5/5 才能执行 Evolution；task/runner/evaluator 无效均返回中性结论并阻止 Evolution。
- 多 subject 可运行同一 Evolution manifest；相同 manifest/data/evaluator/model/runner 环境得到相同 comparison key。
- Final 仍为 custody-only aggregate 输出，不使用 rolling code path。

**验证：**fake fixture、stub DSH、gate、comparison 与泄漏负向测试；不调用 Docker 或模型。

### 任务 4：扩展 registry/CLI 并覆盖兼容性

**依赖：**任务 2、任务 3。

**实施：**在 trusted registry 注册两个滚动 adapter，增加 rotation 初始化/manifest 创建入口，以及滚动
adapter 的 manifest ID 参数校验。保持旧 `livesqlbench-base-lite`、Final 和 `--candidate` CLI 行为可用。

**验收：**

- 未知 adapter、缺失/错误 manifest ID 或企图在静态/Final adapter 上传入 rolling manifest 时以退出码 64
  fail closed。
- CLI 只返回允许的 receipt、run summary 或 Evolution metrics；不输出 Final/reserve、GT、Gold、凭据或完整 session。

**验证：**registry/CLI pytest、旧 CLI 回归与 `git diff --check`。

### 检查点：任务 1--4 后

- [x] 新旧 adapter 的 fake/stub 测试通过。
- [x] `uv run ruff check .` 与 `uv run mypy src` 通过。
- [x] 定向 pytest 不启动 Docker、DSH 或模型。
- [x] `git diff --check` 通过，且无 Final/reserve identity 泄漏。

### 任务 5：完成设计记录与完整无模型验证

**依赖：**任务 1--4。

**实施：**在 `docs/design/` 记录实际 contract、CLI、compatibility/custody 边界和验证结果；更新索引状态。
在不运行真实服务的前提下执行适当的完整静态与 pytest 验证。

**验收：**设计记录只描述实际实现；没有真实 manifest、Docker、DSH、模型、baseline、push 或自动 Skill
动作。

## 4. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| rotation root 可被优化进程读取 | reserve/Final 边界失效 | 运行前采用独立 ACL、账号、容器挂载或机器；代码只接受仓库外 custody root。 |
| candidate 类型在共享代码中残留 | evaluator 仍与候选库耦合 | 从 CLI 边界转换 subject，并以 import 回归测试禁止 benchmark/runner 导入 candidate。 |
| 非原子创建留下部分 state | 以后选择或 gate 错误 | 每个 custody artifact 使用临时同级文件、fsync 与不可覆盖原子创建。 |
| runner/evaluator 故障被当成 subject 失败 | 错误反馈或不公平 gate | 中性状态和 gate receipt 只记录完整 5/5 Smoke 通过。 |
| 动态 manifest 测试碰触真实题单 | Final/reserve 泄漏 | 所有测试仅用临时合成 data/custody；不调用真实初始化命令。 |

## 5. 不在本轮执行的事项

- 真实 rotation/Final manifest 创建、Docker fixture、真实 DSH、模型、baseline 和 push。
- coding agent、自动 Skill 修改、candidate promotion/rollback、并发、第二 benchmark、SQL dialect、依赖或 CI。
