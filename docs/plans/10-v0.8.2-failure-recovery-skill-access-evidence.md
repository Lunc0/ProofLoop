# 实施计划：失败恢复窗口与 Skill 接触证据

> **阶段：**10 · **版本：**v0.8.2 · **状态：**已完成
>
> **依据规格：**[10-v0.8.2-failure-recovery-skill-access-evidence](../specs/10-v0.8.2-failure-recovery-skill-access-evidence.md)

## 1. 实施目标与边界

将现有 v2 agent projection 演进为 `evolution-coding-agent-input-v3`。v3 以 P0 失败 episode 作为不可拆分的 Optimizer evidence，记录失败前后的有限公开上下文、失败 action/result、至多三个后续 action/result，以及当前 evaluated Skill 的版本身份和读取观察。v1 custody artifact 和 v2 的历史读取能力不改变。

只使用现有 Python/Pydantic 组件与合成测试；不调用模型、真实 DSH、Docker、网络、baseline 或评测集。规则层只输出观察事实，不能把后续成功命名为“已修复”，也不能把 Skill read 归因为 coverage/adherence 结论。

## 2. 设计决策

- **局部 episode，而非完整步骤树：**每个失败保留一个 4 KiB 上限的前后窗口，移除全局 progress narration。
- **失败优先：**episode 作为 P0 原子单元参与 evidence 上限选择；其内的后续 action 不再重复输出。
- **subject provenance 特例：**只允许 `evaluated_skill.content_sha256` 标识 payload 已含的当前 Skill；禁止 session/context/custody hash。
- **保守 Skill access：**先以完整 content 严格匹配，再以已声明注入路径匹配；否则 `unknown`，从不把未观测解释为未覆盖。

## 3. 有序任务

### 任务 1：定义 v3 合同与 policy

**实施：**在 `contracts.py` 新增 v3 顶层、evaluated Skill、Skill access、failure episode 与受限 action 合同；在 `policy.py` 增加 episode 的文本、action 和总字节上限，并让其不影响 v1 fingerprint。

**验收：**v3 仅允许 subject SHA-256；所有新模型 frozen/strict；v1/v2 类型不变。

**文件：**`trajectory/contracts.py`、`trajectory/policy.py`。

### 任务 2：构建失败恢复 episode 与文本降噪

**实施：**从 v1 `CompressedStep` 的原有顺序扁平化 calls 和公开文本；为可配对直接失败生成 episode，选择相邻公开文本和后续 actions，遇成功或新失败停止；移除全局 `public_assistant_statement`。保留现有 SQL 结构化输出、sample coverage 和 trace state。

**验收：**每个 action 至多属于一个前序 episode；episode 不以 `corrective`/意图语言表述；无关过程播报不进入 evidence。

**依赖：**任务 1。**文件：**`trajectory/projection.py`。

### 任务 3：建立 evaluated Skill 与 read 对应关系

**实施：**将 evaluated subject 传入 case projection；以完整 read content 严格比较，或以注入 Skill 的声明路径保守匹配；按失败之前的动作顺序生成 Skill access，必要时从 evaluated Skill 选择可重放的约束摘录。

**验收：**exact、declared path、unknown 和未观测互斥；没有匹配绝不声称 coverage 缺失；绝对路径和 session hash 不进入 payload。

**依赖：**任务 1–2。**文件：**`trajectory/agent_input.py`、`trajectory/projection.py`。

### 任务 4：接线 v3 artifact 与合成验证

**实施：**更新 rolling writer/manifest 的 schema version；扩展合成 projection/rotation 测试，覆盖 multi-statement failure、停止规则、Skill access 状态、降噪和 v1/v2 隔离。

**验收：**agent input、manifest 和测试预期均为 v3；不写入真实 case/session；所有 scoped checks 通过。

**依赖：**任务 1–3。**文件：**`benchmark/livesqlbench_rotation_run.py`、三个既有 trajectory/rotation 测试。

## 4. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 把后续成功误判为恢复 | 只用 `*_observed` 状态和相对窗口，不建立根因结论。 |
| Skill read 截断导致错误身份匹配 | 仅完整内容可为 `exact`；其余降级为 path 或 `unknown`。 |
| episode 导致 payload 膨胀 | 固定 512-byte 文本、三 action、4 KiB 上限和 P0 原子选择。 |
| v3 泄露 custody identity | 类型白名单只允许当前 subject hash；测试扫描禁止字段。 |

## 5. 验证与检查点

任务 1–3 后运行定向 projection 测试；任务 4 后运行：

```powershell
uv run pytest tests/test_trajectory_compression.py tests/test_trajectory_projection.py tests/test_livesqlbench_rotation_run.py
```

验证仅使用合成 JSONL、stub runner、临时目录和无模型静态检查。完成后更新 `docs/design/` 与三个目录索引，供代码审查。

## 6. P1 修订任务

### 任务 5：以 result 为失败窗口边界

**实施：**在 `projection.py` 中以 failed call 的 result location 判断后续 action；
pre/post public context 只使用严格相邻方向的 compressed step，排除与 call 或 result
共用 step 的文本。不得修改 v1 `EvidenceText` 或 custody canonical bytes。

**验收：**合成 session 中，同 step 的失败后文本不会成为 pre-context；result 前已
发起的 call 不进入 post_failure_actions。

### 任务 6：将 Skill 摘录绑定到 adapter

**实施：**规则段落须同时含失败 adapter 与 direct failure cause 的规范化文本；
selection basis 明确记载两项约束。

**验收：**其他 adapter 的同原因规则不被摘录；`sql-readonly` 的明确规则仍被摘录。

**验证：**先运行新增的回归测试确认其在旧逻辑下失败，再执行既有定向 pytest、Ruff、
mypy 与 `git diff --check`。
