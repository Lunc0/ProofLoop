# 实施计划：Benchmark Runner Error 计为错题

> **阶段：**31 · **版本：**v0.29 · **状态：**已完成

## 关联规格

[阶段 31 v0.29 规格](../specs/31-next-runner-error-as-incorrect.md)。

## 实施方案

保留 `Verdict.RUNNER_ERROR` 作为诊断性的 case verdict，但将它从 evaluator/data 无效集合移到普通失败集合。对于抛出的 `RunnerError`，在共享 LiveSQLBench 层构造最小的 synthetic `RunnerCaseOutput` 和相同的 `CaseEvaluation`；它不含 candidate SQL、原始异常、成本、Gold 或虚构轨迹。各 benchmark loop 捕获该异常后追加该失败记录并继续下一题。只有 fixture/evaluator 异常仍暂停或产生 evaluator-invalid 状态。

## 任务与依赖

### Task 1：统一 case 级 runner-error 失败合同

**工作：**在 `livesqlbench.py` 增加受控 `RunnerError` 的最小 case 失败构造器；更新 attribution，使 `Verdict.RUNNER_ERROR` 与其他未通过 verdict 一样属于 Skill-side failure，而不再暂停实验。

**验收：**

- `runner_error` 返回状态和抛出的 `RunnerError` 均能生成 `passed == false` 的 evaluation。
- synthetic record 没有 candidate SQL、原始异常文字或编造 usage/result。
- `evaluator_invalid` 仍保留 eval-data attribution。

**验证：**`uv run pytest tests/test_livesqlbench_run.py tests/test_attribution.py`

**依赖：**无。

### Task 2：让 Base-Lite 与 held-out 在 runner 异常后继续

**工作：**在普通和 held-out DSH loop 中仅捕获 `RunnerError` 后追加 synthetic failure、继续下一 case；fixture error 继续使用原 paused/fail-closed 路径。保留已有 runner artifact 写入行为，仅在确实存在 `RunnerExecution` 时写入。

**验收：**

- 任一 runner exception 后，剩余 case 仍被调用，最终统计包含该错题。
- held-out 输出继续遵守 custody-only aggregate 边界。
- fixture 错误仍暂停，不会改算成错题。

**验证：**相关 Base-Lite 和 held-out fake-runner pytest。

**依赖：**Task 1。

### Task 3：更新 rolling 计数、状态与优化边界

**工作：**移除 `partial_runner_error` / discarded-runner-error 计分分支。rolling Smoke、Evolution 和 Final 统一保留 runner-error evaluation，并把 run status 决为 `task_failure`（除非仍有 evaluator-invalid）。可行动 timeout 保留既有可压缩轨迹进入 optimizer 的能力；不可压缩错误只计入错误结果。更新公共结果 aggregate、comparison key 与 CLI status allow-list。

**验收：**

- runner error 不产生 `runner_invalid` 或 `partial_runner_error`，计入 tier 分母、失败数和 evaluated count。
- Evolution 保留可行动 timeout 的 optimizer evidence，但不将无 session/error 伪造为 evidence。
- `partial_evaluator_invalid`、`evaluator_invalid` 和其 comparison-key 限制保持不变。

**验证：**`uv run pytest tests/test_livesqlbench_rotation_run.py tests/test_evolution_cycle.py`

**依赖：**Task 1。

### Checkpoint：离线计分与边界

- [ ] Base-Lite、rolling 与 held-out 的 fake-runner 回归通过。
- [ ] Smoke gate 仍只按通过数判断；runner-error 贡献 0 通过、1 已评测失败。
- [ ] 没有真实 DSH、Docker、模型、网络或 benchmark 调用。

### Task 4：完成验证与设计记录

**工作：**运行定向测试、Ruff、mypy 和 diff 检查；将规格、计划与索引状态更新为已完成，记录实际实现与验证结果。只在全部检查成功后写 design。

**验收：**

- 文档只陈述已实施和已验证的行为。
- 变更保留 fixture/evaluator fail-closed 与 custody 安全边界。

**验证：**运行 `tests/test_livesqlbench_run.py`、`tests/test_livesqlbench_rotation_run.py` 与 `tests/test_evolution_cycle.py` 的 pytest，以及 Ruff、mypy 和 diff 检查。

**依赖：**Tasks 1–3。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| runner exception 没有 case 输出 | 只构造固定、最小的失败 case，不复制异常文本或伪造执行证据。 |
| runner 错误被误送入 optimizer | 继续只接受已有 session 且压缩成功的轨迹。 |
| 评测器故障被错误记为错题 | `LiveSQLBenchFixtureError` 和 `Verdict.EVALUATOR_INVALID` 分支不改变。 |
| held-out 统计或材料泄漏 | 复用 custody-only result writer，不新增 case-level public 输出。 |

## 非并行项

Task 2 和 Task 3 都依赖 Task 1 的 synthetic 失败合同；Task 4 在所有行为测试完成后执行。
