# 实施计划：Held-out 单题诊断运行

> **阶段：**32 · **版本：**v0.30 · **状态：**已完成

## 关联规格

[阶段 32 v0.30 规格](../specs/32-v0.30-heldout-single-case-run.md)。

## 实施方案

在 held-out 专属模块中新增精确 case 选择和 single-run evidence 写入路径。单题 runner 复用现有
`_run_case`、Soft-EX evaluator、DSH 配置校验和 subject materialization，但使用独立的
`single-runs/<timestamp>-<instance_id>` append-only 目录及 `single_case_diagnostic` schema。CLI 使用独立
`benchmark run-heldout-case` 命令，直接加载固定 held-out adapter/suite；它不修改通用
`BenchmarkAdapter` 协议，也不向其他 suite 暴露 case filtering。

单题公开结果只返回 suite/manifest/subject binding、diagnostic mode、status、evaluated count、duration 和
可安全取得的 cost；不返回 run ID、case ID、目录路径、逐题 verdict、tier 或 macro score。完整 evidence
留在 custody，且从该命令不存在 optimizer、gate 或 candidate lifecycle 出口。

## 任务与依赖

### Task 1：建立精确选择与 single-runs custody 合同

**工作：**为 `HeldOutCustody` 增加 `single_runs_root`，新增精确 `instance_id` 选择函数和不可覆盖的
`<UTC timestamp>-<instance_id>` 目录创建函数。创建前检查直接父目录、symlink/reparse/path escape，未知 ID
返回不枚举有效 case 的固定错误。

**验收：**

- 精确 ID 只返回 manifest 绑定的一题；未知、模糊或 unsafe 输入均失败。
- single-run 目录只能位于 custody 的直接 `single-runs/` 子目录，名字满足规格且不可覆盖。
- 验证和选择失败发生在 fixture/DSH/model 副作用前。

**验证：**`uv run pytest tests/test_livesqlbench_heldout.py -k "select or single_run_directory"`

**依赖：**无。

**文件：**`src/skill_evolve/benchmark/livesqlbench_heldout.py`、`tests/test_livesqlbench_heldout.py`。

**范围：**小。

### Task 2：实现单题 custody-only 执行与结果合同

**工作：**新增单题 run service，复用现有 `_run_case` 和 artifact writer；成功、runner error、fixture invalid
都只形成一题 evidence，并写入 `single_case_diagnostic` metadata/result。构造不带 case identity、路径和 verdict
的最小 public receipt，不生成 Final tier/macro aggregate。

**验收：**

- stub runner 恰好调用一次，run input 恰好一题，其他 29 题不建立 fixture。
- 完整 evidence 只在 single-run custody；普通 `runs/` 和 Final `heldout/runs/` 不新增。
- runner error 计为诊断错题，fixture invalid 仍 fail closed；公开 receipt 不泄漏私有材料。

**验证：**`uv run pytest tests/test_livesqlbench_heldout.py -k "single_case"`

**依赖：**Task 1。

**文件：**`src/skill_evolve/benchmark/livesqlbench_heldout_run.py`、`tests/test_livesqlbench_heldout.py`。

**范围：**小。

### Task 3：接入独立 CLI 与 candidate binding

**工作：**在 `cli.py` 新增 `benchmark run-heldout-case`，按既有顺序解析可选 candidate、加载固定 held-out
suite、验证 DSH manifest/model 后调用单题 service。CLI 只打印最小 public receipt，并按既有 paused 语义
返回退出码；不改通用 `benchmark run`。

**验收：**

- CLI 接受 `data-root`、`dsh-manifest`、必填 `--case` 与可选 `--candidate`。
- 未知 case、坏 manifest/candidate/custody 在模型前失败，stderr 不枚举 held-out identity。
- CLI stdout 不包含 case ID、prompt、GT、SQL、verdict、异常原文或绝对 custody 路径。

**验证：**`uv run pytest tests/test_livesqlbench_heldout.py tests/test_benchmark_cli.py -k "heldout"`

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 把单题过滤加入通用 adapter 协议 | 其他 suite 意外获得私有 case 选择入口 | 使用 held-out 独立 CLI/service，不修改通用协议。 |
| 复用 Final aggregate writer | 伪造 30 题分母、tier 或 macro score | 单题使用独立 diagnostic schema 和最小 receipt。 |
| 目录名包含用户自由文本 | 路径逃逸或日志命名污染 | 只允许 manifest 已验证的精确 `instance_id`。 |
| 目录冲突覆盖历史 evidence | 审计链损坏 | 使用原子、不可覆盖创建；冲突 fail closed。 |
| stdout 泄漏题目或 custody | held-out identity 离开 custody | 固定 receipt 字段和负向泄漏测试。 |
| 单题结果进入优化或 gate | 数据泄漏或错误晋级 | 独立命令无 optimizer/gate 出口，metadata 显式诊断模式。 |

## 非并行项

Task 2 依赖 Task 1 的选择与目录合同；Task 3 依赖完成的 service；Task 4 只能在代码与测试真实完成后写
design。为了避免共享 held-out 文件上的交叉修改，本阶段顺序实施，不使用并行 agent。
