# v0.2 设计：真实 DSH 与 DeepSeek v4 接入

**状态：**实施中——headless adapter 已完成离线验证，等待本机 profile 与模型配置后进行真实冒烟运行。

## 目标

用固定版本的、无交互 DSH 执行替换 fake runner：加载一个本地 SQL Skill，并使用配置好的
DeepSeek v4 profile。保留现有 PostgreSQL evaluator 作为 SQL 正确性的唯一裁决者，并建立可复现的
真实运行 baseline。本阶段不修改或自动演进 Skill。

## 当前起点

v0.1 workflow 已有稳定的 `Runner` contract、不可变的 run artifact、隔离且只读的 PostgreSQL
evaluator、失败归因，以及 `fast` / `dev` / `held_out` case 切片。v0.2 只实现真实 adapter 和
baseline，不得削弱 evaluator 的隔离边界。

## 待确认的假设

1. DSH 有无交互命令，可加载指定 profile 和本地 `SKILL.md`，并能写出或暴露 session trace。
2. DeepSeek 凭据仍在 DSH 正常的密钥存储或环境中；绝不写入 experiment manifest、run 目录、
   trace 或 Git。
3. Agent 通过获准的本地 Skill 和/或只读 tool 获得数据库 schema 上下文，绝不获得生产数据库凭据。
4. DSH run 的可重复性足以固定其 release、profile 身份、模型参数、Skill 字节、tool manifest
   字节和 session-log schema。
5. 初始 SQL benchmark 使用可销毁 PostgreSQL fixture。若使用真实 DSH SQL tool，则它仅能访问带有
   受限角色的该 fixture。

## 设计

```text
manifest + 本地 SKILL.md + 固定 DSH profile
                  |
                  v
         DshRunner（argv array，shell=False）
                  |
       脱敏 stdout/stderr + 后续可选 session trace
                  |
                  v
         RunnerOutput v1（每个 case 一条记录）
                  |
                  v
   现有 PostgreSQL policy + objective evaluator
                  |
      失败证据 / 计分卡 / baseline
```

### 1. 真实 DSH adapter

`DshRunner` 每个 case 只运行一个 DSH session。它只从 allowlist argv array 构造 DSH 命令，绝不由
shell string 构造；DSH 以 experiment workspace 为 current directory，从而可按官方规则发现项目本地
Skill。首版调用 `dsh --profile <profile> [--patch <path>] <job>`，并要求最终答案只包含一个标记为
`sql` 的 fenced code block。

adapter 将 headless process evidence 规范化为 `RunnerOutput v1`：

- 每个请求的 `case_id`、终态、final message 与提取出的 candidate SQL；
- DSH invocation 与 final answer event；持久化前对密钥进行脱敏；
- 仅记录 DSH 实际提供的 provider-reported input token、output token 和 cost；缺失值保持
  `null`，绝不估算；
- case 缺失、case 重复、DSH 进程失败或 SQL 提取存在歧义时产生 `runner_error`。这些都是
  `eval_data` failure，不能归因为 Skill bug。

SQL block 之外的自然语言不参与 SQL evaluation；没有 SQL block 会得到 `no_sql_generated`。DSH 的
session trace 路径和 schema 尚未固定，因此首版不会扫描或复制整个 `DSH_HOME`；获得一份真实脱敏
session 后再将其作为声明的额外 artifact 接入。

### 2. 可复现配置与证据

真实 CLI protocol 已固定为 DSH 的 headless public entry point。`dsh` manifest 区域记录非敏感的
DSH release、profile、可选 profile patch、`binary`、传给 profile 的 `runner_args` 与 `timeout_ms`。
`runner_args` 禁止包含 credential option 或 value。导入 Skill 后，`candidate.digest_file` 指向其
`SKILL.md`，使其字节内容进入 fingerprint。

```yaml
dsh:
  version: 0.1.1-rc.2
  profile: headless
  runner: dsh
  binary: dsh
  runner_args: []
  timeout_ms: 300000
```

每个 live run 都会保存：

- resolved 后的非敏感 manifest，以及 Skill、profile patch、tool manifest、schema 和 seed 的 hash；
- `raw/dsh/<case>.invocation.json`、脱敏后的 stdout/stderr，以及内部规范化的
  `raw/runner-output.json`；
- evaluator 所使用的规范化 trajectory 与 `RunnerOutput`；
- evaluator result、attribution，以及按 slice 分组的 scorecard。

保存前会清除常见的 API key、Bearer token 和 credential assignment。任何密钥都不得出现在 manifest
或 `runner_args` 中；发现无法安全处理的敏感 evidence 时，必须停止 run 并修复 adapter，而非保留它。

### 3. Baseline

先以未修改的 champion Skill，在一个小型且经手工验证的 `fast` suite 上运行。其证据和 fingerprint
定义 baseline。只在 fast 稳定后再加入 `dev`。`held_out` 不得写入 Skill 修改 prompt；条件允许时应
放入受保护存储或受保护 CI job。仅按目录命名不能构成保密边界。

## 交付计划

### Phase 0 — 本机 DSH 配置确认

确认本机 `headless` profile、DeepSeek v4 credential reference 和无需 Skill 的最小 SQL case。

**退出条件：**DSH 能从本机执行一条 SQL task，adapter 能保存脱敏 stdout/stderr 并得到单一 SQL block。

### Phase 1 — DSH adapter

实现 config validation、`DshRunner`、单一 SQL block parser、raw artifact capture/redaction，以及使用
mock subprocess 的 contract test。`FakeRunner` 保留为离线 test path。

**退出条件：**`skill-evolve run ... --suite fast` 能调用 DSH，并且要么写入完整 evidence，要么以精确
repair checklist 安全暂停。session trace 接入不阻塞该退出条件。

### Phase 2 — 真实 baseline

创建唯一的本地 Skill、小型稳定的 `fast` suite 和冻结的 baseline run。

**退出条件：**baseline 可复现；所有 score/cost field 均为 provider-reported 或明确为 unknown。

## 明确延后范围

候选 Skill 生成、候选目录、score comparison、`fast → dev → held_out` gate、champion promotion、
rollback 和任何自动 Skill 修改均不属于本阶段。它们只在真实 DSH run、证据格式和 baseline 经验证后
另行设计和实现。

## 开始 Phase 0 所需信息

请提供下列信息，但不要提供 API Key 或其他密钥：

1. **本机 DSH profile：**`headless` 是否可用；如使用自定义 profile，请提供其名称。
2. **一次手工调用：**向 DSH 发送 SQL task 的完整脱敏 command，包含 current directory 和所有非敏感
   flag。
3. **DeepSeek v4 profile：**profile 名称和脱敏 config/profile file，展示 model selection、
   temperature、必要的 endpoint identifier，以及 secret reference 的位置（environment-variable name
   即可，不能提供其值）。
4. **Skill 加载：**本地 Skill directory/file，以及 DSH 加载它的正式方式（CLI option、profile field、
   plugin/bundle 或 workspace convention）。
5. **Tool contract：**agent 如何获得 schema/data context；若它会运行 SQL，请提供 read-only tool
   definition 及 command/protocol，并确认它只访问 disposable fixture。
6. **Evidence sample：**一个 completed case 的 stdout 与 stderr（仅删除密钥）。session/trajectory
   log 可在首条真实 run 后单独接入。
7. **Benchmark policy：**初始 `fast` case 的数量与题目来源；`dev`/`held_out` 可以暂不提供。

## 边界

- 始终执行：使用 disposable PostgreSQL fixture、非特权只读 role、`shell=False` 的 argv array、
  不可变 evidence，并且只记录精确的 provider usage。
- 先询问：新增 SQL dialect、接入真实/生产 DSH 或 database、concurrency、external CI，或任何自动
  Skill 修改。
- 绝不执行：在 repository 或 run artifact 中存储 secret；以 privileged role 执行 candidate SQL；使用
  held-out data 生成 candidate；覆盖当前 Skill 或删除 evidence。

## 成功标准

1. 一个本地 DSH + DeepSeek v4 SQL run 能被捕获并规范化为现有 runner contract；evidence 异常时有
   确定的失败模式。
2. 生成的 SQL 持续只由 disposable PostgreSQL evaluator 做客观验证。
3. 每个 run 均可恢复并 fingerprint 当前 Skill bytes、profile/tool input 与 DSH version。
4. 本阶段的任何 run 都不得修改当前 Skill。
