## 1. 实际实现

新建 Smoke manifest 现在一律写为 v2，并固定选择 Simple 3、Moderate 2、Challenging 0。`selection_index`
仍保留为不可变的审计字段，但不再参与 Smoke 配额轮换。Evolution 继续写 v1 manifest，且仍为三个 tier 各 5 题。

Smoke run 在完整执行五个 case 后，只要 4 或 5 个 case `passed` 且没有 runner/evaluator 无效状态，便写入 v2
gate receipt。4/5 的整体 run status 仍为 `task_failure`，避免把一次含 task failure 的运行伪装成完整成功；gate
receipt 另保存实际通过数、`case_count=5` 和 `minimum_passed_case_count=4`。

## 2. 历史兼容与 retirement

`RotationManifest` 可严格读取 v1 和 v2：v1 Smoke 按历史 `2/2/1` 轮换校验，因此可继续审计；但
`load_rotation_suite` 会在 fixture、DSH、Docker 或模型构造之前拒绝 v1 Smoke。历史 Evolution v1 manifest
未改变。

gate 读取同样支持 v1/v2 摘要验证，但 `has_successful_smoke_gate` 只承认满足当前字段合同的 v2 receipt。
所以历史 5/5 gate 既不被重写，也不能放行新的 Evolution。所有 receipt 保持 subject hash binding、manifest hash
和环境 fingerprint，不含 case ID、题目、GT、Gold、session 或凭据。

## 3. 指标与安全边界

由于 Smoke 不再包含 Challenging case，Smoke 的 Challenging tier 指标为 `case_count=0`、`evaluated_count=0`、
`passed_count=0`、`pass_rate=null`，避免把未覆盖 tier 记作 100%。Evolution 的完整三层指标与比较键不变。

gate 是否写入只从已生成的 `CaseEvaluation` 派生：必须恰有五个 evaluation，run status 只能是 `passed` 或
`task_failure`，且 `passed` 数为 4 或 5。三题及以下、早停、`runner_invalid` 与 `evaluator_invalid` 均 fail closed。

## 4. 验证结果

在合成 fixture、stub DSH runner 和本地 fake optimizer 上执行：

```powershell
uv run pytest tests/test_livesqlbench_rotation.py tests/test_livesqlbench_rotation_run.py
uv run ruff check .
uv run mypy src
git diff --check
```

结果：定向测试 **7 passed**；Ruff 通过；mypy 对 **67 个 source 文件**通过；最终 diff 检查无空白错误。
测试覆盖固定 `3/2/0`、Evolution `5/5/5` 回归、v1 Smoke 审计读取和运行拒绝、4/5/3/5 gate、v1 gate 拒绝与
runner invalid 拒绝。

未调用真实 Smoke、Evolution、Final、DSH、Docker、数据库或模型，也未创建真实 manifest、gate、candidate 或
held-out artifact。
