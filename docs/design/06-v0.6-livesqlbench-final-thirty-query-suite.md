## 实际实现

阶段 06 在静态 registry 中增加 `livesqlbench-base-lite-query-final-v1`，不改动既有
`livesqlbench-base-lite` 五题 smoke suite、`livesqlbench` 兼容命令、公开 case summary 或普通 run evidence 语义。

`benchmark/livesqlbench_heldout.py` 定义 frozen、strict Pydantic manifest。它只保存 schema version、suite ID、
public JSONL SHA-256 与每题必要的公开 metadata；不保存 prompt、Gold SQL、GT test/result、dump 或凭据。选题只读取
public JSONL，使用系统随机性选择可行解，并验证：三十个唯一 Query case、三层各十题、每层十个不同数据库、全局恰十八个
数据库、单库至多两题，以及排除五题 smoke。若同一层可取得两种 `conditions.order`，选择器会优先保留两种；该偏好不会在
数据不可满足时变成硬失败。原子写入之前，初始化还会检查已选题对应的 public、GT、context、dump 与 table-order
材料及其元数据一致性；材料不完整时不会留下不可覆盖的 manifest。

`SKILL_EVOLVE_HELDOUT_ROOT` 必须是已存在的绝对目录，且与 repository 和 `.local/skill-evolve/` 不重叠。解析会拒绝
symlink、路径逃逸、不可读/不可写 root、非法/过大/篡改 manifest、public digest 漂移、public/GT 不一致和缺失的公开
context、dump 或 table-order 文件。manifest 名称固定为 custody root 内的
`livesqlbench-base-lite-query-final-v1.json`，以临时文件、fsync 和原子 hard-link 创建；目标已存在即拒绝，不会覆盖或
重写。代码不提供默认外部目录；评测器可在仓库外预建 root、`runs/` 与 `dsh-session-logs/`，但真实 manifest 仍只能在
获得单独明确授权后创建。该授权已获得并完成一次初始化；真实 manifest 只保存在 evaluator custody 中，仓库、文档和
公开命令均不记录其 case list。

## 执行与公开合同

`benchmark initialize-heldout <data-root>` 是 evaluator-only 初始化入口：成功 stdout **仅**输出 `suite_id` 与
`manifest_sha256`。`benchmark validate` 的 held-out adapter summary 仅含 suite/hash、总数及按难度数量；
`benchmark evaluate` 会拒绝公共 runner-output 文件，避免 case-level 输入或结果通过该命令离开 custody。

`benchmark run livesqlbench-base-lite-query-final-v1 <data-root> <dsh-manifest>`（可选 `--candidate`）忽略普通 workspace
`runs/` root，改在 custody root 的 `runs/` 下创建 evidence。每题仍是串行、独立、可销毁的 PostgreSQL fixture；DSH 只取得
该题公开 prompt/schema/context、验证过的 `candidate/SKILL.md`（若有）和只读 SQL capability。Soft-EX、低权限只读 SQL、
Gold 仅进程内，以及 timeout/nonzero exit 的脱敏 session capture 都继续复用。

held-out run 在 custody 中保存 prompt、case ID、candidate SQL、逐题 verdict、runner output、trajectory、redacted DSH
session artifact、candidate bytes、GT-safe private report 与 aggregate result。外部 stdout 仅有 suite ID、manifest hash、
candidate binding 或 `null`、状态、30 题总数、每 tier 的总数/已评数量/通过数/通过率、三个 tier 等权 macro-average、总耗时
和仅在全部 30 题均报告成本时才给出的 `cost_usd`；不输出 case ID、SQL、路径、prompt、Gold、GT、dump、凭据或 session
内容。若 run 未完整取得三层结果，`macro_average` 和总成本为 `null`，不会将部分数据伪装成正式分数。

真实 held-out run 还要求 `dsh.session_log_root` 与 custody root 中预先存在的 `dsh-session-logs/` 精确一致；否则在 Docker
或 DSH 之前 fail closed。部署层仍必须把实际 DSH session writer、OS ACL、container mount 或独立机器配置到这个 custody
边界。代码只验证路径和写入边界，**不**声称 `.gitignore`、Python 路径检查或自身进程权限能够提供跨进程的隔离保证。
