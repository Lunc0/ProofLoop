> **阶段：**13 · **版本：**v0.11 · **状态：**已完成
>
> **规格：**[结构化 Skill 与行为导向修改计划](../specs/13-v0.11-structured-skill-edit-plan.md) ·
> **计划：**[实施计划](../plans/13-v0.11-structured-skill-edit-plan.md)

## 1. 实际实现

v0.11 在既有 v0.9 advice 旁新增显式 `skill-evolve optimizer plan <run-id>`。它只打开一个已经完成的
Evolution run，不启动新 run，也不改变 manifest、rotation 自动 advice、benchmark 状态或 candidate 生命周期。

命令复用现有 DeepSeek 无工具 client，但使用独立的 `skill-edit-plan-prompt-v1` 和严格
`skill-edit-plan-model-v1` 返回合同。模型只能提出缺陷簇、语义操作、行为规则要素和可证伪验证；本地服务负责
Skill map、可信 target contract、所有 source hash、权限、引用闭集、本地 ID 和最终状态。

本阶段仍不生成 Markdown patch、不修改 `SKILL.md`、不创建 child，也不执行 Failure Replay、回归、消融、
晋级或回退。

## 2. 模块与公开合同

### 2.1 共用 Evolution 准入

`optimizer/evidence.py` 从 v0.9 service 抽出 fail-closed 准入。它只读取 run 内非 symlink 的
`agent-input/manifest.json` 和 `agent-input/trajectory.json`，验证：

- v3 schema 与 `exposed_for_optimization: true`；
- canonical JSON 和 agent-input SHA-256；
- 输入大小、环境 fingerprint、projection rule version 和 included case count；
- materialized subject ID、Skill SHA-256 及 UTF-8 Skill 正文完全一致。

v0.9 advice 改为复用该读取函数，原有 prompt、artifact、receipt、自动触发和 CLI 行为不变。

### 2.2 `skill-map-v1`

`optimizer/skill_map.py` 使用标准库单遍解析 UTF-8 Markdown，识别 frontmatter、标题、段落、连续列表、
fenced code block 和表格。它不执行 Skill、不读取引用文件、不访问网络，也不判断业务语义。

每个 block 包含标题路径、类型、行号、内容 hash、逻辑层和权限。block ID 同时绑定完整 Skill SHA-256、
标题路径、类型、行号和区块内容 SHA-256；相同字节输入产生相同映射。未闭合 frontmatter/代码块、非法 UTF-8、
NUL、空输入和超限输入 fail closed。

固定标题策略把 Runtime/Safety 合同映射为 `locked`，Core Strategy 已知章节映射为 `evolvable`，
Heuristics/Examples 映射为 `experimental`；Purpose/Activation 和未知旧章节保守映射为 `guarded`。

### 2.3 `skill-target-contract-v1`

`optimizer/target_contract.py` 只为 `livesqlbench-base-lite-evolution-v1` 返回固定可信合同：`sql-readonly`、
只读、单次一条 statement、三类任务上下文来源和单条最终 SQL 输出。合同由仓库代码构造并绑定 canonical
SHA-256，不从 Skill、trajectory、模型输出或 run artifact 推断，也不包含 endpoint、凭据、路径、GT 或 Gold。

### 2.4 `skill-edit-plan-v1`

`optimizer/edit_plan_contracts.py` 定义冻结、拒绝额外字段的 Pydantic 合同，包括：

- 九个功能模块、九类缺陷、四类作用域和八种语义操作；
- `locked`、`guarded`、`evolvable`、`experimental` 四级权限；
- workflow、recovery、constraint、heuristic 四类规则的不同必填行为要素；
- 行为断言、缺陷类型最低证据、最多三个 edit 和本地 source binding；
- `proposed`、`requires_guarded_approval`、`findings_only` 及失败 terminal status。

`incorrect_guidance` 必须引用 Skill block 和可信合同字段；contradiction/redundancy/priority conflict 必须引用
至少两个 block；underspecified/workflow/recovery 具有各自最低字段。模型不能声明 source hash、状态或本地 ID。

## 3. 计划生成流程

`optimizer/edit_plan_service.py` 的实际顺序是：

1. 验证 run status、v3 evidence 与 exact subject；
2. 本地生成 Skill map 和可信 target contract；
3. 为 case/evidence 派生只在当前计划中有效的 hash 引用，不把原始 case ID写入模型输出合同；
4. 把 JSON schema 作为可信块，把 Skill、target contract 和投影 evidence 作为转义后的不可信块；
5. 调用无工具 client 最多一次；
6. 校验引用闭集、case/evidence 关系、block/contract 字段、缺陷最低证据、operation 映射、模块一致性、
   target 可追溯性、edit 重叠、权限和敏感文本；
7. 本地生成 cluster/edit ID、状态和 source binding，原子发布 artifact 目录。

多 case 可以归入一个 cluster，一份计划最多三个 edit。不同 edit 不能共享 target 或 placement block。
对 `locked` block 的 edit 会被拒绝；如果所有 finding 都只涉及 locked block 且模型没有 edit，则保存
`findings_only`。guarded target 产生 `requires_guarded_approval`，但本阶段不会继续应用。

> 后续策略调整：上述状态是 v0.11 已落地 artifact 的历史事实。阶段 14 将兼容读取该状态，但不再把它解释为人工审批门槛；
> guarded edit 只要通过 parent/target binding 与 diff 机械校验即可 materialize。`locked` 仍被拒绝。

## 4. Artifact 与兼容性

成功、待批准或纯 finding 写入：

```text
optimizer/edit-plan/
  skill-map.json
  edit-plan.json
  edit-plan.md
  receipt.json
```

四件产物先在 run 内同级临时目录完整生成并回读，再切换到目标目录。非法 evidence、provider 错误或非法模型输出
只发布 terminal receipt，不保留旧 plan 伪装成当前结果。

根 `result.json` 的 `optimizer_edit_plan` 只包含 status、相对 plan/map 路径、provider/model/prompt、plan/map
SHA-256 和 cluster/edit 数量。stdout 只输出 run ID 和同一摘要，不复制 Skill、prompt、evidence 或计划正文。

v0.9 的 `optimizer/advice.json`、`optimizer/advice.md`、`optimizer/receipt.json` 和根 `optimizer` 摘要保持原样；
新产物位于独立子目录，显式 plan 不被 rotation 自动调用。

## 5. 安全边界

- Skill、trajectory、模型输出始终是不可信数据；Skill 中的 XML 结束标签会在提示中转义。
- 模型引用必须属于本地 case/evidence/block/contract-field 闭集；source binding 只能由服务加入。
- semantic text 拒绝机械 patch、完整 Skill、绝对私有路径、credential-like 和 private-answer-like 内容，以及原始 case ID。
- runner/evaluator invalid、空失败集、subject/hash 漂移、未知 adapter 或超限输入不会调用模型。
- CLI 只接受同时由 `run.json` 和 `result.json` 绑定的已完成 Evolution run；Smoke、Final、held-out 和普通 adapter
  不能进入该路径。
- target contract 和 plan artifact 不进入 candidate store；阶段 13 没有任何自动 Skill 修改能力。

## 6. 验证结果

使用合成 Skill、合成 v3 artifact、fake client 和本地 CLI runner 完成了无模型、无网络、无 Docker 的验证：

```powershell
uv run pytest tests/test_edit_plan_contracts.py tests/test_target_contract.py tests/test_skill_map.py tests/test_optimizer_contracts.py tests/test_optimizer_service.py tests/test_edit_plan_service.py tests/test_optimizer_cli.py tests/test_edit_plan_cli.py
uv run ruff check src/skill_evolve/optimizer src/skill_evolve/cli.py tests/test_edit_plan_contracts.py tests/test_target_contract.py tests/test_skill_map.py tests/test_edit_plan_service.py tests/test_edit_plan_cli.py
uv run mypy src
git diff --check
```

结果为 **30 passed**；Ruff 通过；mypy 对 **64 个 source 文件**通过；`git diff --check` 无空白错误，
只有 Git 的 LF/CRLF 转换提示。测试覆盖确定性权限映射、合同最低证据、未知引用、locked/guarded、
findings-only、多 case 聚类、DBHub 多 statement 与单 statement target contract 冲突、私有路径拒绝、提示结束
标签转义、原子替换、v0.9 service/CLI 兼容和显式 plan CLI。

没有执行真实 DeepSeek、DSH、Docker、数据库、Smoke、Evolution、Final 或 held-out，没有生成 patch、修改 Skill、
创建 child、操作 candidate store 或推送远端。
