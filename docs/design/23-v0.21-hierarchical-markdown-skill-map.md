## 实际实现

`build_skill_map()` 现在生成 `skill-map-v3`。它只序列化标题 block 的 `block_id`、`heading`、`heading_level`、`permission`：标题路径采用 `b1`、`b1.2`、`b1.2.4`。标题与字节范围在 parser 内部计算，不写入 artifact 或模型输入；fenced code 内的伪标题被忽略。

新模型计划为 `skill-edit-plan-model-v2`，持久化计划为 `skill-edit-plan-v2`。每个 edit 只有：

- `replace_block`：`target_block_id` 与完整 `replacement_markdown`；
- `add_block`：`parent_block_id`、可选直接子 `after_block_id` 与完整 `new_block_markdown`。

替换文本保留其标题行，允许改标题文字；后续标题不得提升至目标同级或更高层。新增文本必须从 parent 的下一标题层级开始，因此不能新增一级标题。

## 绑定与渲染边界

binding 和 renderer 都检查 block 是否存在、fragment 标题边界、direct-child `after` 关系、祖先/后代影响范围重叠，以及 locked block 的祖先/后代关系。cluster 仍只通过 edit 的 `cluster_indices`/`cluster_ids` 建立归因关系；不会用于 block、rule 或运行时 contract 校验。

renderer 重新解析 parent Skill 后才取得私有 section span，逆序写入 replace/add 结果，并重建 v3 map、生成 unified diff、精确回放 patch。它不做行级/list-item patch、规则语义推断、自动 Markdown 修复或 edit 重排。

## 兼容性

历史 `skill-edit-plan-v1` 继续使用 `build_legacy_skill_map()` 和 legacy renderer policy v2；新 v2 plan 使用 renderer policy v3。materialize 从实际 render 结果写 provenance，避免历史计划被误标为 v3。candidate store 验证 v3 map，同时接受与同一 Skill 字节一致的历史 v2 map；显式 rebuild 产出 v3。

当前 `raw-response.txt` 对应的 v1 proposed plan 未被转换或 materialize；要使用标题 section 语义，必须重新生成 v2 EditPlan。

## v6 提示词后续

阶段 23 的 section-level plan 路径后续将默认 prompt 升级为 `skill-edit-plan-prompt-v6`。该版本要求模型先做
跨 case 聚类、区分目标兼容性与失败因果假设、满足 defect-specific 证据门槛，并按最终 section 位置提出最小修改。
完整 section 替换必须保留无关行为；每项 edit 还须给出行为断言及 `automatic` 或 `review_only` 验证模式。

该提示词不改变 SkillMap、plan schema、binder、renderer、materialize、gate 或候选生命周期。模型输出仍须经过既有
schema、引用闭集、target contract、locked/overlap 与敏感文本检查；prompt 不是安全证明。receipt 继续接受历史
prompt v1–v5，新生成 plan 记录 v6。
