# 实现记录：失败恢复窗口与 Skill 接触证据

> **阶段：**10 · **版本：**v0.8.2 · **状态：**已完成
>
> **规格：**[失败恢复窗口与 Skill 接触证据](../specs/10-v0.8.2-failure-recovery-skill-access-evidence.md) · **计划：**[实施计划](../plans/10-v0.8.2-failure-recovery-skill-access-evidence.md)

## 1. 实际实现

`build_evolution_agent_input()` 现生成 `evolution-coding-agent-input-v3`，rolling runner 的 `agent-input/trajectory.json` 和 manifest 同步标为 v3。v1 custody artifact 与 v2 合同仍保留，未改写其 canonical bytes、读取路径或 custody 语义。

v3 的 `evaluated_skill` 含 `subject_id` 和 `content_sha256`。后者是安全处理后、实际随 payload 交付的 `skill` UTF-8 文本的 SHA-256，因此不会把一个可能已清理的文本错误地标识成原始 subject 内容。除此以外，v3 不输出 session、context、artifact 或 custody hash。

## 2. Failure Context Window

每个已配对的直接工具失败现在投影为一个 P0 `failure_recovery_episode`，而不是平铺的 `tool_failure` 加上 `later_same_tool_success` 布尔值。episode 包含：

- 当前或之前 step 的最后一条公开 assistant 文本，作为 `pre_failure_public_context`；
- failed action、direct failure 和受限 error；
- 紧接后一个 step 的首条公开文本（若存在）；
- 至多三个后续 action/result，按既有压缩 calls 的稳定顺序输出；
- `first_subsequent_success_observed`、`no_success_observed` 或 `truncated_before_success` 的观察状态。

遇到首个后续成功 action 时窗口停止；若先遇到新的失败，前一个 episode 停止并由新失败创建自己的 episode。因此后续 action 不会跨两个 episode，也不会重复作为独立 evidence 输出。`trace_state` 这类没有失败 call/result 配对的 P0 evidence 保持独立。

全局 `public_assistant_statement` 已从 v3 移除。公开文本仅作为上述局部窗口的前后上下文保留；没有将其解释为内部 reasoning 或规则引擎认可的结论。

## 3. Skill read 与文本限制

失败前成功的 `read` 依次检查：完整、未截断 read output 是否与当前 payload Skill 严格相同；否则其安全 target 是否为声明的 `subject/SKILL.md`（包括标准 workspace 前缀）。结果分别为 `exact`、`declared_subject_path` 或 `unknown`。

没有匹配 read 时，完整 trace 输出 `not_observed`，不完整 trace 输出 `unknown`。两者都不等同于 Skill 没有该规则。若 direct failure 的规范化原因短语在当前 Skill 的一个段落中精确出现，v3 才输出带 `direct_failure_cause:*` basis 的有界 `rule_excerpt`；没有命中时不伪造摘录。

每个 episode 的前后公开文本最多 512 bytes、后续 action 最多三个、总字节数最多 4 KiB。投影先删除尾部后续 action，再删除前后上下文；若仍超限，会收缩 failed action 为 tool、direct failure、受限 error 和至多两个受限 action 参数。这样 P0 直接失败不会因大参数列表而突破输入边界。

schema、knowledge 与 column-meaning 的选择继续复用 v0.8.1 的直接引用与 fallback 机制；非 subject 的 read 没有被复制成 Skill evidence。

### 3.1 P1 修订：保守时序与 adapter 关联

`evolution-projection-v3.1` 保持 v3 schema，但以 failed tool result 而非 call
所在 step 作为后续窗口边界。`pre_failure_public_context` 只来自严格更早的
compressed step；与 call 同 step 的文本不再倒灌到失败前。`post_failure_public_context`
只来自严格晚于 result step 的文本；同 result step 的文本不作时间推断。后续 action
也必须在 result location 之后才进入窗口。因此，现有 v1 不保存单条 assistant text
location 时，投影宁可省略不确定文本，也不会倒置其与失败的关系。

Skill 摘录现在同时要求规范化段落包含 failed adapter 与 direct failure cause，且
`selection_basis` 记录两项条件。失败前确实读到当前 Skill、但找不到双重匹配段落时，
仍只输出 read observation，不输出任何 coverage 或 adherence 结论。

## 4. 安全与兼容性边界

- session-derived text、工具输出和公开 assistant 文本仍标为不可信；规则层不输出 skill gap、模型 adherence 或纠正意图结论。
- v3 不含内部 reasoning、GT、Gold、私有 dump、凭据、绝对路径、session event location 或 custody 索引。
- 没有新增依赖、SQL dialect、parser、并发、网络服务、自动 Skill 修改或 candidate 生命周期行为。
- 只向 Evolution 的失败 case 写入 agent artifact；Smoke 和 Final 的既有隔离未改。
