# v0.3 设计：DSH session 证据与 LiveSQLBench 接入门槛

## v0.2 到 v0.3：能力边界的变化

v0.2 的评测边界是「Agent 根据任务交付一条候选 SQL；evaluator 在隔离数据库中将其与
gold SQL 的结果比较」。它只能证明最终答案是否正确，主要证据是 runner 的输出。

v0.3 保留相同的客观判分方式，但把 DSH 的实际解题过程纳入受控的评测边界：

| 维度 | v0.2 | v0.3 |
| --- | --- | --- |
| Agent 能力 | 根据任务和 schema 生成最终 SQL | 可查看 schema，并通过工具执行多次只读 SQL 查询 |
| 数据库访问 | 无交互式查询能力 | 仅限临时 fixture 的无凭据 localhost 只读 capability |
| 运行证据 | 最终 SQL / stdout | 脱敏 session log、结构化 trajectory、最终 SQL 与实际 token 用量 |
| 判分数据库 | 隔离 evaluator fixture | 与探索阶段完全独立的新 evaluator fixture |

这不等于把数据库管理权限交给 Agent。DSH 没有 PostgreSQL 凭据、Docker 权限或写入接口；它只能
调用 task workspace 中生成的 `sql-readonly.ps1`，由该脚本请求本机服务执行已校验的只读查询。

## 已实现的 DSH 评测路径

每个真实 DSH case 使用以下顺序：

```text
冻结 manifest / DSH version / profile / session-log root
  → 生成 run-scoped、无密钥的 manifest model settings 覆盖
  → 创建 disposable PostgreSQL exploration fixture
  → 启动仅允许 task inputs 的 DSH workspace
  → 将只读查询交给无凭据 localhost capability
  → 保存已脱敏的 session.jsonl
  → 销毁 exploration fixture
  → 创建新的 evaluator fixture，独立执行 gold 和 candidate SQL
```

探索 fixture 与 evaluator fixture 分开，Agent 的工具调用无法改变最终评分数据库。DSH 不再以
experiment workspace 为 current directory，因此看不到 expected query、seed、fake result 或 resolved
manifest。

从业务角度，探索 fixture 是让 Agent 为解题而查询的「临时业务数据副本」；evaluator fixture 是
「正式判卷用的全新副本」。两者都由同一份 schema 和 seed 创建，且都不是生产数据库。即使未来工具
或权限边界出现缺口，探索阶段的意外写入、事务状态或数据污染也不能改变最终分数；正式评分只依赖
全新、确定的数据副本。

## Session-log contract

当前只接受 DSH `0.1.1-rc.2` 观测到的 JSONL session protocol（header `version: 0`）。原始日志采用
追加式 zstd frame；runner 使用 DSH 自带 Node runtime 解压，并保存为
`raw/dsh/<case>.session.jsonl` 的已脱敏 JSONL。

解析器会从 `assistant/message`、`tool/call`、`tool/result` 和 `turn/end` 构建 trajectory，累计 DSH
实际报告的 input/output token。cost 未被 DSH 事件提供时保持 `null`，绝不估算。

一个 case 是本 harness 中的一个评测单位，通常对应 benchmark 的一道题。DSH 为每个 case 串行运行
一次；运行前后分别快照 session-log root，并要求恰有一份 `session.jsonl.zstd` 新增或变化。50 个
benchmark 题目在正常情况下会产生 50 份 DSH session log。零份或多份变化均为 `runner_error`，避免
把其他会话错误归属到当前题目。

DSH 的压缩原始文件继续由 DSH 保存在配置的 session-log root（默认
`~/.dsh/sessions`）。harness 将解压且脱敏后的每题证据保存为
`runs/<run-id>/raw/dsh/<case-id>.session.jsonl`，将全部 case 的规范化事件、候选 SQL 与 usage 汇总为
`runs/<run-id>/trajectory.json`。因此每条 SQL、工具调用、用量和错误状态都带有 `case_id`，可以追溯到
具体题目。

DSH 的用户级 `agent-default-model` 设置优先于 profile composition。为了使 manifest 的模型不是仅记录在
environment fingerprint 中，runner 会读取其中经检查的 `llm-*` provider route 配置、在短生命周期 settings
文件中保留这些路由并写入 manifest 的 `agent-default-model`，再通过最后一个 `--patch` 指向该文件。
credential provider 仍指向正常 DSH credential store，明文 credential 字段会使 run 在启动前暂停。每个 case
保存 provider/model invocation 与无密钥 selection evidence，因此用户的交互式默认模型不会静默改变评测模型，
OpenAI 等已配置 route 也不会被覆盖删除。

未知且非关键事件会保留在 raw log 中并记录事件类型；缺失 session header、最终 assistant message、
completed turn，或已识别关键事件的字段不符合协议时，run 以 `runner_error` 暂停，不归因为 Skill。

## 错误归因的当前范围

v0.3 已实现保守的一级归因，并利用 session log 为归因保留证据：

- `runner_error`：例如 DSH 启动/超时问题、未找到唯一 session log、日志不符合协议，或没有可提取的
  最终 SQL；
- `evaluator_invalid`：例如 gold SQL 或 evaluator fixture 本身无法产生有效结果；
- `no_sql_generated`、`unsafe_sql`、`sql_execution_error`、`wrong_result`：候选 SQL 未通过客观评测；
- `pass`：候选 SQL 与 gold SQL 的结果等价。

只要存在 `runner_error` 或 `evaluator_invalid`，run 归为 eval/data/runner 证据问题并暂停，不能归咎于
Skill。其余未通过的候选 SQL 暂归为当前 Skill/Agent 能力需要改进；全部通过则完成。

这不是自动化根因诊断。系统尚不会自动判断错误源于 join 条件、字段理解、工具调用策略还是模型推理；
`trajectory.json` 与每题 raw log 是后续构建该分析能力的输入，而不是已经完成的诊断结论。

## LiveSQLBench 接入门槛

优先范围是 Base-Lite 的 `category: Query`（SELECT-only）任务。每个任务还需要：

- PostgreSQL dump；
- 非空的 `sol_sql`；
- 所需的 external knowledge / HKB；
- 需要官方可比成绩时的 test cases 与 Soft EX evaluator。

公开的 `livesqlbench_data.jsonl` 将 `sol_sql`、`external_knowledge` 和 `test_cases` 置为空，不能用
模型生成的 SQL 替代。适配器在缺少这些 GT artifacts 时必须 fail closed；取得官方 GT 和 dump 后，先
用一个 SELECT case 走完整 DSH session / 独立 evaluator，再扩大到小批量。
