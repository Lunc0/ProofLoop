# 实现记录：LiveSQLBench 分层滚动评测器

> **阶段：**07 · **版本：**v0.7 · **状态：**已完成
>
> **依据：**[规格](../specs/07-v0.7-tiered-rolling-evaluator.md) · [实施计划](../plans/07-v0.7-tiered-rolling-evaluator.md)

## 1. 实际交付

Stage 07 新增两个受信任且显式注册的 adapter：

- `livesqlbench-base-lite-smoke-rotation-v1`
- `livesqlbench-base-lite-evolution-v1`

既有固定五题 `livesqlbench-base-lite` 保持原 ID、固定选题和运行入口；Final
`livesqlbench-base-lite-query-final-v1` 继续使用独立 Held-out custody 且只输出 aggregate result。

### 通用被测对象边界

`RunSubject` 是 benchmark/runner 唯一接受的被测对象：包含不透明 ID、内容 SHA-256、只读字节和安全文件名。
DSH 工作区只取得 `subject/SKILL.md` 及已声明的公开 task context；它被明确作为文本处理，不能执行、import 或加载其引用代码。

candidate store 没有进入 benchmark 或 runner 的导入图。已有 `--candidate` CLI 入口仍保留，但仅由 CLI/workflow
边界把已验证 candidate 转换为 `RunSubject`。run evidence 绑定 `subject_id` 与 `content_sha256`，不保存 candidate
谱系解释。

### 轮换 custody 和题单

`SKILL_EVOLVE_ROTATION_ROOT` 指向预先存在、仓库外的 evaluator custody。解析时拒绝 symlink，以及与 repository、
candidate store 或 `SKILL_EVOLVE_HELDOUT_ROOT` 的路径重叠；这仍是代码边界，实际隔离必须由 ACL、账号或挂载保证。

初始化命令只在 rotation custody 创建一次 private reserve：Simple、Moderate、Challenging 各 5 题。新 manifest
会校验既有 Final manifest、reserve、公开数据 digest、GT、schema/context 和 dump，随后以不可覆盖的原子文件写入
`manifests/`。调用者不能指定 case、seed 或题池。

- Smoke 每份 5 题，按 `2/2/1`、`2/1/2`、`1/2/2` 顺序循环；第 4 份回到首个配额。
- Evolution 每份 15 题，三个 tier 各 5 题。
- 两层从同一排除了 Final 与 reserve 的开发题池独立选择，因而允许跨层 case 重叠；v0.7 没有同层复用窗口或新 manifest
  预算。

CLI 新增：

```powershell
uv run skill-evolve benchmark initialize-rotation <data-root>
uv run skill-evolve benchmark create-rotation-manifest <data-root> --kind smoke
uv run skill-evolve benchmark run livesqlbench-base-lite-smoke-rotation-v1 <data-root> <dsh-manifest> --manifest <id> --candidate <id>
```

两个滚动 adapter 的 `validate`、`fixture-check`、`run` 都通过 `--manifest` 绑定既有 custody manifest；固定 adapter 和
Final 明确拒绝该参数。

### 运行、gate 与可比性

滚动运行沿用普通 `runs/` 目录中的脱敏 DSH session-log/evidence；本阶段没有增加新的逐题 projection schema。
输出的中性状态仅为 `passed`、`task_failure`、`runner_invalid`、`evaluator_invalid`，不包含“修改 Skill”等行动指令。

Smoke 仅在恰好 5/5 通过时，在 rotation custody 写入按 subject binding 校验的 gate receipt。Evolution 在启动前必须找到该
receipt；任务失败、runner 无效或 evaluator 无效不会写成功 gate。Evolution result 额外包含 tier 的 case/evaluated/passed
计数、pass rate、macro-average、成本（未知则保持缺失）与不含 subject 的 comparison key。两个 Evolution result 的 key
不同即为 `incomparable`，只表示不应公平比较，不产生 promotion 或 rollback。

## 2. 兼容性与安全边界

- Final 不调用 rolling selection 或 gate 路径；其 case identity、逐题 result、GT、Gold SQL、完整 session、manifest 和
  credentials 不进入 Git、stdout、普通 run root、candidate store 或 `RunSubject`。
- 正常 Smoke/Evolution run 只写现有的脱敏 evidence；CLI 的 reserve/manifest 成功 receipt 只有 adapter、manifest ID/hash
  和 tier 计数，不含 case ID、Final 或 reserve identity。
- 任何缺材料、digest 漂移、文件链接、manifest 篡改、Final/reserve 重叠或数量不足，都会在 fixture、DSH 或模型启动前
  fail closed。
- 没有接入 coding agent、自动 Skill 改写、candidate promotion/rollback、并发、第二 SQL dialect 或真实服务调用。

## 3. 验证结果

全部验证使用临时合成 data/custody、fake fixture 和 stub runner：

- `uv run ruff check .`：通过。
- `uv run mypy src`：通过（46 个 source 文件）。
- `uv run pytest`：83 passed，1 skipped（Windows 环境不支持 symlink 创建）。
- 额外确认 `src/skill_evolve/benchmark` 和 `src/skill_evolve/runner` 不直接导入 candidate 模块；`git diff --check` 通过。

本阶段没有初始化真实 rotation manifest、没有读取或改写真实 reserve/Final custody、没有运行 Docker、真实 DSH、真实模型或
baseline，也没有推送远端。
