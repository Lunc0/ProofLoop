# 实现记录：Codex Coding Agent 原子 Skill 编辑路径

> **阶段：**29 · **版本：**v0.27 · **状态：**已完成

## 实际实现

v0.27 在现有 DeepSeek advice → EditPlan → materialize 与 `evolution cycle` 之外新增两个显式命令：

```powershell
uv run skill-evolve optimizer agent-edit <run-id>
uv run skill-evolve optimizer agent-materialize <run-id> --candidate-name-prefix <prefix>
```

`agent-edit` 从既有 Evolution v3 投影中生成匿名 evidence ref，将 parent `SKILL.md`、本地重建的
SkillMap、evidence 与闭集 manifest 复制到每次独立的 workspace。Codex CLI launcher 使用 argv、
`shell=False`、ephemeral/ignore-user-config/ignore-rules 和 strict config，通过 inline config overrides
选择 `skill-optimizer` permission profile；workspace 默认只读，仅 `output` 可写，command network、Web
Search、approval、apps、multi-agent、memories 与 hooks 关闭。CLI 低于 0.138.0 或配置无法解析时不降级。

控制进程只接收 `output/SKILL.md` 与 `output/atomic-edits.json`。输入集合在调用前后做 SHA-256 校验；
输出目录同时绑定 realpath 与目录对象身份，输出文件必须是有大小上限、单链接的普通文件。超时会终止
Codex 进程组/进程树。stdout、stderr 和 agent 的自然语言成功声明不参与成功判定。

## 原子编辑与确定性重放

agent declaration 只允许 1–3 个 `replace_block`。系统不信任 agent 提供的 ID、offset 或 hash，而是从
同一 parent 的 SkillMap v3 生成 `edit-NNN`、半开 UTF-8 字节范围、before/replacement hash 和 source
binding。目标仅允许 `evolvable`/`experimental`，并拒绝未知 evidence、重复/父子覆盖、范围重叠、空变更、
结构无效、敏感文本与换行约定变化。

每个 edit 都先单独应用到原 parent 并生成可精确回放的 unified patch；全部 edits 再按原字节位置倒序
应用。full replay 必须与 agent 的完整 `SKILL.md` 逐字节相同，因此未声明变化不能进入 bound artifacts。
编辑 artifacts 先写入 run 内 staging 目录，再一次性发布到 `optimizer/coding-agent/`；同一 run 不允许覆盖。

## Candidate 合同与兼容性

`agent-materialize` 重新验证 edit receipt、bound plan、invocation receipt、parent candidate、SkillMap、patch 与
full Skill hash，然后创建一个 `<prefix>-full` 和 N 个 `<prefix>-edit-NNN` immutable draft siblings。
新增 `CandidateOrigin.CODING_AGENT` 与独立 `CodingAgentProvenance`，绑定 parent/SkillMap/evidence/atomic-edits/
patch hash、role、edit ID、policy、Codex CLI version 和可选 model。child SkillMap 仍由 candidate store 从最终
`SKILL.md` 重建，绝不复用 parent map。

materialization receipt 采用独占创建；重复物化拒绝覆盖。创建中途失败时 receipt 明确列出已创建的 candidate
IDs，不把部分成功伪装成原子成功。本阶段不自动 benchmark、select、promote、retire 或选作下一代 parent。

旧 DeepSeek optimizer 的命令、contracts、artifact namespace、默认配置和 Evolution cycle 控制流均未替换；
新路径使用独立 package、result keys、receipts 和 provenance。
