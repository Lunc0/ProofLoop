## 实际实现

新增显式入口：

```powershell
uv run skill-evolve evolution cycle $DataRoot $DshManifest `
  --candidate <candidate-id> `
  --max-generations <1..100> `
  --child-name-prefix evolution
```

`EvolutionCycleRequest` 在启动前验证 candidate ID、child prefix 和 1 至 100 的代数范围，并预先检查所有将生成的
`<prefix>-001` 形式 candidate 名称没有冲突。没有默认无限循环、后台任务或重试；任何 terminal failure 都结束当前 cycle。

`run_evolution_cycle` 直接调用现有的 candidate、rotation、runner、optimizer 和 materialization Python service，不解析
CLI stdout 或启动嵌套 shell。rotation reserve 不存在时初始化，存在时重新读取并验证；每一代只使用新建的 custody manifest。
safe cycle receipt 写入 `.local/skill-evolve/cycles/`，stdout 仅输出同一份摘要中的 cycle/candidate/run ID、manifest hash、状态、
停止原因和 child ID。

无父代 baseline 仅在本次 cycle 的第 1 代传入 `allow_ungated_evolution=True`，因而可直接运行 Evolution。该参数默认 false，
普通 `benchmark run` 以及所有未显式传入该参数的调用仍必须有有效 Smoke gate。成功 child 与任一有父代的起始 candidate 都先运行
Smoke。cycle 以**当前 Smoke outcome**的完整五题、无基础设施无效和至少 3 个通过决定是否继续，不能借同一 candidate 的历史 gate
绕过本轮 Smoke 失败。

cycle 先拒绝 DSH manifest 的 `environment.optimizer.enabled: true`。Evolution runner 使用 manifest 中的 disabled optimizer 配置，
不会向 provider 发起隐式 advice 请求；随后编排器以同一配置仅将 `enabled` 改为 true，按顺序调用 advice 和 plan。advice 未达
`proposed` 时不会调用 plan；plan 未达 `proposed` 时不会 materialize；materialize 不调用模型。成功 child 始终复用既有
materialization 的 immutable lineage、hash binding 和 `draft` 状态，未自动 select、推广、回退或覆盖任何 candidate。

## 兼容性与安全边界

- 既有 `benchmark`、`optimizer advise`、`optimizer plan` 和 `optimizer materialize` 命令未改变。
- Final/held-out、GT/Gold、完整 Skill、EditPlan、patch、session、custody 路径和凭据不进入 cycle receipt 或 stdout。
- Smoke gate 的普通 fail-closed 行为未放宽；例外只在 trusted cycle service 完成 lineage 与 generation 双重判定后传入。
- 未新增依赖、SQL dialect、并发、云端控制面或定时任务。
