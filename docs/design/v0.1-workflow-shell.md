# 技术设计：DSH SQL Skill Evaluation Workflow Shell v0.1

**状态：**v0.1 已实现；真实 DSH adapter、并发调度和自动 Skill 修改仍待后续版本。
**目标：**先固化一次可重复、可审计的 SQL Skill 评估闭环；不在 v0.1 解决大规模调度、自主优化或发布治理。

## 1. 目标与边界

### 1.1 要实现的 workflow

```text
冻结 Environment
  (model + DSH + tools + DB fixture + evaluator)
                │
                ▼
执行任务，保存 trajectory / SQL / 执行结果 / 成本
                │
                ▼
客观 SQL Eval：执行正确性、结果等价性、回归切片
                │
                ▼
Failure attribution
     ┌──────────┴──────────┐
     ▼                     ▼
  Skill                 Eval/data
     │                     │
     ▼                     ▼
生成修复建议与          暂停本轮实验，输出
回归用例草案            evaluator / fixture 版本化清单
     │
     ▼
人工修改 Skill 后再次运行 `run`
```

系统只自动产出**证据、判定和下一步动作**。人或上层 agent 负责改 Skill；之后使用同一 manifest 重新运行。

### 1.2 明确不在 v0.1 的范围

- 并发、队列、定时调度、资源配额和多机执行。
- 自动根据报告改写 Skill、自动改 benchmark、自动发布 champion 或 rollback。
- 真实 DSH 的内置 SDK / event API 集成；先定义稳定的 runner 边界并用 fake runner 验证 workflow。
- PostgreSQL 以外的数据库方言与生产数据库连接。
- LLM-as-a-judge。SQL 正确性只由确定性 evaluator 判断。

## 2. 设计原则

1. **环境变化即新实验空间。**修改 model、DSH profile、plugins、tools、database fixture 或 evaluator 后，environment fingerprint 必须变化；新旧结果不可直接做 Skill 优劣结论。
2. **原始证据优先。**原始 runner 输出和解析后的结构化信息同时保存；报告只是派生物。
3. **评估独立于 Agent 自述。**Agent 宣称“SQL 执行成功”不算证据。候选 SQL 和真值 SQL 都由 evaluator 在同一冻结 fixture 上独立执行。
4. **宁可暂停，不能误归因。**fixture、expected query、evaluator、runner evidence 任一不可信时归为 `eval_data` 并暂停；不得归咎于 Skill。
5. **可重跑而非隐式续跑。**每个 run 保存 resolved manifest；`rerun` 以它为输入新建 run，而不使用上次运行的临时状态。

## 3. 总体架构

```text
                 experiment.yaml + fixture + candidate
                              │
                              ▼
┌────────────────────────────────────────────────────────────────┐
│ CLI: validate | run | show | rerun                               │
├───────────────┬────────────────┬───────────────┬────────────────┤
│ Manifest      │ Environment    │ Runner         │ Run store      │
│ resolver      │ fingerprint    │ interface      │ (filesystem)   │
└───────────────┴────────────────┴───────┬───────┴────────────────┘
                                          │
                         ┌────────────────┴─────────────────┐
                         ▼                                  ▼
                  FakeRunner v0.1                 DshRunner later
                  deterministic JSON              external dsh process
                         │                                  │
                         └────────────────┬─────────────────┘
                                          ▼
                     Trace normaliser / evidence extractor
                                          │
                                          ▼
               PostgreSQL objective evaluator + slice aggregator
                                          │
                                          ▼
                         Attribution + reports + regression draft
```

### 3.1 为什么 v0.1 使用 runner interface

DeepSeek Harness（DSH）以 profile、bundle 和 patch 组合运行环境，并把会话记录为 append-only event log；这些非常适合做环境快照和 trajectory 证据。DSH 当前仍处于 developer preview，兼容性会变化。因此 v0.1 不导入其内部 package API，而是约定一个小的、可测试的 `Runner` 输入输出协议。未来 `DshRunner` 只需负责将固定版本 DSH 的 session log 转换成该协议，其余 evaluator 与归因逻辑不变。

`skill-up` 的 YAML suite、显式 artifacts、统一的 session result 和 rule-based judge 设计可作为格式参考；本项目不复制其源码，也不要求安装它。

### 3.2 技术栈

- **Python 3.11+：**主项目语言；以 `pyproject.toml` 管理依赖，`uv` 负责创建与锁定本地虚拟环境。
- **Typer：**本地 CLI 的命令、参数和退出码。
- **Pydantic + PyYAML：**manifest 的 schema 验证、路径解析和可序列化的 resolved manifest。
- **psycopg：**PostgreSQL bootstrap、只读执行和结果读取；PostgreSQL 通过本机 Docker 临时容器提供。
- **pytest：**单元与端到端测试；`ruff` 负责格式与静态 lint，`mypy` 负责类型检查。

选择 Python 的原因是 v0.1 的主要复杂度在 PostgreSQL fixture、确定性 SQL Eval、数据规范化和测试，而不是 DSH 的内部 plugin API。Python 仅以外部进程调用 DSH，因此不受 DSH 实现语言限制。若未来确实需要订阅 DSH 内部 event，可单独提供一个很薄的 TypeScript bridge，将事件写为本设计的 `RunnerOutput` JSON；Python 主项目不需要改写。

## 4. 实验 manifest 与环境快照

### 4.1 `experiment.yaml`

```yaml
schema_version: v1
experiment: sales-sql-skill
candidate:
  ref: skills/sql-analyst              # 可选，作为被评估 Skill 的身份
  digest_file: skills/sql-analyst/SKILL.md

environment:
  model:
    provider: deepseek
    name: deepseek-v4
    params:
      temperature: 0
  dsh:
    version: 0.1.0-rc.6
    profile: sql-eval
    profile_patch: profiles/sql-eval.patch.yml   # 可选；会被 hash
    runner: fake                                  # v0.1 内置 runner
    fake_output: fake-results/results.json        # fake runner 的冻结 trajectory
  tools:
    - id: sql-readonly
      version: 1.0.0
      manifest: tools/sql-readonly.json
  database:
    kind: postgresql
    image: postgres:16.6
    image_digest: sha256:<pinned-image-digest>
    schema: fixtures/schema.sql
    seed: fixtures/seed.sql
  evaluator:
    version: sql-result-v1
    result_order: ignore
    numeric_tolerance: 0
    max_rows: 1000
    timeout_ms: 5000

cases:
  - id: customer-count
    slice: fast
    prompt: 每个国家有多少客户？
    expected_query: |
      SELECT country, COUNT(*) AS customer_count
      FROM customers
      GROUP BY country
  - id: top-product
    slice: held_out
    prompt: 销售额最高的商品是什么？
    expected_query: |
      SELECT product_name, SUM(amount) AS revenue
      FROM order_items
      GROUP BY product_name
      ORDER BY revenue DESC
      LIMIT 1
```

### 4.2 环境指纹

`environment_fingerprint` 采用 SHA-256，输入包括：

- canonical YAML（字段排序、路径解析为相对 manifest 的规范路径；不含 secrets）；
- `candidate.digest_file`、PostgreSQL image digest、schema、seed、profile patch、fake runner output、tool manifests 的内容 digest（不包含这些文件在 manifest 中的路径拼写）；
- DSH / model / evaluator 的版本与非敏感参数。

输出单独存放为 `environment.json`，同时列出每项 digest。manifest 中不允许 API key、password、token；解析阶段发现敏感键时直接失败。路径在 workspace 外时直接失败，防止意外读入用户环境文件。

**可比性规则：**只有 environment fingerprint 相同的 run 才可被同一 regression slice 直接比较。指纹不同时，报告只显示“环境改变后的 baseline 对比建议”，不显示“Skill 退化/提升”。

## 5. Runner contract

### 5.1 输入

```python
@dataclass(frozen=True)
class RunInput:
    run_id: str
    workspace: Path
    environment_fingerprint: str
    candidate_ref: str | None
    cases: tuple[ResolvedCase, ...]


class Runner(Protocol):
    def run(self, input: RunInput) -> RunnerOutput: ...
```

### 5.2 输出

```python
@dataclass(frozen=True)
class RunnerCaseOutput:
    case_id: str
    status: Literal["completed", "runner_error"]
    final_message: str | None
    candidate_sql: str | None
    trajectory: tuple[TrajectoryEvent, ...]
    agent_execution: AgentExecution | None
    usage: Usage


@dataclass(frozen=True)
class RunnerOutput:
    schema_version: Literal["v1"]
    cases: tuple[RunnerCaseOutput, ...]
```

该 contract 有三个约束：

1. `trajectory` 必须按发生顺序原样保留。v0.1 不要求特定 event taxonomy。
2. cost / token 缺失必须保留为缺失，报告展示为 `unknown`，不得估算或写 0。
3. runner 成功但没有 candidate SQL 是 Skill 的 `no_sql_generated`；runner 无法提供完整结构化输出或 case 级证据，则是 `eval_data`。

### 5.3 `FakeRunner`

v0.1 内置 `FakeRunner`。它从案例 fixture（例如 `fake-results/<case-id>.json`）加载 `RunnerOutput`，以覆盖以下 workflow 分支：

- 正确 SQL 与可用 cost；
- 错误 SQL；
- 无 SQL；
- runner error / malformed trace；
- 缺失 cost。

它不是 mock 掉 evaluator，而是只替换 Agent/DSH 调用；SQL evaluator、证据保存和 attribution 都使用真实代码路径。

### 5.4 后续 `DshRunner`（非 v0.1 实现）

Python `DshRunner` 接受已固定的 DSH binary、version、profile、patch 和 argv；通过 `subprocess.run(..., shell=False)` 创建子进程，复制 stdout/stderr 与 session log，并将 DSH 的消息、tool call/result、usage 转为 `RunnerOutput`。若 log schema 不匹配，返回 `runner_error`；该错误必须走 `eval_data`，绝不能视为 Skill 问题。

## 6. PostgreSQL objective evaluator

### 6.1 数据库隔离与安全

每个 run 使用一个由固定 PostgreSQL image 启动的临时容器。容器先执行固定的 `schema.sql` 与 `seed.sql`，再为每个 case 创建独立数据库或从只读模板库克隆；候选 SQL、expected SQL 都只能通过专用 `eval_reader` 角色连接。该角色无 DDL / DML / role-management 权限，并在会话中设置 `default_transaction_read_only = on`、`statement_timeout`、`lock_timeout` 和 row cap。候选 SQL 没有任何到生产数据库或共享开发数据库的连接信息。

仅允许一条根类型为 `SELECT`、`WITH … SELECT` 或 `EXPLAIN SELECT` 的语句。拒绝：多语句、`INSERT`、`UPDATE`、`DELETE`、`MERGE`、`CREATE`、`DROP`、`ALTER`、`COPY`、`SET`、事务语句和未知语句。语法检查不是唯一防线；PostgreSQL role 权限和只读事务也必须确保写操作失败。

### 6.2 判定

每个 case 都执行两次：

1. 执行 `expected_query`，得到 expected result；
2. 执行 candidate SQL，得到 actual result。

结果规范化规则：

- 保留列数量、列名和每行值；
- `result_order: ignore` 时按稳定 JSON representation 排序行；
- null、布尔、数值和 ISO 时间用明确的类型标记表示；
- 数值仅在 `numeric_tolerance` 非零时按绝对误差比较；
- 默认不接受列名不同、额外行或缺失行。

对应 verdict：

| 条件 | `verdict` |
|---|---|
| expected query 无效、PostgreSQL fixture 启动/seed 失败、evaluator 内部错误 | `evaluator_invalid` |
| candidate 缺失 SQL | `no_sql_generated` |
| candidate SQL 不安全 | `unsafe_sql` |
| candidate SQL 不能执行 / 超时 | `sql_execution_error` |
| candidate 与 expected result 不等价 | `wrong_result` |
| 两者等价 | `pass` |

### 6.3 回归切片

每个 case 只属于 `fast`、`dev` 或 `held_out` 一个 slice。`run --suite fast` 仅执行 fast；不指定 `--suite` 时执行全部。v0.1 的切片用于报告和人工运行顺序，**不实现自动 gate 或 promotion**。

### 6.4 `case`、`held_out` 与隔离的含义

- **case** 是一条可重复测试：包含一个自然语言 prompt、固定的数据库 fixture、expected query 和预期的评估规则。例如“每个国家有多少客户？”就是一个 case。
- **slice** 是 cases 的分组，决定何时运行：`fast` 是每次改 Skill 都跑的少量冒烟题，`dev` 是开发期回归集，`held_out` 是不用于日常调优的保留集。
- **held_out** 的用途是验证 Skill 没有只记住 `fast` / `dev` 的题目或针对这些题作提示词特化。它不是不同的 evaluator，而是一组不应频繁暴露给 Skill 修改者的普通 cases。
- **cases 隔离**可能有两种强度：
  1. *目录隔离*：`cases/fast/`、`cases/dev/`、`cases/held_out/` 分开存放。这方便管理，但任何能读取仓库的人或 agent 仍可看见 held_out，只有组织约定意义。
  2. *访问隔离*：held_out 位于受保护的私有仓库/制品，只有受保护 CI 和评估维护者读取；常规开发者与修改 Skill 的 agent 看不到它。这才可以防止 benchmark 泄漏，但需要额外的凭据与 CI 配置。

v0.1 只实现 slice 标签和目录隔离；访问隔离列为后续增强，不把它误称为安全的 held-out 保护，也不依赖 CI 实现该 workflow。

## 7. Failure attribution 与下一步动作

v0.1 只有两个根归因，避免不可靠的细粒度归因：

| 前置条件 / verdict | attribution | run status | 自动产物 |
|---|---|---|---|
| manifest / fingerprint / fixture / expected query / evaluator 错误 | `eval_data` | `experiment_paused` | `repair-checklist.md` |
| runner error、缺少结构化 evidence、DSH log schema 不匹配 | `eval_data` | `experiment_paused` | `repair-checklist.md` |
| `no_sql_generated`、`unsafe_sql`、`sql_execution_error`、`wrong_result` | `skill` | `needs_skill_change` | `regression-case.draft.yaml` + `skill-change-suggestion.md` |
| 全部通过 | `none` | `completed` | `next-run.md` |

任何 case 是 `eval_data` 时，整体 run 都是 `experiment_paused`；即便其他 case 有 Skill failure，也不生成“可直接优化 Skill”的结论。这样可以避免错误的 evaluator 推动 Skill 向错误目标优化。

### 7.1 Regression draft

对 Skill failure，系统从失败 case 生成 draft：保留原 prompt、冻结后的 fixture / evaluator 指纹、expected query、实际 SQL、verdict、原 run ID 和最小复现说明。它默认写进该 run 的 artifact 目录而非直接修改 suite，人工审阅后才把它加入 `cases/`。

`held_out` 的 expected query 不出现在默认人类可读报告中，避免它被用来针对性调优；只有拥有该 suite 文件访问权的操作者能从对应 artifact 中读取它。

## 8. Artifact layout 与状态机

```text
runs/<run-id>/
  manifest.resolved.yaml             # 规范化后的非敏感输入
  environment.json                   # fingerprint 与 component digests
  raw/
    runner-output.json               # 不修改的 RunnerOutput
    runner.stderr.log                # 若适用
  work/<case-id>/                     # 临时 PostgreSQL connection metadata；报告完成后可配置清理
  evaluation.json                    # 每个 case 的执行与比较证据
  attribution.json                   # root cause、证据引用、next action
  report.md                          # 人类摘要
  result.json                        # 机器可读总结果
  regression-case.draft.yaml         # 仅 Skill failure
  repair-checklist.md                # 仅 Eval/data failure
```

状态转换：

```text
created → validated → snapshotted → running → evaluating → attributing
                                                            │
                                 ┌──────────────────────────┼─────────────────────────┐
                                 ▼                          ▼                         ▼
                           completed              needs_skill_change        experiment_paused
```

`result.json` 写入前的阶段文件可以追加；进入终态后所有产物视为只读。`rerun <run-id>` 读取 `manifest.resolved.yaml` 并生成新 run ID，旧 run 永不覆盖。

## 9. CLI 行为

**CLI（Command-Line Interface，命令行界面）**是本项目的本地操作入口：开发者在终端调用命令来验证 manifest、运行评估、查看报告或重跑。它不是图形界面，也不意味着自动化调度。

```text
skill-evolve validate <manifest>                 解析、校验路径与 schema，打印 fingerprint
skill-evolve run <manifest> [--suite <slice>]    创建 run，执行完整 workflow，打印 run-id 与终态
skill-evolve show <run-id>                       读取 result、attribution、报告路径
skill-evolve rerun <run-id> [--suite <slice>]    用已保存的 resolved manifest 重新开始新 run
```

退出码：`0` = completed / needs_skill_change（workflow 正常完成）；`2` = experiment_paused（需修 evaluator/data）；`64` = manifest / CLI 参数无效；`70` = 未捕获内部错误。`needs_skill_change` 不是进程异常，避免自动化调用方将“发现真实 Skill bug”误当作 harness 故障。

## 10. 本地验证（CI 不属于 v0.1 交付）

v0.1 只提供本地 CLI。使用者通过下面命令验证工具与自己的 Skill workflow：

```text
uv sync --all-groups
uv run ruff check .
uv run mypy src
uv run pytest
uv run skill-evolve validate examples/sql-agent/experiment.yaml
uv run skill-evolve run examples/sql-agent/experiment.yaml --suite fast
```

**CI（Continuous Integration，持续集成）**是项目维护者在提交本工具代码时可选择添加的自动测试，例如 GitHub Actions。它既不是用户使用本工具评估 Skill 的功能，也不是 v0.1 的实现任务；将来若需要，只是自动调用上述同一套本地 CLI 命令。

## 11. 验收场景

| 场景 | 预期终态 | 必须存在的证据 |
|---|---|---|
| candidate SQL 与 expected result 等价 | `completed` | raw trajectory、evaluation pass、slice summary |
| candidate SQL 语法错误 | `needs_skill_change` | PostgreSQL error、actual SQL、regression draft |
| candidate 执行写操作 | `needs_skill_change` | policy rejection、regression draft |
| expected query 语法错误 | `experiment_paused` | expected-query error、repair checklist、无 regression draft |
| PostgreSQL image / schema / seed 不匹配或启动失败 | `experiment_paused` | component digest or bootstrap error、repair checklist |
| runner 输出无法解析 | `experiment_paused` | raw output、parse error、repair checklist |
| cost 不存在 | 仍可完成 | `cost_usd: unknown`，无估算值 |

## 12. 后续扩展，不改变 v0.1 核心

1. **真实 DSH adapter：**固定 DSH release + profile bundle / patch，解析 session log 到现有 Runner contract。
2. **其他数据库 adapter：**以 disposable container 或专用只读数据库执行，fingerprint 加入 engine image / schema / seed digest。
3. **执行编排：**为 `Runner` 增加队列、并发和预算控制，不更改 evaluator 和 run artifact schema。
4. **更细归因：**在可靠证据充分后增加 `harness_tool` 子类，但保留 v0.1 的 Skill / Eval-data 根结论。
5. **演进与治理：**上层 agent 消费 `skill-change-suggestion.md`，经人工确认写 Skill；再增加 gate、champion 和 rollback。

## 13. 待确认的设计决策

1. v0.1 已确定 PostgreSQL 为唯一 fixture dialect；本机已安装 Docker CLI。首版以本地可销毁 PostgreSQL 容器运行 fixture；运行完整 PostgreSQL 验证前须启动 Docker daemon。
2. v0.1 默认采用目录隔离；未来是否需要对 held_out 实施受保护 CI 的访问隔离？
3. 所谓“成本”是否仅记录 DSH / provider 已提供的精确值？本设计默认是；不做模型价格表估算。
