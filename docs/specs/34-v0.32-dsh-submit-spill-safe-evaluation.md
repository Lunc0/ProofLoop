# 规格：DSH Submit Spill 安全解析与语义判分

> **阶段：**34 · **版本：**v0.32 · **状态：**已完成
>
> **关联阶段：**[阶段 33：DSH 原生 SQL 工具与 SQL Harness Policy](33-v0.31-dsh-native-sql-harness-policy.md) ·
> **实施计划：**[阶段 34 v0.32 计划](../plans/34-v0.32-dsh-submit-spill-safe-evaluation.md) ·
> **实现记录：**[阶段 34 v0.32 Design](../design/34-v0.32-dsh-submit-spill-safe-evaluation.md)。

## 1. 目标

修复 DSH 将大体积 `sql_submit` 结果外置并在 JSON 后追加 spill 提示时，session normalizer 抛出
`sql_submit result is not JSON`、导致本可判分的最终 SQL 被提前标记为 `runner_error` 的问题。

本阶段保持“最终 SQL 必须与受控 `sql_submit` 调用绑定”的审计边界，同时把 DSH 的已知展示包装与工具返回的
结构化 JSON 分开解析。只要提交调用成功、最终 SQL 可提取且与提交参数一致，就必须继续进入现有 Soft-EX
evaluator；工具执行成功本身仍不代表答案正确。

## 2. 范围与核心假设

本阶段包含：

- 为 `sql_submit` tool result 增加严格、显式的 DSH spill 包装识别。
- 从被识别的包装中只解析内联 JSON，不读取提示指向的临时文件。
- 保留 `sql_submit` call/result 配对、`isError=false`、成功 payload 和 final/submit SQL 一致性校验。
- 增加覆盖大结果 spill、任意尾随文本、失败 result、缺失 result 和 SQL 不一致的离线回归测试。
- 更新阶段 33 的实现记录，说明修复后的实际兼容边界；不回写或改造已完成阶段的原始规格。

核心假设：

- DSH spill 提示是 transport/display 包装，不是 SQL 结果语义的一部分。
- 当前已观测格式为独立尾行，包含省略字节数、临时文件路径和读取提示；它属于不可信输入，必须按完整格式
  匹配，不能通过简单截断首行或忽略任意尾随内容来接受。
- `sql_submit` 的内联 JSON 即使含大量 `rows`，仍是 runner 判断提交成功所需的权威结构化 payload。
- 最终答案仍由唯一的 `sql` 或 `postgresql` fenced block 提供；evaluator 仍通过执行结果做 Soft-EX，不做 SQL
  文本相等判分。

## 3. 行为合同

### 3.1 可继续判分

同时满足以下条件时，runner 必须产生 `status=completed` 和 `candidate_sql`，并继续进入 evaluator：

1. session 存在正常完成的 turn 和最终 assistant message；
2. 配对的 `sql_submit` tool result 标记 `isError=false`；
3. tool result 文本是一个 JSON object，或是一个 JSON object 后紧跟一个严格识别的 DSH spill 提示；
4. JSON payload 为 `ok=true`、`intent=submit`、`phase=finalize`；
5. 最终消息含且仅含一个 SQL fenced block，并与提交调用参数中的 SQL 规范化一致。

### 3.2 必须受控失败

以下情况继续形成 `runner_error`，不得降级为可判分：

- JSON 后存在无法识别或格式不完整的任意尾随文本；
- spill 提示要求读取的文件不存在、不可读或内容不同——runner 根本不得读取该路径，因此不能依赖它补证；
- tool result 标记错误、JSON payload 不是成功的 finalize submit，或 call/result 无法配对；
- 最终 SQL 缺失、出现多个 SQL block，或与提交 SQL 不一致；
- 任何输入试图借 spill 文本注入命令、URL、额外 JSON 或控制 runner 行为。

### 3.3 证据与输出

- 原始、脱敏后的 session artifact 保持不变，继续保留 DSH 实际产生的 spill 提示供审计。
- runner 不执行、打开、搜索或持久化 spill 提示中的临时路径。
- public evaluation 继续只暴露既有稳定 verdict/detail，不暴露绝对路径、SQL、结果行或解析异常原文。
- 本阶段不把 submit 证据另建为新的公开评分维度；成功解析后沿用阶段 33 的绑定合同。

## 4. 技术栈、项目结构与代码风格

继续使用 Python 3.11+、标准库 `json`、严格类型与现有 Pydantic runner contracts，不新增依赖。

预期文件范围：

- `src/skill_evolve/runner/dsh_session.py`：严格解析 JSON 与可选的已知 spill 尾行。
- `tests/test_dsh_session.py`：session normalization 单元回归。
- `tests/test_dsh_runner.py`：证明可恢复 case 会生成 candidate 并到达 evaluator 前置输出。
- `docs/design/33-v0.31-dsh-native-sql-harness-policy.md`：实现完成后补充兼容说明。
- `docs/design/34-<version>-dsh-submit-spill-safe-evaluation.md`：实现完成后记录实际合同和验证结果。

新增解析 helper 使用 `snake_case`、窄输入输出类型和固定错误文本。不得用宽泛正则删除未知尾部，也不得以
`splitlines()[0]` 代替 JSON 边界解析。

## 5. 测试与验证

默认仅执行离线定向检查：

```powershell
uv run pytest tests/test_dsh_session.py tests/test_dsh_runner.py
uv run ruff check src/skill_evolve/runner/dsh_session.py tests/test_dsh_session.py tests/test_dsh_runner.py
uv run mypy src
git diff --check
```

测试 fixture 使用合成 SQL 和合成 Windows/POSIX 临时路径，不复制 held-out case、真实 SQL、结果行或 session。
本阶段不运行真实 DSH、模型、数据库、Docker 或 benchmark；需要这些验证时必须另行获得授权。

## 6. 验收标准

1. 合成的成功 `sql_submit` JSON 加合法 DSH spill 提示可被 normalizer 接受，并保留最后一次成功提交 SQL。
2. 同一合成 session 的最终 SQL 与提交 SQL 一致时，runner 输出 `completed` 且 evaluator 可以执行 Soft-EX。
3. 纯 JSON 的现有 session 行为不变。
4. 任意尾随文本、第二个 JSON、畸形或伪造 spill 提示仍稳定产生 `runner_error`。
5. parser 不读取 spill 路径；测试通过指向不存在路径证明行为不依赖外部文件。
6. `isError=true`、非 finalize payload、缺失配对、缺失/多个最终 SQL block和 final/submit 不一致仍失败关闭。
7. 错误与公开 artifacts 不泄漏绝对路径、SQL、结果行、GT、凭据或第三方异常原文。
8. 定向 pytest、Ruff、mypy 与 `git diff --check` 通过；不以真实模型或 held-out rerun 作为完成条件。

## 7. 边界

- **始终：**保持只读执行、call/result 配对、成功 payload 校验、final/submit 确定绑定和 Soft-EX 语义判分。
- **先询问：**版本号、真实 DSH/model、Docker、benchmark、修改 DSH spill 生产端、扩大到其他 tool result、commit
  或 push。
- **绝不：**读取 spill 临时文件、接受未知尾随文本、从提示执行命令、把 tool success 当作 evaluator pass、
  输出 held-out SQL/GT/结果行，或绕过最终 SQL 与提交 SQL 的一致性检查。

## 8. 非目标

- 不取消 `sql_submit` 或阶段 33 的最终候选绑定合同。
- 不让 evaluator 从 tool result 直接取得候选 SQL，也不让 Harness 生成或修复模型答案。
- 不改变 Soft-EX、Gold 执行、verdict 聚合或 runner error 计数策略。
- 不重新评测或改写既有 held-out artifacts；修复后的历史日志重解析能力只由离线合成测试覆盖。
- 不引入通用的 DSH spill 文件读取、缓存、清理或生命周期管理。
