# 规格：EditPlan 渲染、机械校验与不可变 Child Skill

> **阶段：**14 · **版本：**v0.12 · **状态：**已完成
>
> **前置阶段：**[阶段 05：本地 Skill 候选版本库](05-v0.5-local-skill-evolution.md) ·
> [阶段 13：结构化 Skill 与行为导向修改计划](13-v0.11-structured-skill-edit-plan.md)
>
> **实施计划：**[阶段 14 v0.12 实施计划](../plans/14-v0.12-edit-plan-render-child-candidate.md) ·
> **实现记录：**[阶段 14 v0.12 实现记录](../design/14-v0.12-edit-plan-render-child-candidate.md)

## 1. 目标

将阶段 13 已验证、带来源绑定的 `skill-edit-plan-v1` 转换为一份可审计的 Markdown
patch，在不改写父版本的前提下，生成候选库中的一个不可变 child Skill。

成功意味着系统可以回答“这份 child 从哪个父 candidate、哪个 run、哪一份 EditPlan 产生，实际改了什么”，并能以
机械校验证明 patch 只作用于允许的目标区域。产物是 **新的 draft Skill 候选版本**，而不是评测结论或自动晋级结果。

建议的显式入口为：

```powershell
uv run skill-evolve optimizer materialize <run-id> --candidate-name <child-name>
```

命令代表用户对该次写入 candidate store 的明确授权；它不启动新的 run、不调用优化模型，也不隐式选择、评测、晋级或
回退 candidate。

## 2. 范围

本阶段应完成：

1. 从 run 内的 `optimizer/edit-plan/` 读取并严格验证 `skill-edit-plan-v1`、`skill-map-v1`、receipt 和来源绑定。
2. 重新读取并校验固化的父 `SKILL.md`、parent candidate 及其 hash；任何 run/plan/parent/map/contract 漂移均 fail closed。
3. 将有限种 `SemanticEdit` 以确定性的、无模型的 renderer 转为具体 Markdown 内容和标准 unified diff。
4. 对新旧 Skill、diff 及 target permission 做机械校验；不满足时不创建 child。
5. 通过既有本地 candidate store 原子创建一个新 draft child，并保存完整 lineage/provenance。
6. 在 run 内保存最小化、不可覆盖的 materialization evidence，并在 `result.json` 和 stdout 仅记录摘要。
7. 取消阶段 13 新计划的 `requires_guarded_approval` 状态分支；保留 `guarded` 作为区块定位风险标记，
   并兼容读取历史 artifact 中的该状态。

## 3. 已采用的前提

1. **EditPlan 是唯一语义输入。** renderer 不再请求 LLM，不从 trajectory、完整 prompt、session、GT 或 Gold 补充规则。
2. **父版本是不可变输入。** 只使用 run materialized subject 与候选库中已验证、hash 一致的 parent；不得就地修改
   `SKILL.md`，也不得从工作区任意路径读取替代内容。
3. **渲染是保守的。** 只有能被精确定义为文本变换的 edit 才能 materialize；未知 block 类型、含糊 target 或无法保持
   既有 Markdown 边界的 operation 一律拒绝，不尝试“尽力修复”。
4. **权限在写入前再次执行。** `locked` 永远不能 materialize；`guarded` 仅表示需要保守定位和机械校验，
   不再要求逐项人工审批；`evolvable` 与 `experimental` 同样可自动进入本阶段。
5. **一次 materialization 只产生一个完整 child。** 该 child 应用本次计划的全部可执行 edit；部分应用、自动拆分
   sibling、消融和组合搜索均不属于本阶段。
6. **创建不等于有效。** child 初始状态固定为 `draft`；后续 Failure Replay、Smoke/Evolution 回归、Final、比较、
   晋级与回退仍由之后阶段及明确授权处理。

若第 4 或第 5 项需要改变，应先更新本规格并重新确认。

## 4. 输入准入与绑定

`optimizer materialize` 仅接受已完成的 `livesqlbench-base-lite-evolution-v1` run，且必须同时满足：

- run 内存在可解析的 `edit-plan.json` 与 receipt，计划状态可执行（`proposed` 或历史兼容的
  `requires_guarded_approval`）；
- plan 的 run ID、parent candidate ID 和 parent Skill SHA-256 与当前 run 一致；
- parent candidate 可由 local store `resolve_and_verify`，其 Skill bytes 与 run materialized subject 一致；
- 每个 edit 引用的 target/anchor block 存在于当前父 Skill map，且没有 `locked` target。

`findings_only`、阶段 13 的 skipped/failed status、非 Evolution run、symlink、超限或非 UTF-8 输入均不得产生 patch 或
child。阶段 13 已完成 plan 的内部证据校验在这里不重复做一遍；本阶段只复核渲染所必需的 parent 与目标绑定。

阶段 13 的新计划在本阶段实施后只产生 `proposed` 或 `findings_only`；`guarded` 不再改变计划状态。历史 v0.11
artifact 的 `requires_guarded_approval` 只在读取边界兼容并等价归一为 `proposed`，不得再由新代码写出。

## 5. 渲染合同与机械 patch

### 5.1 确定性 renderer

renderer 只消费 `SemanticEdit` 中的 operation、目标 block/anchor、rule definition 与受信任父字节。它使用版本化的
`skill-edit-render-policy-v1`，为 workflow、recovery、constraint、heuristic 四类规则生成固定 Markdown 模板；相同
parent bytes、EditPlan bytes 与 policy 必须产生逐字节相同的 child bytes 和 patch。

八种 operation（`add_rule`、`clarify_rule`、`correct_rule`、`set_precedence`、`generalize_rule`、`merge_rules`、
`remove_rule`、`reorder_workflow`）都必须有明确的 target 形状、替换/插入规则与不可渲染条件。若某一 operation 需要的
block 类型、目标数量、anchor 或文本边界不满足模板，返回 `render_failed`，不得退化为自由文本重写或整篇格式化。

除被 plan 明确命中的 block 和其批准的 insertion boundary 外，父 Skill 字节必须保持不变。renderer 必须保留父文件的
UTF-8、行尾风格和末尾换行约定；不得重排 frontmatter、标题、code fence、表格或未命中的列表。

### 5.2 `skill-rendered-patch-v1`

成功渲染的 evidence 至少包含：

- policy version、EditPlan SHA-256、parent/child Skill SHA-256、parent candidate ID、run ID 和 target contract SHA-256；
- 每个 `edit_id` 的 operation、旧/新 block hash、目标权限、精确行区间和 renderer template ID；
- 单文件、相对路径仅为 `SKILL.md` 的标准 unified diff；
- `changed_edit_ids` 的精确集合。

patch 不得包含绝对路径、凭据、GT/Gold、held-out identity、原始 case ID、完整 prompt、session 或未经转义的控制字符。
它是本地 run evidence，不进入 Git、stdout、optimizer 输入或 candidate store。

### 5.3 机械校验

创建 child 前，服务必须完成以下无模型检查：

1. parent 和 child 都是受大小限制、无 NUL 的 UTF-8 Markdown；
2. unified diff 可无歧义地应用到 exact parent bytes，结果逐字节等于 renderer child bytes；
3. diff 非空，且每个 hunk 都对应一个 plan target 或其 insertion boundary；
4. `locked` block 及其边界没有变化，且每项 plan edit 恰好 materialize 一次；
5. child 中不得出现 patch 标记、完整 plan JSON、private path、secret-like 或 private-answer-like 文本。

candidate name 必须遵循既有安全 name contract，且目标 ID 不存在。出现同名冲突、store 验证失败或任一写入异常时，保持
parent 与 catalog 不变；不得覆写旧 child 或自行挑选下一个名称。

成功时 stdout 只输出 run ID、parent/child candidate ID、child hash、patch hash、edit 数量与 materialization status。
失败时只输出安全 error code 与最小诊断，不输出 Skill 正文、diff、evidence 或计划正文。

## 6. 持久化、lineage 与兼容性

run 内独立使用以下目录，不覆盖阶段 13 的 plan artifact：

```text
optimizer/
  edit-plan/                 # 阶段 13，保持原样
  materialization/
    rendered.patch
    receipt.json
```

成功 evidence 以原子目录发布；非成功状态只保留本次 terminal receipt，不能让过期 patch 伪装为当前结果。根
`result.json` 新增独立 `optimizer_materialization` 摘要键，只存 status、相对路径、parent/child ID、hash 与 edit 数量。

child 仍只存放既有 candidate store 允许的 `SKILL.md` 与 `metadata.json`。metadata 必须兼容读取历史 v1 candidate，
并增加仅用于 optimizer child 的非机密 provenance：EditPlan SHA-256、render policy version、patch SHA-256 与 parent
Skill SHA-256。`source_run_id` 绑定生成它的 Evolution run；origin 应新增明确的 `optimizer` 值，不能伪装成
`manual` 或 `external_agent`。

既有 v0.5 candidate、v0.9 advice、v0.11 edit plan、rotation 和 manifest 的阅读及默认行为必须保持兼容；本命令不应被
rotation 或普通 `run` 自动调用。`guarded` permission 与其保守 heading mapping 继续保留；删除的只是
`requires_guarded_approval` 的新建状态和人工审批语义。

## 7. 非目标

- 不生成新的 EditPlan，不调用 DeepSeek 或任何其他模型，不解释或补全 plan 的语义。
- 不访问或复制 GT、Gold、held-out 数据、原始 session、完整 prompt 或逐题 private evidence。
- 不运行 DSH、Docker、数据库、Failure Replay、Smoke、Evolution、Final、消融或 candidate 比较。
- 不选择、晋级、回退、退休、删除或覆盖任何 candidate；不修改 parent。
- 不自动格式化、迁移、拆分或重构完整 Skill，不支持不确定的自然语言补丁。
- 不新增 SQL dialect、benchmark、并发、云存储、CI、第三方 Markdown/diff 依赖或远端推送。

## 8. 技术约束与预期结构

继续使用 Python 3.11+、Pydantic、Typer、pytest、ruff 与 mypy，优先标准库实现 Markdown 片段变换和 unified diff
round-trip 检查，不新增依赖。所有持久化合同均严格、冻结并拒绝额外字段；路径、symlink、大小、UTF-8、hash 和 candidate
store 原子性必须沿用既有 fail-closed 边界。

获批后，实施计划应至少覆盖：

```text
src/skill_evolve/
  optimizer/      # materialization contracts、deterministic renderer、receipt、CLI orchestration
  candidate/      # optimizer lineage metadata 和 immutable store compatibility
  cli.py          # explicit optimizer materialize command and summary-only output
tests/            # synthetic plans/Skills, diff round-trip, permissions, store atomicity, CLI coverage
```

## 9. 验收标准

1. 相同的 verified parent、plan 与 render policy 产生字节稳定的 child Skill、unified diff 和 receipt hash；不调用网络或模型。
2. parent/run/plan binding 不匹配、artifact 为 symlink、目标 block 缺失或 plan status 不可执行时，零 patch、零 child；
   新生成的阶段 13 plan 不得再写出 `requires_guarded_approval`，历史值仅在读取时归一。
3. 八种语义 operation 都有可测试的确定性模板或明确 `render_failed` 分支；服务绝不以自由文本或全篇重写替代。
4. patch 可正反向应用并精确还原 parent/child；未命中 block 逐字节不变，diff 为空或出现额外 hunk 时失败。
5. `locked` target 绝不 materialize；`guarded` target 可自动 materialize，但必须满足同一套 target binding 与 diff
   机械校验，且不能携带额外文本修改。
6. 成功创建的 child 可由现有 store verify，状态为 `draft`，parent lineage、source run、plan/patch/policy hash 均可追溯；
   parent 内容和 metadata 不变，冲突名称不覆盖旧 candidate。
7. rendered patch、receipt、`result.json` 摘要和 stdout 不包含 GT/Gold、凭据、held-out identity、private path、原始 case ID、
   完整 Skill 或完整计划正文；candidate store 仍只保留允许的两个文件。
8. 阶段 13 `optimizer plan`、v0.9 advice 与普通评测流程保持不变，materialize 不自动触发评测或 provider 调用。
9. 合成 artifact、fake candidate store 和本地 CLI 定向测试覆盖上述分支；ruff、mypy 和 `git diff --check` 通过，且不运行
   真实模型、DSH、Docker、数据库或 benchmark。

## 10. 实施后验证命令

规格获准、计划完成并实施后，使用无模型、无网络、无 Docker 的定向验证：

```powershell
uv run pytest tests/test_edit_plan_contracts.py tests/test_skill_map.py tests/test_edit_plan_service.py tests/test_candidate_store.py tests/test_materialization_contracts.py tests/test_edit_plan_renderer.py tests/test_materialization_service.py tests/test_materialization_cli.py
uv run ruff check .
uv run mypy src
git diff --check
```

实施计划获准前不修改源码，也不执行这些验证命令。

## 11. 边界

- **始终：**重新验证所有来源 hash；只用确定性 renderer；在 store 写入前完成 diff/permission 校验；原子创建 child；最小化
  stdout 与 run evidence。
- **先询问：**批准实施计划、执行真实 materialize 写入、运行任何真实 DSH/模型/
  数据库/评测、增加依赖或推送远端。
- **绝不：**修改或覆盖父 Skill、绕过 `locked` 权限、将 held-out 或秘密资料写入 patch/candidate/artifact、把 child
  直接标为 evaluated/selected，或将机械校验当作效果评测。

## 12. 已确认决策

1. 阶段 14 的正式版本为 `v0.12`。
2. `guarded` 不设人工审批；它保留为保守定位与机械校验标记。
3. 正式 CLI 名称为 `optimizer materialize`。
