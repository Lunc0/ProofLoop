## 1. 目标

将 `SkillMap` 从 optimizer 的临时输入提升为每个 candidate 的本地、确定性、可审阅派生产物。

用户能够在 candidate 创建后立即检查其 Markdown 区块、权限、行号与 block ID；optimizer 只读取并复核该 Map，不再决定
Map 是否存在或在模型返回无效时丢失它。成功标准是：相同的 `SKILL.md` 和相同版本的 Map policy 始终产生相同的
`skill-map.json`，且 Map 与 candidate 的 Skill hash 可机械绑定。

## 2. 范围

本阶段应完成：

1. MVP 复用当前 `optimizer/skill_map.py` 的纯确定性 Map 生成能力；不在本阶段重构模块归属。
2. 在 baseline 初始化与 child/import 创建时，本地从已验证的 `SKILL.md` 生成 `skill-map.json`，并与 `SKILL.md`、
   `metadata.json` 一起原子写入 candidate 目录。
3. 扩展 candidate 文件允许列表：本地 candidate 为 `SKILL.md`、`skill-map.json`、`metadata.json`；带外部来源的
   candidate 额外允许 `NOTICE.md`。
4. 复用现有 Map 的 schema/policy version 与 `skill_sha256` 字段；MVP 不修改 candidate metadata，也不增加 Map 签名或
   metadata 内的 Map hash 绑定。
5. `resolve_and_verify()` 对存在的 Map 做 JSON/schema 解析，并校验 Map 内 `skill_sha256` 与实际 `SKILL.md` 一致；这
   是基本一致性检查，不引入签名、认证服务或复杂迁移。
6. 不改变 optimizer 当前的确定性即时建图与 run artifact 行为；candidate Map 是创建后可用的权威审阅副本，模型返回无效
   不会影响 candidate 中的 Map。
7. 为当前存量 candidate 提供显式、无模型的 Map 回填入口；该入口只写入由当前 `SKILL.md` 确定生成的 `skill-map.json`，
   绝不修改 `SKILL.md` 或 `metadata.json`。

## 3. 非目标

- 不使用 LLM、自然语言处理库或第三方 Markdown parser 理解 Skill 内容；仍采用受限、确定性的结构解析与标题规则。
- 不改变现有 Map 的 block 切分语义、标题白名单或 `locked`/`guarded`/`evolvable`/`experimental` 分类含义；这些属于
  后续独立策略变更。
- 不运行 DeepSeek、DSH、Docker、数据库、benchmark、Failure Replay、Smoke、Evolution 或 Final。
- 不自动重写、格式化、修复或升级 `SKILL.md`；不自动修改候选状态、选择版本、晋级、回退或推送 Git。
- 不存储 GT、Gold、held-out 身份、逐 case 结果、session、凭据、prompt 或优化模型原文到 candidate Map。

## 4. 候选文件合同

新 candidate 的目录内容为：

```text
candidates/<skill-id>/<candidate-name>/
  SKILL.md
  skill-map.json
  metadata.json
  NOTICE.md                  # 仅 external candidate
```

`skill-map.json` 是 `SKILL.md` 的衍生索引，不是用户或外部 agent 提交的输入：创建服务只接受 `SKILL.md`，在本地生成 Map。
Map 至少包含 schema/policy version、被映射 Skill 的 SHA-256、总行数及每个 block 的标题路径、类型、行区间、内容 hash、
layer、permission 和稳定 block ID。

Map policy version 已在 Map 中。MVP 读取者只校验 JSON/schema 和 Map 内 Skill hash；不增加 metadata 签名或远端认证。

## 5. 历史 candidate 与回填

现有 v1 candidate 没有 `skill-map.json`，不能在普通 `verify`、`select`、评测或 optimizer 命令中隐式改写。

本阶段建议提供显式命令：

```powershell
uv run skill-evolve candidate backfill-skill-map <candidate-id>
```

它先校验现有 candidate 的 `SKILL.md` 与 metadata，再由本地代码生成 Map；只能补写缺失的、与当前 Skill 精确匹配的 Map。
若 Map 已存在、candidate 不安全或 Map 无法生成，命令失败而不覆盖现有文件。

## 6. Optimizer 与 run artifact 边界

optimizer 继续从 run materialized subject 确定性建图，因此不会因本阶段改变其输入或已有 run artifact。candidate Map 是同一
规则的可审阅持久副本；模型响应失败、JSON 非法或 evidence 校验失败只影响 EditPlan terminal receipt，**不得删除或替换**
candidate 中的 Map。

## 7. 技术栈、命令与项目结构

- Python 3.11+、Pydantic、Typer、pytest、ruff、mypy 与标准库；不新增依赖。
- 主要代码：`src/skill_evolve/candidate/`、共享 Map 模块、`src/skill_evolve/optimizer/`、`src/skill_evolve/cli.py`。
- 定向验证：

```powershell
uv run pytest tests/test_skill_map.py tests/test_candidate_store.py tests/test_candidate_cli.py tests/test_edit_plan_service.py tests/test_materialization_service.py
uv run ruff check src/skill_evolve tests/test_skill_map.py tests/test_candidate_store.py tests/test_candidate_cli.py tests/test_edit_plan_service.py tests/test_materialization_service.py
uv run mypy src
git diff --check
```

实施计划获准前不执行上述验证命令，不调用模型或评测。

## 8. 代码风格与安全边界

继续采用严格 Pydantic 合同、冻结不可变值对象、`snake_case`、UTF-8/大小/NUL/symlink/hash fail-closed 校验，以及
`shell=False` argv subprocess 约定。

```python
if skill_map.skill_sha256 != actual_skill_sha256:
    raise CandidateStoreError("skill-map does not match candidate SKILL.md")
```

- **始终：**本地重建或验证 Map；校验 Map 内 Skill hash；原子写入；保留已有 candidate 的无关内容与
  dirty worktree。
- **先询问：**改变 Map policy 白名单、引入 Map metadata 签名、自动迁移或改造 optimizer 的 Map 输入来源。
- **绝不：**接受外部 Map 作为可信输入；让模型写 Map；在读取/评测/optimizer 中隐式回填；向候选库写入敏感评测材料；覆盖
  `SKILL.md`、已有 Map 或 candidate。

## 9. 验收标准

1. 新 baseline、手工 child、external candidate 与 optimizer materialized child 均在原子创建后拥有经过本地生成的
   `skill-map.json`；Map 的 Skill hash 与 `SKILL.md` 精确一致。
2. candidate verify 能拒绝缺失、额外、损坏、非 UTF-8、错误 policy、错误 Skill hash 或 symlink Map；外部
   candidate 的 `NOTICE.md` 兼容规则保持有效。
3. 同一 Skill bytes 与 policy 产生字节稳定的 Map；Map 生成不调用网络、模型、数据库或 benchmark。
4. 模型产生无效 EditPlan 时 candidate Map 仍可被 `candidate verify` 读取，且现有 optimizer 输入与 run artifact 行为不回归。
5. 显式回填能为指定历史 candidate 创建正确 Map；正常读取、选择、评测和 optimizer 不会隐式回填或改写候选。
6. EditPlan/materialization 对 Map hash、parent hash、block ID 与 permission 的现有 fail-closed 约束不回归。
7. 仅运行合成、无模型、无网络、无 Docker 的定向测试，且 ruff、mypy、`git diff --check` 通过。

## 10. 开放问题

1. 未来是否在 metadata 中增加 Map hash/policy binding，作为更严格的候选完整性合同？
2. 未来是否让 optimizer 从 candidate Map 读取，而不是从 run subject 即时建图？
3. Map policy 升级时，是在同一 candidate 目录保存多个版本 Map，还是用显式迁移替换当前 Map？本阶段不自动升级。
