## 1. 目标

把当前“针对失败给出自由文本建议”的优化方式，提升为可审计、可验证但尚不修改文件的
**行为导向 Skill 修改计划**。

本阶段在一次有效的 Evolution 开发集运行后，基于当前被评测 Skill、受信任的目标运行合同和
已有的 `evolution-coding-agent-input-v3`，完成以下工作：

1. 为任意一份现有 `SKILL.md` 建立确定性的逻辑结构映射，不要求原始 Skill 预先重写为标准格式。
2. 把多个失败 case 归纳为少量、证据绑定的缺陷簇，并区分问题所在模块、缺陷形式和适用作用域。
3. 把缺陷簇映射为有限种语义修改操作，明确修改前行为、期望行为和后续验证方式。
4. 产生严格、带来源 hash 的 `skill-edit-plan-v1`，供未来阶段渲染补丁、创建 child candidate 和执行
   对照评测。

成功意味着：系统能回答“为什么改、改哪个行为、允许改哪个区域、预期观察到什么变化”，但不会直接重写
`SKILL.md`，不会创建 candidate，也不会因为 LLM 的判断自动晋级或回退任何版本。

## 2. 已采用的前提

1. **Skill 的最小优化单位是行为规则，不是文字。** 文案变得更流畅、更完整或更专业，不能单独构成修改理由。
2. **标准骨架是目标格式，不是输入门槛。** 外部或历史 Skill 可以保持原样进入结构映射；不得在优化前静默整篇重排。
3. **目标运行合同由受信任代码提供。** 可用工具、只读限制、单次允许的 SQL 语句数、上下文来源和最终输出合同，
   不能由 Skill、session 或 LLM 自行声明为事实。
4. **一次处理当前输入中的全部失败 case。** LLM 应先寻找跨 case 的共性，再形成最多三个互不重叠的修改项；不得按
   case 数量机械追加规则。
5. **本阶段只输出修改计划。** 机械补丁渲染、文件修改、child 创建、Failure Replay、回归评测、消融、晋级和回退属于
   后续阶段。
6. **现有 v0.9 artifact 保持历史可读。** `skill-optimization-advice-v1` 不被原地改写；新合同使用独立 schema 和 prompt 版本。

若这些前提需要改变，应先修订并重新评审本规格。

## 3. 标准 Skill 骨架与修改权限

### 3.1 逻辑三层

推荐的新 Skill 逐步收敛到以下逻辑层，但本阶段不强制旧 Skill 一次性完成迁移：

```markdown
# Purpose and Scope

## Runtime Contract

## Core Strategy

### Task Understanding
### Workflow
### Reasoning Guidelines
### Validation
### Recovery
### Completion

## Heuristics and Examples
```

三层含义如下：

| 逻辑层 | 内容 | 优化原则 |
| --- | --- | --- |
| 硬合同层 | 适用范围、运行时能力、安全限制、最终输出合同 | 不允许普通优化器修改 |
| 核心策略层 | 任务理解、执行顺序、推理原则、验证、恢复和完成条件 | 主要优化对象 |
| 软经验层 | 常见错误、经验规则、注意事项和通用示例 | 可以修改，但必须防止过拟合 |

### 3.2 修改权限

每个逻辑块必须具有以下一种权限：

| 权限 | 含义 |
| --- | --- |
| `locked`（锁定） | 修改计划不得把它作为目标；合同不一致时应暂停并报告 |
| `guarded`（受保护） | 可以提出人工适配请求，但不能被后续自动补丁直接修改 |
| `evolvable`（可优化） | 允许进入普通修改计划，是核心策略的默认权限 |
| `experimental`（实验性） | 允许修改，但必须声明泛化风险并经过新开发题回归验证 |

frontmatter 中的 Skill 身份、受信任 Runtime Contract 和安全边界默认 `locked`；适用范围或激活描述默认
`guarded`；核心策略默认 `evolvable`；经验与示例默认 `experimental`。无法确定所属层的旧 Skill 区块必须
保守标记为 `guarded`，不能默认开放修改。

## 4. Skill 结构映射

### 4.1 结构映射职责

`skill-map-v1` 以确定性规则读取 UTF-8 Markdown，并识别：

- frontmatter；
- 标题层级；
- 普通段落；
- 连续列表；
- fenced code block；
- Markdown 表格。

每个逻辑块至少包含：当前 Skill SHA-256、区块 ID、标题路径、区块类型、起止行、区块内容 SHA-256 和修改权限。
区块 ID 必须绑定当前 Skill 内容；它只用于定位本次父版本，不承诺跨版本保持不变。

结构映射只处理文本边界，不执行 Skill，不加载其引用文件，不访问网络，也不判断业务语义。frontmatter 未闭合、代码块
未闭合、输入超过大小上限或无法稳定分块时必须 fail closed，不得产生部分映射。

### 4.2 功能模块

修改计划使用固定功能模块回答“问题在哪里”：

- `activation_and_scope`：适用范围与激活条件；
- `task_and_context_parsing`：理解任务、schema 和上下文；
- `planning_and_order`：步骤规划与先后依赖；
- `domain_reasoning`：领域推理和 SQL 构造原则；
- `tool_execution`：工具选择、参数和调用方式；
- `safety_constraints`：只读、安全和禁止行为；
- `validation`：中间结果与最终结果检查；
- `recovery`：失败后的修正、重试和退出；
- `final_submission`：停止探索与提交最终结果。

每个缺陷簇和修改项必须有一个主要模块，最多再有两个次要模块。功能模块是语义标签，不决定文件一定要拆成对应章节。

## 5. 受信任的目标运行合同

目标运行合同必须由受信任 benchmark/runner adapter 生成、版本化并绑定 SHA-256。它只包含 optimizer 所需的非机密能力
事实，例如：

```json
{
  "schema_version": "skill-target-contract-v1",
  "available_capabilities": ["sql-readonly"],
  "sql_mutability": "read_only",
  "max_statements_per_call": 1,
  "task_context_sources": ["schema", "knowledge", "column_meaning"],
  "final_submission_contract": "one_final_sql_statement"
}
```

合同不得包含 endpoint、凭据、绝对路径、GT、Gold、held-out identity 或逐题私有结果。Skill 内容与目标合同冲突时，
可以形成 `target_compatibility` finding；如果冲突位于 `locked` 区域，只能报告合同不一致，不能生成自动修改项。

## 6. 缺陷簇

### 6.1 三维描述

每个缺陷簇必须同时回答：

1. **功能模块：**问题在哪里；
2. **缺陷类型：**以什么形式出现；
3. **作用域：**相对于什么标准存在问题。

作用域固定为：

- `intrinsic_quality`：Skill 自身的矛盾、重复或结构问题；
- `target_compatibility`：Skill 与当前目标运行合同不兼容；
- `failure_causal_hypothesis`：可能与一个或多个开发集失败相关，但因果关系尚未验证；
- `candidate_generalization`：child 的过拟合或回归；本阶段只可将它列为未来风险，不可据首次失败直接认定。

### 6.2 缺陷类型

| 缺陷类型 | 中文含义 | 最低要求 |
| --- | --- | --- |
| `missing_guidance` | 缺少必要指导 | 声明所需行为、适用模块和证据；只能作为待验证假设 |
| `underspecified_guidance` | 指导过于模糊 | 引用已有规则，并指出缺少哪项行为要素 |
| `incorrect_guidance` | 规则与可信合同或直接事实冲突 | 引用 Skill 区块和受信任合同字段 |
| `workflow_order_issue` | 执行顺序或依赖不合理 | 引用至少两个动作及其顺序依据 |
| `missing_recovery_strategy` | 缺少失败恢复路径 | 引用失败 episode、恢复观察和相关 Skill 区块 |
| `priority_conflict` | 多目标优先级不清 | 引用至少两条同时适用的规则和具体冲突场景 |
| `contradiction` | 两条适用规则给出不兼容动作 | 引用至少两个 Skill 区块 |
| `redundancy` | 相同作用域下重复表达相同行为 | 引用至少两个 Skill 区块；默认仅为静态质量风险 |
| `activation_issue` | 适用范围、激活或接触路径不清 | 引用 Skill access 观察或受保护的激活区块 |

LLM 可以提出缺陷簇，但不能声明“根因已确认”，不能输出数字置信度，也不能把没有观察到规则读取表述为规则不存在。

## 7. 从缺陷到语义修改

### 7.1 有限修改操作

本阶段只允许以下语义操作；它们描述行为意图，不是文件补丁：

| 语义操作 | 中文含义 | 常见来源 |
| --- | --- | --- |
| `add_rule` | 增加一条通用行为规则 | 缺少指导、缺少恢复 |
| `clarify_rule` | 补足已有规则的触发、动作或结束条件 | 指导模糊、激活不清 |
| `correct_rule` | 用符合可信合同的规则替换错误规则 | 错误指导 |
| `set_precedence` | 明确规则冲突时的优先顺序 | 优先级冲突 |
| `generalize_rule` | 去除对具体 case 的过度限定 | 后续 child 泛化问题 |
| `merge_rules` | 合并重复或冲突规则 | 冗余、矛盾 |
| `remove_rule` | 删除错误且无替代价值的规则 | 错误、冗余、过拟合 |
| `reorder_workflow` | 调整步骤依赖与顺序 | 工作流顺序问题 |

`insert_block`、`replace_block`、`delete_block`、`move_block` 等具体文件动作属于后续 Patch Renderer，本阶段不得输出或应用。

### 7.2 行为规则类型

不同规则不强制填写同一套字段，而是按规则类型验证完整性：

- **工作流规则：**触发时机、执行动作、验证方式、结束或下一步；
- **恢复规则：**失败信号、诊断动作、恢复动作、重试或替代路径、验证方式、停止条件；
- **约束规则：**适用范围、要求或禁止行为、优先级、违反后的处理；
- **经验规则：**适用条件、建议动作、适用边界。

`underspecified_guidance` 必须指出当前规则缺少该类型的哪个必要要素，不能只写“需要更清楚”。

## 8. 行为导向修改计划

### 8.1 修改计划合同

`skill-edit-plan-v1` 至少包含：

- 父 candidate ID、父 Skill SHA-256、agent-input SHA-256 和目标合同 SHA-256；
- 输入中的缺陷簇及其 case/evidence/block 引用；
- 最多三个语义修改项；
- 每项修改的目标层、权限、模块、缺陷类型、语义操作和目标区块；
- 修改前观察到的行为；
- 期望出现的可观察行为；
- 规则类型及其必要行为要素；
- 泛化范围、回归风险和可证伪验证方案。

模型不能声明或覆盖可信 source binding、计划状态、Skill/contract hash 或本地生成的 ID。服务必须在严格校验后加入这些字段。

### 8.2 行为断言

每个修改项必须描述可在未来轨迹中观察的行为变化，至少包含：

- 触发事件；
- 修改前观察行为；
- 期望动作；
- 提交前必须出现的动作或结果；
- 禁止的提前行为；
- 成功或停止条件。

例如，恢复规则不能只写“增强错误处理”，而应表达为：工具失败后，在最终提交前必须先检查直接错误、修正动作、执行重试并
验证结果；若无法恢复，应明确停止，而不是无限重试。

无法由现有安全投影客观判断的断言必须标记为 `review_only`，不能伪装成可自动验证条件。

### 8.3 批量优化规则

1. 单次计划消费当前授权输入中的全部失败 case，并先形成跨 case 缺陷簇。
2. 一份计划最多包含三个修改项；每个修改项必须绑定至少一个缺陷簇和一个 evidence case。
3. 不同修改项不得修改同一目标区块；如果目标重叠，必须合并为一个修改项。
4. 修改项不得直接复制 case ID、完整 prompt、具体答案、Gold、GT 或私有路径进入规则意图。
5. 本阶段不预先生成所有修改组合。后续仅在 batch child 回归或结论不明确时，才允许按修改项创建 sibling child 做消融。

## 9. 准入、持久化与兼容性

计划生成沿用阶段 11 的 v3、subject hash、输入大小、无工具模型和 prompt-injection 边界，并增加以下准入：

- 只处理有效的 Evolution run；runner/evaluator invalid、无有效失败轨迹、Skill hash 不符或目标合同无效时不调用模型；
- Smoke、Final、普通 benchmark 和 held-out 不产生修改计划；
- Final 的 case identity、逐题结果、session 和 manifest 永远不进入缺陷簇或修改计划；
- Skill、trajectory 和模型输出继续视为不可信文本。

成功时只在当前 run 的本地 optimizer artifact 子目录下保存：

```text
optimizer/
  edit-plan/
    skill-map.json
    edit-plan.json
    edit-plan.md
    receipt.json
```

根 `result.json` 在独立的 `optimizer_edit_plan` 摘要键下只记录 terminal status、相对 artifact 路径、hash、缺陷簇数量和
修改项数量，不复制正文。artifact 不进入 Git 或 candidate store。历史 `skill-optimization-advice-v1` artifact 及其
`optimizer/receipt.json` 保持原样；新 schema 不原地覆盖旧文件。

## 10. 非目标

- 不渲染 Markdown 修改内容，不输出机械 patch，不修改任何 `SKILL.md`。
- 不创建、导入、选择、晋级、回退或删除 candidate。
- 不执行 Failure Replay、Smoke、Evolution 回归、Final、消融或多候选比较。
- 不自动重构旧 Skill 为标准骨架，不把格式变化伪装成无行为影响的预处理。
- 不让 optimizer 修改 locked 区域或自行修复目标运行合同。
- 不判断模型能力不足，不把单个失败直接认定为 Skill 根因。
- 不增加 SQL dialect、benchmark、第三方 Markdown parser、并发、CI、云存储或远端推送。
- 不在实施验证中调用真实 LLM、DSH、Docker、数据库或真实 benchmark。

## 11. 技术约束与预期结构

继续使用 Python 3.11+、Pydantic、Typer、pytest、ruff 与 mypy，不新增第三方依赖。所有持久化合同严格、冻结并拒绝额外字段；
所有输入执行 UTF-8、大小、数量、路径、hash 和 symlink 校验。

预期责任边界如下，具体文件由规格批准后的实施计划确定：

```text
src/skill_evolve/
  trajectory/     # 保持 v3 optimizer-safe evidence 合同
  optimizer/      # Skill map、目标合同、缺陷簇、EditPlan、LLM 编排与 receipt
  candidate/      # 本阶段不改动 candidate 生命周期
tests/            # 合成 Skill、合成 v3 evidence、fake LLM 与严格合同测试
```

## 12. 验收标准

1. 任意有效 UTF-8 旧 Skill 无需预先重写即可生成字节稳定的 `skill-map-v1`；相同输入与 policy 产生相同 block ID 和 hash。
2. 标准骨架中的 hard contract、核心策略和经验层被映射为正确权限；未知旧区块默认 `guarded`，不被误开放。
3. 一个受信任、无机密的目标运行合同可与 Skill 和计划绑定；模型不能伪造或覆盖合同字段。
4. 合成 DBHub 风格 Skill 中“支持多语句”的规则与 `max_statements_per_call: 1` 冲突时，形成
   `target_compatibility + incorrect_guidance` finding，但不声称它已经造成某个 runner error。
5. 多个失败 case 可以聚为同一缺陷簇；一份计划最多三个非重叠修改项，每项都可追溯到 case、evidence、Skill block 和缺陷簇。
6. 每个修改项包含修改前行为、期望行为、规则类型、泛化范围、回归风险和可证伪验证方案；“让文案更清晰”不能单独通过校验。
7. 对 locked 区域的修改被拒绝；guarded 区域只产生待人工批准的适配请求；evolvable/experimental 区域仍受 evidence 和风险校验。
8. contradiction、incorrect guidance、missing recovery 等类型缺少其特定最低引用时被拒绝；首次失败诊断不能把
   overspecialization 声称为已确认缺陷。
9. 模型返回虚构 case/evidence/block ID、额外字段、完整新 Skill、机械 patch、GT/Gold、凭据或绝对 custody 路径时，结果为无效且不留下部分计划。
10. runner/evaluator invalid、无失败轨迹、subject/contract hash 漂移、Smoke/Final/held-out 输入均不会调用计划模型。
11. 现有 v0.9 advice artifact 和旧 run 保持可读；本阶段不修改 candidate store，也不产生 child。
12. 实施验证只使用合成 artifact 和 fake client；定向测试、ruff、mypy 与 `git diff --check` 通过，不运行真实服务。

## 13. 实施后的验证命令

规格获准并完成实施后，优先使用无模型、无网络、无 Docker 的定向验证：

```powershell
uv run pytest tests/test_optimizer_contracts.py tests/test_optimizer_service.py
uv run ruff check .
uv run mypy src
git diff --check
```

实际新增测试文件和完整命令见阶段 13 实施计划。实施计划获准前不修改源码，也不执行上述命令。

## 14. 边界

- **始终：**保持 Skill/target contract/evidence/plan 的 hash 绑定；把模型输出视为不可信；使用固定枚举、类型特定验证、
  原子 artifact 写入和最小 stdout。
- **先询问：**批准实施计划、调用真实优化模型、允许生成或应用 patch、创建 child、修改 candidate
  生命周期、运行真实 DSH/Docker/Evolution/Final、增加依赖或推送远端。
- **绝不：**把 GT/Gold、凭据、原始 session、held-out identity/逐题结果、私有路径或完整新 Skill 交给计划 artifact；让 LLM
  修改硬合同、覆盖父 Skill 或把建议状态冒充为客观评测结论。

## 15. 已确认决策与开放问题

### 15.1 已确认决策

1. 原始 Skill 不强制预先重构，标准骨架是逐步收敛目标。
2. Runtime Contract 由受信任 runtime/adapter 提供并锁定，普通 optimizer 无权修改。
3. EditPlan 不包含整篇新 Skill，也不包含机械 patch。
4. 规则完整性按工作流、恢复、约束和经验四类分别判断。
5. 单次处理全部失败 case，但每份计划最多三个互不重叠的修改项。
6. 每项优化必须声明可观察行为变化和可证伪验证方案。
7. batch child 回归或结论不明确时，才在后续阶段按修改项执行消融。
8. 阶段 13 的正式版本为 v0.11。
9. 新 `edit_plan` 与 v0.9 advice 并存，通过显式 `optimizer plan` 命令触发；本阶段不改变旧 manifest 和 rotation 的默认行为。
10. 新产物写入 `optimizer/edit-plan/`，避免覆盖 v0.9 advice 及其 receipt。

### 15.2 开放问题

1. 阶段 14 对 guarded 修改采用逐项人工批准还是整份计划批准，需要在 child/patch 规格中确定；不阻塞阶段 13 实施。
