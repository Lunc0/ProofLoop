# 规格：本地 SQL Skill 候选版本库与受控演进

> **阶段：**05 · **版本：**v0.5 · **状态：**已完成
>
> **对应计划：**[实施计划](../plans/05-v0.5-local-skill-evolution.md) · **实现记录：**[v0.5 本地候选库](../design/v0.5-local-skill-evolution.md)

**状态：**阶段 A、B、C 已实现并完成验证。
**目标版本：**v0.5（项目包版本保持 0.4.0，本阶段不发布）。

## 1. 目标

为本机上的 SQL Skill 建立一个独立于 Git 的候选版本库。系统可以保存初版 Skill、后续优化产生的多个
候选版本、它们之间的谱系和已知评测证据；操作者可选择其中任一版本，安全地注入一次本地 benchmark run，
并以客观 SQL 评测结果作为后续优化的输入。

这里的“版本管理”是本地 candidate 管理，不要求把每次优化结果提交到 GitHub。Git 仍可用于维护本项目代码
和可公开的基线 Skill，但不是候选版本库的唯一存储方式。

成功后的闭环：

```text
初版 Skill
  → 导入为本地 baseline candidate
  → 选择一个 candidate 运行 benchmark
  → 仅从公开、脱敏的 run evidence 生成优化输入
  → 导入一个新的 candidate（保留父版本）
  → 评测、比较、人工或受控策略选择下一版本
```

## 2. 当前状态与缺口

当前 `candidate.ref` 只是身份标签，`candidate.digest_file` 只接受 manifest workspace 内的单个文件。它会被
哈希、复制到 run inputs，并在普通 DSH workflow 中复制到 task workspace 的 `candidate/` 子目录。

这还不是完整的 Skill 加载机制：

- runner 不会明确要求 DSH 读取 `candidate/SKILL.md`；
- `benchmark run` 目前没有 candidate ID 或 candidate 文件参数；
- LiveSQLBench run 会把 `candidate_ref` 设为空，故不会复制候选 Skill；
- 没有 candidate catalog、谱系、状态、比较或 champion 选择；
- 当前 LiveSQLBench Base-Lite 是固定的五题 fast suite，尚无可用于自动 promotion 的 dev/held-out gate。

因此，本规格只把“候选存储、受控注入、证据绑定和选择接口”定义为核心能力；自动模型改写 Skill 不在首个
实现范围内。

## 3. 已批准的前提

维护者已批准以下实现边界：

1. 候选版本只保存在本机，不写入 Git；本地根目录会被 `.gitignore` 忽略。
2. MVP 只支持文本型单文件 `SKILL.md`，不运行 candidate 中的 Python、JavaScript、shell、插件或下载脚本。
3. 新 candidate 由人工或外部上层 agent 产出后显式导入；本项目 MVP 不调用模型，也不自动覆盖已有 Skill。
4. LiveSQLBench 的 GT、Gold SQL、Gold 结果、私有 dumps 和 held-out 数据永远不会成为 candidate 内容、优化
   prompt、catalog、stdout、report 或 Git 输入。
5. 第一个受支持的运行目标仍是 `livesqlbench-base-lite` + PostgreSQL + DSH；不新增 SQL dialect、并发、
   网络存储、依赖或 CI。

### 3.1 已选择的上游 baseline

首个 baseline 来源确定为 Bytebase DBHub 的 `skills/dbhub/SKILL.md`：

```text
https://github.com/bytebase/dbhub/blob/main/skills/dbhub/SKILL.md
```

导入时必须将 `main` 解析为具体 Git commit SHA，并记录无追踪参数的 source URL、commit SHA、文件
SHA-256、来源仓库和 MIT 许可。不能只记录会随时间变化的 `main` 分支 URL。

导入后的不可变原始 candidate ID 为 `dbhub/000-upstream-baseline`。它逐字保存上游 Skill，不为适配
benchmark 而先行修改；同目录额外保存 `NOTICE.md`，保留上游 MIT 版权和许可通知。agent workspace
只复制 `SKILL.md`，不复制 `NOTICE.md`。

DBHub baseline 假设可调用 `search_objects` 与 `execute_sql` 两个 DBHub MCP tools。当前 LiveSQLBench
workspace 不提供这两个工具，只提供公开 schema/context 与 `sql-readonly.ps1`。因此：

- `dbhub/000-upstream-baseline` 是来源和效果的原始对照，不能被悄悄改写；
- 第一个可适配候选应是它的 child，例如 `dbhub/001-livesqlbench-readonly-adaptation`；
- 不得为使 baseline 原样运行而私自安装或启动 DBHub、加入 MCP server、连接任意数据库，或改变 benchmark
  的只读能力。这些都属于需要单独确认的真实 DSH/工具集成。

## 4. 本地目录与数据模型

### 4.1 根目录

候选版本库使用固定的、被 Git 忽略的根目录：

```text
.local/skill-evolve/
├── catalog.json
└── candidates/
    └── sql-analyst/
        ├── 000-baseline/
        │   ├── SKILL.md
        │   └── metadata.json
        ├── 001-improve-joins/
        │   ├── SKILL.md
        │   └── metadata.json
        └── 002-fix-aggregation/
            ├── SKILL.md
            └── metadata.json
```

`examples/` 继续只放可提交的示例；`data/` 继续只放 benchmark 数据。候选 Skill 既不放入 `examples/`，也不
放入 `data/`。

### 4.2 Candidate metadata

每个 `metadata.json` 是严格验证的、非秘密 JSON：

```json
{
  "schema_version": "v1",
  "candidate_id": "sql-analyst/001-improve-joins",
  "skill_id": "sql-analyst",
  "parent_candidate_id": "sql-analyst/000-baseline",
  "created_at": "2026-08-26T00:00:00Z",
  "source_run_id": "20260826T000000Z-12345678",
  "skill_sha256": "<64 lowercase hex characters>",
  "origin": "external_agent",
  "status": "draft"
}
```

字段约束：

- `candidate_id`、`skill_id` 和父 ID 使用安全的小写标识符；ID 不能携带路径、URL 或 import path。
- `skill_sha256` 必须等于同目录 `SKILL.md` 的 bytes hash；不信任 metadata 自报的值。
- `parent_candidate_id` 只允许为空（baseline）或引用 catalog 中已有 candidate；禁止谱系环。
- `source_run_id` 仅保存公开 run ID；不复制其 GT 或完整私有数据。
- `origin` 首版枚举为 `manual` 与 `external_agent`，只表明来源，不执行来源所代表的程序。
- 外部来源 candidate 必须额外记录不可变 revision、canonical source URL 和许可，并在 `NOTICE.md` 保留
  许可通知；`NOTICE.md` 不进入 agent workspace。
- `status` 首版枚举为 `draft`、`evaluated`、`selected`、`retired`；同一 `skill_id` 最多一个 `selected`。

`catalog.json` 是由本机 candidate store 写入的索引，只保存 candidate ID、状态、hash、父 ID、创建时间和
公开 run ID。candidate 的完整文本仍只保存在候选目录和 run 的已忽略 inputs 中。

### 4.3 不可变性

一旦 candidate 被导入，`SKILL.md` 和 `metadata.json` 不得原地修改。优化产生新版本时必须创建新目录和
新 candidate ID。若校验发现目录的实际 hash 与 metadata 或 catalog 不一致，该 candidate 视为损坏，拒绝
运行和选择。

## 5. 公开 CLI 设计

以下命令均只操作 `.local/skill-evolve/` 中的已验证文本 artifacts；不执行 candidate 内代码。

```text
skill-evolve candidate init <skill-id> <skill-file>
skill-evolve candidate import <skill-id> <candidate-name> <skill-file> --parent <candidate-id> --source-run <run-id>
skill-evolve candidate list <skill-id>
skill-evolve candidate show <candidate-id>
skill-evolve candidate select <candidate-id>
skill-evolve candidate verify <candidate-id>

skill-evolve benchmark run <adapter-id> <data-root> <dsh-manifest> --candidate <candidate-id>
```

命令语义：

- `init` 将一个明确提供的初版 `SKILL.md` 复制为 `000-baseline`，计算 hash，建立 catalog。
- `import` 将一个明确提供的候选文件复制为新目录；它只接受文本 `SKILL.md`，验证父版本和来源 run，不改写
  任何旧版本。
- `list` 和 `show` 只显示 metadata、hash、状态、谱系和公开评测摘要，不显示 GT。
- `select` 只变更本机 catalog 中的当前选择，不修改文件，也不自动发起 benchmark。
- `verify` 重新计算 hash、检查 catalog/metadata 一致性及谱系无环。
- `benchmark run --candidate` 只接受 candidate ID，不接受任意文件路径；它从固定 local root 解析候选版本。

对未知 ID、路径逃逸、重复目录、hash 不一致、缺失父版本、谱系环或非法 metadata，命令必须以退出码 64
失败，且不得启动 DSH、Docker 或模型。

## 6. Candidate 注入与 GT 隔离

### 6.1 运行时流程

```text
candidate ID
  → LocalCandidateStore.resolve_and_verify()
  → 读取 SKILL.md bytes，重新计算 hash
  → environment fingerprint 写入 candidate ID + hash
  → 每题新建 agent workspace
  → 仅复制 candidate/SKILL.md、公开 schema 和公开 context
  → TASK.md 明确要求先读取 candidate/SKILL.md
  → DSH 在该隔离 workspace 中运行
  → adapter 在本地私有 GT 上评分
```

DSH job 只包含“读取 `candidate/SKILL.md` 并按其指引完成任务”的固定指令，不将 Skill 正文拼入命令行。
这样 session invocation artifact 不会重复记录 candidate 文本，也不会把候选文本与 Gold SQL 混在一起。

`SKILL.md` 是受评对象，不是可执行程序：系统只复制和让 DSH 阅读其文本。任何 candidate 附带的脚本、
插件、symlink、二进制文件或超出最大尺寸的文件都必须被拒绝。

### 6.2 允许与禁止进入 agent workspace 的内容

| 内容 | 是否允许 | 原因 |
|---|---|---|
| `candidate/SKILL.md` | 允许 | 正在比较的公开/本地 Skill 文本。 |
| case prompt、公开 schema、公开 HKB/字段说明 | 允许 | Agent 完成题目所需的公开上下文。 |
| 本地只读查询 capability | 允许 | 仅探索该题 disposable PostgreSQL fixture。 |
| Gold SQL、GT test cases、Gold query result | 禁止 | 仅 evaluator 本地内存可见。 |
| 私有 dump、data root 路径、数据库凭据 | 禁止 | 不属于 Agent 输入。 |
| candidate 的可执行代码或任意外部文件 | 禁止 | 防止数据目录或 candidate 成为执行入口。 |

### 6.3 优化反馈包

供人工或外部上层 agent 优化的输入只允许包含：candidate ID/hash、公开 prompt、候选 SQL、公开 verdict、
公开错误详情、usage、脱敏 trajectory，以及 `skill-change-suggestion.md` 中的公开建议。

反馈包不得读取、拼接或传递 `data/.../gt/`、Gold SQL、Gold results、fixtures dump、DSH 凭据或原始未脱敏
session log。外部上层 agent 返回的新 `SKILL.md` 后，必须通过 `candidate import` 创建新版本，而不能覆写父
目录。

## 7. 选择、比较与晋级

### 7.1 首版选择规则

首版只提供本机的显式 `select`：操作者按公开评测证据选择一个 candidate。`selected` 表示“下次默认使用”，
不意味着 Git 发布、DSH 全局安装或永久 champion。

系统可以为同一冻结环境比较两个 candidate 的公开 summary，但环境指纹、adapter ID、source digests、DSH
配置、模型配置和 candidate hash 任一不同，必须显示为“不可直接比较”。

### 7.2 自动晋级的后续门槛

自动 `select`/promotion 不属于首版。它至少要求：

1. 一个有明确 fast、dev、held-out 访问边界的 suite；
2. candidate 仅能从允许暴露的 fast/dev 公开 evidence 产生；
3. 已冻结的环境下，候选通过规定 gate 且不造成回归；
4. 对 held-out 的运行不把题目、Gold 或结果反馈给优化器；
5. 明确的 rollback 指向先前 `selected` candidate。

当前 LiveSQLBench Base-Lite 的固定五题不满足这套 gate 前提，因此不得将其五题总分直接用于自动 champion
选择。

## 8. 技术基础与代码风格

沿用当前 Python 3.11+、Typer、Pydantic、PyYAML、pytest、ruff 和 mypy；首版不增加依赖、数据库或服务。
Candidate metadata、catalog 和 CLI JSON 都使用 frozen Pydantic model 或 frozen dataclass，禁止用未验证的
`dict[str, Any]` 表示 candidate 状态。

```python
class CandidateMetadata(StrictModel):
    candidate_id: str
    skill_id: str
    parent_candidate_id: str | None = None
    skill_sha256: str
    status: CandidateStatus
```

命名使用 `snake_case`；文件写入采用“写入临时同级文件 → fsync/replace”的原子模式；所有路径先 resolve 并
验证仍在 `.local/skill-evolve/` 根目录内。任何来自 candidate、catalog、run evidence 或 CLI 的文本都视为
不可信输入。

## 9. 项目结构与模块边界

```text
src/skill_evolve/
  candidate/
    contracts.py       # Candidate、metadata、catalog 的严格公开类型
    store.py           # .local root、原子写入、hash 与谱系校验
    service.py         # init/import/list/show/select/verify 纯编排
  benchmark/
    ...                # adapter 仍私有持有 GT；只接收已验证 Candidate
  runner/
    dsh.py             # 每题复制 SKILL.md，固定 TASK.md 加载指令
  cli.py               # candidate 子命令和 benchmark run --candidate

tests/
  test_candidate_store.py
  test_candidate_cli.py
  test_candidate_lineage.py
  test_candidate_dsh_injection.py
  test_candidate_benchmark_integration.py
```

Candidate store 不属于 benchmark data adapter registry；它不会改变 `livesqlbench-base-lite` 的静态注册规则，也
不会从 `.local/` import 或执行 Python。

## 10. 实施阶段

### 阶段 A：本地 candidate store

实现严格 typed 的 candidate metadata、catalog、hash 和谱系验证，以及 `init/import/list/show/verify`。

- 验收：可创建 baseline 和 child；同名、路径逃逸、hash 篡改和谱系环都被拒绝。
- 验证：单元测试；`ruff`、`mypy`、`pytest`。
- 不做：模型调用、自动改写、DSH、Docker。

### 阶段 B：候选选择与普通 workflow evidence

实现 `select` 和将 candidate ID/hash 绑定进普通 workflow 的 fingerprint、resolved manifest 与 run evidence。

- 验收：选择状态在重启后仍可读；同环境的两个 candidate 可显示公开可比性；candidate 输入被保存。
- 验证：fake runner 测试，不调用真实 DSH 或模型。
- 不做：自动 promotion 或 benchmark data 改动。

### 阶段 C：LiveSQLBench 受控注入

为 `benchmark run` 增加 `--candidate <candidate-id>`，每题仅复制已验证的 `SKILL.md`，并由固定 TASK 指令
要求 DSH 读取它。adapter 继续私有管理 GT。

- 验收：agent workspace 和 DSH job 有 candidate 加载证据，但不包含 GT；每题仍是独立 fixture。
- 验证：stub DSH/fixture 测试；保留 timeout 和非零退出的脱敏 session log 回归。
- 不做：真实 DSH 或模型调用。

### 阶段 D：受控优化器接口（未批准，不实施）

定义只读 feedback bundle 和外部 optimizer 的文本输出格式；优化器只能提交新 `SKILL.md`，由 candidate import
验证和持久化。

- 验收：反馈包不含 GT；导入不会改写父版本；失败导入没有部分目录或 catalog 更新。
- 需要先确认：是否允许本项目调用模型，使用哪个 provider/凭据路径、预算、人工审阅和失败处理。

### 阶段 E：gate 与自动选择（可选，未批准，不实施）

在存在真实 fast/dev/held-out 数据隔离方案后，定义 promotion、rollback 和不可比环境的规则。

- 需要先确认：held-out 的授权/保管、访问隔离与自动选择权限。

## 11. 测试策略

- **纯单元测试：**metadata schema、ID/path 校验、hash、原子写、catalog、谱系和选择状态。
- **CLI 测试：**所有 candidate 命令的 JSON 输出、退出码 64，以及不产生部分本地状态。
- **Runner 测试：**stub DSH 断言每题只收到 `candidate/SKILL.md`、公开 context 和只读 capability；Gold 字符串
  不出现在 workspace、job、runner output、session artifact、evaluation、result 或 report。
- **Benchmark 回归：**五题 Soft-EX、独立 fixture、DSH timeout/非零退出 session capture 均保持现有行为。
- **完整检查：**`uv run ruff check .`、`uv run mypy src`、`uv run pytest`、`git diff --check`。

没有已批准的真实 DSH 或模型调用时，测试一律使用 stub/fake；不得为验证候选版本而消耗真实模型额度。

## 12. 边界

- **始终：**验证所有本地输入；使用 argv 和 `shell=False`；以原子方式写 candidate/catalog；保留父版本；
  让 GT 只在本地 evaluator 内存中可见；保存脱敏证据；把 candidate hash 纳入环境指纹。
- **先询问：**调用模型或真实 DSH；自动生成/改写 Skill；新增 SQL dialect、第二 benchmark、依赖、CI、云存储；
  建立 held-out 数据访问策略；启用自动 promotion/rollback。
- **绝不：**从 candidate、data 或 catalog 动态 import/执行代码；将 GT、Gold SQL、Gold results、凭据或未脱敏
  session log 写入 candidate store、优化反馈包、Git、stdout、report 或 agent workspace；覆盖已导入版本；
  以高权限角色执行候选 SQL；连接生产数据库。

## 13. 成功标准

1. 一台离线机器可保存一个 baseline 与多个本地 child candidate，并在不依赖 Git 的情况下验证它们的 hash 和
   谱系。
2. 每次 run 都能唯一关联 candidate ID 和 hash；任一变化都会改变 fingerprint，旧 run 仍保留对应输入证据。
3. `benchmark run --candidate` 只向每题 agent workspace 注入该 candidate 的单个 `SKILL.md` 与公开上下文，
   并保持 LiveSQLBench GT 隔离和 fixture 隔离。
4. 优化反馈包不含任何 GT 或 Gold material；新 candidate 只能通过显式导入产生，不能覆盖旧版。
5. 在未额外确认前，系统不调用真实模型/DSH，不自动改写 Skill，也不自动选择 champion。

## 14. 已确认与保留问题

1. 已确认使用 `.local/skill-evolve/` 作为本机候选版本库，并将其加入 `.gitignore`。
2. 已确认 MVP 严格限定为单文件 `SKILL.md`，不支持 references、脚本或插件。
3. 已确认阶段 C 以 `benchmark run ... --candidate <candidate-id>` 作为受控注入入口；原有不带 candidate 的 benchmark CLI 保持兼容。
4. 阶段 D 的上层优化器权限、provider、凭据和人工审阅流程尚未确认，因此不实施。
5. `selected` 仅表示本机默认候选；自动 gate、promotion 与 rollback 留待持有隔离策略后另行批准。
