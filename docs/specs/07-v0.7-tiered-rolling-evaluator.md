# 规格：LiveSQLBench 分层滚动评测器

> **阶段：**07 · **版本：**v0.7 · **状态：**已完成
>
> **前置阶段：**[阶段 04：Benchmark Adapter](04-v0.4-postgres-benchmark-adapter-framework.md)、[阶段 05：本地 Skill 候选版本库](05-v0.5-local-skill-evolution.md)、[阶段 06：最终 Held-out](06-v0.6-livesqlbench-final-thirty-query-suite.md)

## 1. 目标

建立独立于 Skill 优化方式的 LiveSQLBench 分层评测链路：滚动 Smoke（5 题）、滚动 Evolution（15 题）与既有固定 Final Held-out（30 题）。

本阶段只负责创建和执行可审计的评测题单、保存符合可见性策略的证据、产生分层指标和比较键。它不假定 Skill 由人工、coding agent 或其他程序生成，也不创建、改写、选择、晋级或回滚任何 Skill。

成功意味着：任意被测对象只要能被外部适配为只读的评测输入，就能在三层中运行；同一份题单、环境和评测器下的多个运行可以可靠比较；最终 30 题的身份和逐题证据继续与优化侧隔离。

## 2. 范围

### 2.1 分层 suite

1. 保留既有 `livesqlbench-base-lite` 固定五题 adapter 的 ID、选题与历史 evidence 合同，不原地改为随机选题。
2. 新增 `livesqlbench-base-lite-smoke-rotation-v1`：每份 manifest 恰有 5 个 Query case，从与 Evolution 共用的开发题池抽取。每个 manifest 使用连续三轮轮换的 `2/2/1` 难度配额，使 Simple、Moderate、Challenging 长期均衡。
3. 新增 `livesqlbench-base-lite-evolution-v1`：每份 manifest 恰有 15 个 Query case，Simple、Moderate、Challenging 各 5 题，也从同一开发题池抽取。Evolution manifest 可包含已进入 Smoke manifest 的 case；两层之间允许重叠。
4. 保持 `livesqlbench-base-lite-query-final-v1` 的 30 题不可变 manifest、custody-only 执行与 aggregate-only 输出，不重新选题、不将它接入滚动或优化反馈。

### 2.2 评测器职责

评测器负责：

- 校验公开题目元数据、GT、fixture dump、schema/context 和难度配额；材料不全时在启动 Docker、DSH 或模型前 fail closed。
- 在 evaluator custody 内创建不可覆盖、带 SHA-256 的 rotation manifest；每次 run 记录 manifest hash、公开数据源 digest、评测器版本和环境比较键。
- 复用既有 disposable PostgreSQL fixture、只读 SQL capability、DSH runner、Soft-EX 与 timeout/nonzero-exit 的脱敏证据语义。
- 输出每个 tier 的数量、通过数、通过率、macro-average、状态与成本字段；缺失成本保持缺失，不推断。Smoke 与 Evolution 的逐题 session-log 和报告沿用现有 run 目录的保管方式；本规格不新增逐题投影字段合同。
- 区分 `passed`、`task_failure`、`runner_invalid`、`evaluator_invalid` 与 `incomparable` 等中性评测结论。

### 2.3 与 Skill 优化解耦

`benchmark` 与 `runner` 只接收 benchmark-local 的只读 `RunSubject`：不透明 subject ID、内容 SHA-256 和已物化的只读输入。candidate store 未来可在边界处把 `ResolvedCandidate` 适配为 `RunSubject`，但 benchmark contract 不再导入 candidate 模块。

评测结果只绑定 subject ID/hash，不解释其来源和谱系。任何“是否修改 Skill”“如何生成新 Skill”“是否自动 select/promotion/rollback”的规则属于未来独立模块。

## 3. 轮换与可比性规则

1. 每次 rotation 先生成并冻结 manifest，后执行 run；不提供调用者指定 case ID、随机 seed、动态 import 或外部插件入口。
2. Smoke 可以按一次评测尝试创建新 manifest，并作为进入 Evolution 的硬门槛：仅当 5 个 case 全部 `passed` 时，被测对象才具备运行 Evolution 的资格。任一 `task_failure`、`runner_invalid` 或 `evaluator_invalid` 都必须停止该次漏斗，不启动 Evolution；前两类结论不可被伪装为通过，后两类结论不可被误归因为被测对象失败。Smoke 的通过不构成 promotion 分数或任何 Skill 决策。
3. Evolution 只接收通过 Smoke 门槛的被测对象，并按评测轮次创建新 manifest；同一轮中所有需比较的被测对象必须运行同一 manifest。同一对象的运行若没有相同的 manifest hash、数据 digest、评测器版本、DSH/model 配置与 runner 环境，结果标记为不可直接比较。这里的比较键只回答两份 Evolution 结果能否公平比较，不产生 promotion、rollback 或任何对被测对象的动作指令。
4. Final 只在被测对象冻结后的里程碑运行；题目、逐题 outcome、完整 session 和 manifest 不进入普通 workspace、Git、candidate store 或任何未来优化器输入。
5. 一个 manifest 内 case ID 必须唯一。Smoke 与 Evolution 共享同一开发题池，允许同一 case 出现在两层的 manifest 中；Final 的固定 30 题始终不得进入任一滚动 manifest。evaluator ledger 必须记录每份 manifest 的选择与审计重试；v0.7 不设置同层 case 的复用窗口，也不设置周期或新 manifest 预算。为公平比较或在 runner/evaluator 失效后审计重试，可对同一份既有 manifest 重复执行，但不得把该重试视为新抽题或新一轮反馈。

## 4. 数据保管与可见性

最终 30 题的 custody 继续遵循阶段 06：实际 ACL、独立账号、容器挂载或机器隔离是前置条件，`.gitignore` 和文档不构成访问控制。除 Final 外，evaluator custody 还保留 Simple、Moderate、Challenging 各 5 个 Query case 作为 reserve；reserve 不进入 Smoke 或 Evolution manifest，也不向开发侧暴露其身份。

滚动题单的选择器同样在 evaluator custody 执行。普通调用方最多取得当前已授权运行所需的 manifest 和受限结果，不取得完整 eligible pool，避免通过补集推断 Final case ID。原始 DSH session、GT、Gold SQL、Gold result、私有 dump、凭据和 data-root 路径永远不进入 stdout、Git、candidate store、`RunSubject` 或结果投影。Smoke 与 Evolution 的 session-log 按既有 run 目录的脱敏、保留和访问边界处理；本阶段不为它另设逐题公开投影 schema。

评测器保存的内部证据与对外结果分离：

| Suite | 内部 evidence | 默认结果投影 |
| --- | --- | --- |
| Smoke | 沿用既有 run 目录的脱敏 session-log 与 evidence | 沿用现有报告边界；本规格不新增逐题投影字段 |
| Evolution | 沿用既有 run 目录的脱敏 session-log 与 evidence | 沿用 Smoke 的报告边界，并附 tier 指标、macro-average 与比较键 |
| Final | custody 内完整受限 evidence | aggregate-only |

## 5. 非目标

- 不接入 coding agent、模型调用或自动 Skill 改写。
- 不新增 candidate 生成、谱系决策、自动 promotion、rollback 或 champion 选择。
- 不执行真实 DSH、真实模型、Docker fixture 或 baseline；这些均需要届时的新明确授权。
- 不增加 SQL dialect、第二 benchmark、并发、网络存储、云服务、依赖或 CI。
- 不删除或改变阶段 03 固定 smoke adapter、阶段 05 candidate store 或阶段 06 final held-out 的历史语义。
- 不将任何 Final 的 case identity、prompt、Gold、GT、逐题结果或 session 作为轮换输入、优化反馈或公开输出。

## 6. 技术约束与预期结构

继续使用 Python 3.11+、Typer、Pydantic、PyYAML、psycopg、pytest、ruff 与 mypy；所有模型严格 typed、冻结或不可变，所有子进程使用 argv 数组与 `shell=False`。

预期改动范围如下，具体文件由获准后的实施计划确定：

```text
src/skill_evolve/
  benchmark/     # RunSubject、rotation manifest、adapter 与分层报告
  runner/        # 只消费通用 RunSubject 的 workspace materialization
  attribution/   # 中性诊断，不输出 Skill 修改动作
  candidate/     # 后续仅作为到 RunSubject 的边界适配器
tests/           # manifest、custody、可比性、兼容性与 fake runner 测试
docs/specs/      # 本规格及索引
docs/plans/      # 规格批准后的实施计划
docs/design/     # 实现并验证后的设计记录
```

## 7. 验收标准

1. 原 `livesqlbench-base-lite` 和 Final adapter 的 ID、静态/私有输出语义保持兼容。
2. Smoke rotation manifest 恰有 5 个合格且唯一的 Query case，并符合当前轮次的难度配额；Evolution manifest 恰有 15 个，三层各 5 个；两者从同一开发题池抽取，允许跨层 case 重叠，但均不得与 Final 重叠。
3. Smoke 的 5 个 case 全部 `passed` 时才允许创建或执行该被测对象的 Evolution run；任一任务失败、runner 无效或 evaluator 无效都必须返回明确的 gate 结论，且不启动 Evolution。
4. rotation selector 拒绝不足题数、难度/类别/数据库元数据不符、缺少必要材料、symlink/路径逃逸、manifest 篡改、Final 重叠或复用策略违规的输入，且不留下部分 manifest。
5. 最终 30 题和完整 eligibility pool 不会通过 CLI、报告、普通 run root、Git、candidate store、subject binding 或优化器投影泄漏。
6. benchmark 核心不导入 candidate store；被测对象来源只经 `RunSubject` 边界绑定。
7. 同一 Evolution manifest 上的多个运行可生成相同 comparison key；不同 key 的运行明确标为不可直接比较。
8. 分层报告包含 tier 计数、成功率与 macro-average；原始不均衡样本数不取代 macro 指标。
9. 全部验证使用 fixture、stub/fake runner 和 no-model preflight；相关单元/CLI 测试及 `ruff`、`mypy`、`pytest` 在实施后通过。

## 8. 验证命令

在获准实现后，优先执行针对性、无模型的测试；未获真实运行授权时不启动 Docker、DSH 或模型。

```powershell
uv run pytest tests/test_benchmark_registry.py tests/test_livesqlbench_heldout.py
uv run ruff check .
uv run mypy src
uv run pytest
git diff --check
```

## 9. 已确认事项与开放问题

1. **Smoke 配额：**已确认使用三轮 `2/2/1` 轮换：`2/2/1`、`2/1/2`、`1/2/2`，随后重复配额模式但继续轮换实际题目。
2. **共享题池与 reserve：**已确认 Smoke 与 Evolution 从同一开发题池抽取，允许跨层 case 重叠；Final 固定 30 题始终排除在滚动题池之外。除 Final 外，custody 另保留 Simple、Moderate、Challenging 各 5 个 case 作为永不向开发侧暴露的 reserve。
3. **同层复用与预算：**v0.7 不设置 Smoke→Smoke 或 Evolution→Evolution 的复用窗口，也不引入“周期”或每周期新 manifest 预算；除单份 manifest 内唯一性、Final 排除和既有 manifest 审计重试外，不新增选择限制。
4. **逐题投影：**本阶段不新增投影字段设计，沿用现有 run 目录的 session-log/evidence 保管方式。Evolution 仍需提供 tier 指标、macro-average 与比较键；若未来优化器消费任何运行信息，必须由未来独立阶段定义其输入边界。
5. **开放问题：**当前没有阻止规格审阅的产品开放问题；实施细节在规格获准后进入计划阶段。

## 10. 边界

- **始终：**验证所有 manifest、路径和 runner 输出；保留 GT/Gold/credential/session 隔离；保留失败与 timeout 的脱敏审计证据；使用原子写入和 `shell=False`。
- **先询问：**真实 DSH/模型或 Docker 运行、改变 custody/ACL、增加依赖或并发、向任何 agent 发送评测证据、自动修改或选择 Skill、推送远端。
- **绝不：**执行或动态导入被测 Skill 内容；把 Final 数据或秘密写入 Git/stdout/candidate store/优化器输入；以高权限角色执行候选 SQL；连接生产数据库。
