# 规格：失败恢复窗口与 Skill 接触证据

> **阶段：**10 · **版本：**v0.8.2 · **状态：**已完成
>
> **前置阶段：**[阶段 09：Evolution 失败轨迹的依赖感知 Agent 投影压缩](09-v0.8.1-agent-projection-evidence-compression.md)

## 1. 目标

在保持 v0.8.1 的 custody、隐私与无业务根因判断边界的前提下，把 Optimizer 可见的失败证据从平铺的 `evidence[]` 提升为有界的**失败恢复 episode**。它让未来的 Coding Agent 能观察到：失败前可见的决策上下文、失败动作及直接错误、失败后的少量实际动作和其结果，以及 Agent 是否在失败前读取过当前被评测的 Skill。

成功意味着：同一份已脱敏 Evolution session、可信 subject 和固定 policy 总是得到字节稳定的 `evolution-coding-agent-input-v3`；每个可配对的 P0 工具失败都作为不可拆散的 evidence episode 输出。Optimizer 能比较失败与后续动作的实际差异，但规则层不宣称 Agent 的意图、错误已被修复、Skill 是否覆盖规则，或应如何修改 Skill。

## 2. 范围

### 2.1 v3 artifact 与兼容性

- 新增 `evolution-coding-agent-input-v3`；v1/v2 artifact 与 `dsh-trajectory-compressed-v1` 的读取和 custody 语义不变。
- Evolution 中继续只投影 `CaseEvaluation.passed == false` 的 case；Smoke 不产生逐题输入，Final 保持 aggregate-only。
- v3 不复原完整 session 步骤树。它只增加 P0 失败的局部、相对顺序关系，不输出 event type、seq、timestamp、call/result location、custody 路径或原始 session 索引。
- 每个 `failure_recovery_episode` 是 P0 不可拆分单元；其中的后续动作不再重复作为独立 SQL/tool evidence，除非它有独立的 P0 失败或 evaluator 关联。

### 2.2 Failure Context Window

每个已配对且具有直接失败证据的工具调用生成至多一个 episode：

```text
pre_failure_public_context   0–1 条公开 assistant 文本，最多 512 UTF-8 bytes
failed_action                1 个 action/result 对与既有 direct_failure
post_failure_public_context  0–1 条公开 assistant 文本，最多 512 UTF-8 bytes
post_failure_actions         最多 3 个后续 action/result 对，总 episode 最多 4 KiB
```

- `post_failure_actions` 按原始已配对调用的相对顺序选择；首个后续成功 action 出现即停止。若新的 P0 工具失败先出现，前一 episode 停止，新失败开始自己的 episode，避免一个 action 归属多个 episode。
- 每个后续动作只记录其既有受限 action、结构化结果、adapter 与 outcome。它叫作 `post_failure_action`，不得称为 `corrective_action`，除非已有直接、可验证的结构事实。
- episode 只可输出 `first_subsequent_success_observed`、`no_success_observed` 或 `truncated_before_success` 等观察状态；不得由“后续同工具成功”推断已恢复任务、已理解错误或完成根因纠正。
- `trace_state` 等没有可配对失败 call/result 的 P0 evidence 继续独立保留，不伪造恢复窗口。

### 2.3 Skill 身份、读取与规则摘录

v3 顶层保留当前被评测的完整、受限 `skill` 文本，并新增只标识该 subject 版本的 `evaluated_skill`：`subject_id`、`content_sha256` 与非敏感 schema/version 标识。该 hash 仅可指向随 payload 已交付的 Skill 内容；session、context、artifact 或 custody hash 仍不得进入 v3。

对于 session 内的 `read`，若其 target 或完整读取内容可由固定规则与当前注入的 subject 对应，输出有界的 `skill_access` 观察：

- `occurred_before_failure`：`observed`、`not_observed` 或 `unknown`；
- `subject_match`：`exact`、`declared_subject_path` 或 `unknown`；
- 可选 `rule_excerpt`：仅来自顶层 evaluated Skill 的一个有界段落，且必须具有可重放的确定性选择基础，例如精确 adapter 标识和来自可信 tool contract 的约束 signature。

无法可靠匹配时必须是 `unknown`/`not_determined`。没有摘录或没有观测到 read，绝不能被表述为“Skill 未覆盖该规则”。其他 schema/knowledge/column-meaning read 继续使用 v0.8.1 的直接引用选择和 fallback，不复制正文。

### 2.4 公开 assistant 文本降噪

- 移除全局、逐条的 `public_assistant_statement` evidence。
- 公开 assistant 文本只在 episode 的前后上下文中出现，或作为 `observed_result_claim` 保留：后者必须与紧邻的结构化 tool result 存在确定性的直接 token/value 对应。
- “Let me inspect/check/verify” 等无可验证结果关联的过程播报不输出。`observed_result_claim` 仍是 session-derived、untrusted text，不代表规则引擎认可其结论。

## 3. 非目标

- 不交付内部 reasoning、chain-of-thought，亦不从公开文本猜测 Agent 想法。
- 不让规则层判定 adherence/model problem、skill coverage problem、skill gap 或推荐改写内容。
- 不新增 SQL dialect、第三方 parser、网络、并发、模型调用、自动 Skill 修改、candidate promotion/rollback、CI 或远端推送。
- 不改变 evaluator verdict、candidate 生命周期、滚动评测 gate、Final custody 或 v1/v2 artifact。
- 不运行真实 DSH、模型、Docker、baseline、Evolution 或 Final；不把真实 case/session/逐题结果写入 Git、stdout 或 Optimizer 输入。

## 4. 技术约束与预期结构

沿用 Python 3.11+、Pydantic、pytest、ruff 与 mypy，不添加依赖。实现继续位于现有 trajectory 边界：

```text
src/skill_evolve/trajectory/
  contracts.py     # 严格冻结的 v3 contract
  projection.py    # episode、Skill access 与公开文本选择
  policy.py        # 窗口数目和字节上限
  agent_input.py   # v3 builder 与 subject provenance
tests/
  test_trajectory_projection.py
  test_trajectory_compression.py
  test_livesqlbench_rotation_run.py
```

使用严格、冻结的 Pydantic 合同和 `snake_case`：

```python
class FailureRecoveryEpisode(StrictTrajectoryModel):
    pre_failure_public_context: str | None
    failed_action: ProjectionEvidence
    post_failure_actions: tuple[ProjectionEvidence, ...]
    first_subsequent_success_observed: bool
```

具体字段名与 enum 在获批后的实施计划中确定；它们必须表达观察到的事实，不能表达模型意图或根因判断。

## 5. 测试与验收标准

1. 合成轨迹中的“读当前 Skill → 多 statement 失败 → 单 statement 成功”生成一个有界 episode；失败、直接原因、读前关系、后续 query 与成功结果均可见。
2. 随后的成功调用若不属于允许的窗口，或被新的 P0 失败截断，不被错误标为恢复；episode 选择对同一输入 byte-identical。
3. 完整读取的 active Skill、仅 target 匹配、无法匹配和未读取四种情形分别产生 `exact`、`declared_subject_path`、`unknown` 与 `not_observed`，且最后三种均不声称 Skill 缺失规则。
4. 任意无关的进度播报不生成全局 statement evidence；有直接 token/value 支持的公开结果主张才保留，并仍标为 untrusted。
5. v3 不含内部 reasoning、GT、Gold、凭据、原始 session/custody metadata、绝对路径或非 subject 的 hash；v1/v2 行为和 canonical bytes 不变。
6. 全部测试只使用合成 JSONL、stub runner、合成 Skill/context 和临时目录；不调用模型、DSH、Docker、网络或真实 benchmark 材料。

### 5.1 P1 修订：时序与规则关联

- 失败窗口以已配对失败 call 的 result location 为错误观测边界。由于 v1 的
  `CompressedStep.public_assistant_text` 不保存单条文本 location，同一 compressed
  step 的公开文本不得归入该 step call 的 pre/post context；只选严格更早或更晚
  step 的文本，宁缺毋错。
- 后续 action 必须在失败 result 后发生；在 result 前已发起但较晚返回的 call
  不能称为失败后的 action。
- `rule_excerpt` 必须同时匹配规范化的 failed adapter 与 direct failure cause；
  只命中其中一项时不输出摘录。无摘录不表达 Skill coverage/adherence 结论。
- 该确定性投影语义修订使用新的 projection rule version，schema 仍为
  `evolution-coding-agent-input-v3`，v1 custody canonical bytes 不变。

实施后的无模型验证命令为：

```powershell
uv run pytest tests/test_trajectory_compression.py tests/test_trajectory_projection.py tests/test_livesqlbench_rotation_run.py
uv run ruff check .
uv run mypy src
git diff --check
```

## 6. 边界

- **始终：**保持 Evolution/Smoke/Final 可见性隔离，使用固定 policy 和显式相对关系，将 session-derived 文本视为不可信，并保留失败证据。
- **先询问：**批准本规格、创建实施计划、修改 custody/ACL、引入依赖或 parser、扩大 SQL dialect、调用真实 Optimizer/模型、DSH、Docker、baseline、Evolution、Final 或推送远端。
- **绝不：**向 Optimizer 输出内部 reasoning、GT/Gold、私有 dump、凭据、原始 session、custody 路径/索引；让规则引擎给出 Skill 缺口、模型不遵守或自动改写 Skill 的结论。

## 7. 开放问题

无。窗口大小、停止规则与 Skill 读取不确定性均采用本规格中的保守默认值；若要扩大窗口、输出更多 Skill 段落或支持新的工具契约，必须先修改并批准本规格。
