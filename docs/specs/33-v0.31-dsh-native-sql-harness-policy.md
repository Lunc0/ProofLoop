# 规格：DSH 原生 SQL 工具与 SQL Harness Policy

> **阶段：**33 · **版本：**v0.31 · **状态：**已完成
>
> **关联阶段：**[阶段 03：DSH session 与 LiveSQLBench](../design/v0.3-dsh-session-and-livesqlbench.md)、
> [阶段 08：DSH 轨迹压缩](08-v0.8-dsh-trajectory-compression.md)和
> [阶段 12：Benchmark DSH 禁用 Web Search](12-v0.10-dsh-no-web-profile-patch.md)。

## 1. 目标

把 PostgreSQL benchmark 中通过通用 `pwsh` 调用 `sql-readonly.ps1` 的探索能力，替换为 DeepSeek
Harness（DSH）直接注册和调度的原生 `sql_probe`、`sql_submit` 工具；同时新增一个仅用于 SQL
benchmark 的受信任 DSH Harness Policy 插件，在第一次模型请求前收窄工具目录，并在运行时阻止确定性的
冗余或越界工具调用。

本阶段成功后，Skill 继续负责 SQL 语义指导，Harness Policy 则机械执行以下动作边界：模型只看到当前
任务需要的文件读取、内容搜索与 SQL 工具；成功的最终候选提交后，后续工具调用不能再执行，模型只能
输出 runner 现有合同要求的唯一 SQL fenced code block。

## 2. 范围与核心假设

本阶段包含两个按依赖顺序交付的能力：

1. **DSH 原生 SQL executor：**注册 `sql_probe` 和 `sql_submit`，复用现有
   `ReadOnlyQueryService` 与 disposable PostgreSQL fixture，不新增数据库访问路径。
2. **DSH SQL Harness Policy：**使用 DSH 的 Agent scoped tool restriction、pre/post execute 或 monotonic
   guard 执行工具白名单、精确重复调用防护和提交后的 finalize gate。

核心假设如下：

- DSH 版本继续由 manifest 固定；首个实现适配当前 `0.1.1-rc.2` 的 Cordis/tool runtime 合同。
- 插件是仓库内受信任、静态、可审计的 JavaScript ESM 文件，通过每次运行生成的 `--patch` overlay
  加载；不修改用户全局 DSH 安装、`$DSH_HOME/profiles/headless` 或已发布 DSH package。
- 插件不需要新增 npm 依赖；只使用 DSH 注入的 runtime 服务与 Node 内建能力。
- query endpoint 是 Harness 私有配置，不是模型可填写的工具参数；模型只能提交 SQL 字符串。
- `sql_submit` 成功表示“候选已在只读探索 fixture 上成功执行”，不表示 evaluator 判定正确。
- 第一版只阻止可确定证明的冗余行为，不使用 LLM、embedding 或模糊规则判断两个不同搜索是否语义等价。

## 3. 原生 SQL 工具合同

### 3.1 `sql_probe`

输入：

```json
{"query": "SELECT ..."}
```

行为：

- 只向 Harness 配置的 loopback `ReadOnlyQueryService` 发送一个 JSON POST 请求。
- 继续由现有 PostgreSQL executor 执行单 statement、只读、安全检查、行数和超时限制。
- 成功返回稳定 JSON：`ok`、`columns`、`rows`；受控失败返回不含 endpoint、凭据和内部异常原文的错误。
- 成功或失败后都不结束 Agent turn，模型可以依据结果继续分析。

### 3.2 `sql_submit`

输入与底层只读执行合同和 `sql_probe` 相同，但显式表示最终候选：

- 执行失败时返回受控错误，Harness 保持探索阶段，允许模型修正后重试。
- 执行成功时记录该 Agent 的最终候选 SQL，状态转为 `FINALIZE`，并在结果中要求模型输出该候选的唯一
  SQL fenced code block。
- `FINALIZE` 后任何工具调用都必须在执行前被拒绝；不得访问数据库、文件、shell、搜索或 delegation。
- 本阶段不直接用 tool result 代替 final assistant message，也不调用会让当前 runner 缺失
  `assistant/message` 的提前终止捷径。
- runner 仍从最终 assistant message 提取候选 SQL；若最终输出与最后一次成功 `sql_submit` 的规范化 SQL
  不一致，case 必须成为受控 `runner_error`，不能静默接受不同查询。

### 3.3 安全与兼容

- 不再向有 `database_access` 的 DSH workspace 写入 `sql-readonly.ps1`，任务说明改为原生工具协议。
- 没有 `database_access` 的通用 DSH run 不加载 SQL 工具或 SQL policy，保持现有行为。
- endpoint 必须是 Harness 生成的 loopback HTTP URL；非 loopback、包含 userinfo、非预期 path 或无效 URL
  在启动 DSH 前失败。
- 插件错误、patch 生成错误或 DSH 版本/工具合同不兼容必须 fail closed 为 runner error，不能回退到普通
  `pwsh` SQL 执行。

## 4. SQL Harness Policy 合同

### 4.1 初始工具目录

在 `agent/created` 同步阶段、第一次 prompt assembly 之前，对该 Agent 应用 allowlist：

```text
read
grep
sql_probe
sql_submit
```

`glob` 不进入首版 allowlist。Python workspace builder 已知并物化所有 task-visible 文件，因此 `TASK.md`
必须列出 `schema.sql`、可选 `subject/<filename>` 和当前 case 的全部 `context/NN-*` 精确相对路径。模型无需
再次发现文件。

`pwsh`、`bash`、`write`、`edit`、`read_image`、`glob`、Web、jobs、todo、goal、Skill discovery、subagent、
workflow 和 Ralph 等其他继承工具必须从该 Agent 的模型可见目录中移除。Policy 另注册 monotonic guard
作为纵深防护，不能由后续 listener 重新放行非 allowlist 工具。

工具目录在整段会话中保持稳定，以避免中途改变 DSH tool schema；进入 `FINALIZE` 后由 guard 拒绝调用，
而不是动态删除工具。

### 4.2 精确重复调用

Policy 按 Agent 保存已完成调用的 canonical key：工具名加深度排序后的 JSON arguments。

- 只有前一次完全相同调用成功完成时，下一次相同调用才被拒绝。
- 失败、取消或 timeout 的调用不进入成功缓存，允许精确重试。
- 不同 grep pattern、不同路径或不同 SQL 不判为重复。
- 被拒绝结果只能提示复用已有 observation，不复制无限长度的历史结果，也不虚构语义事实。

### 4.3 Finalize gate

- 仅一次成功的 `sql_submit` 能把状态从 `EXPLORE` 转为 `FINALIZE`。
- 状态按 Agent 隔离；并行或后续 case 不能共享工具历史或 final candidate。
- `FINALIZE` 后 guard 对所有工具返回稳定拒绝原因；拒绝事件继续进入 DSH session，供审计其是否发生。
- 若模型在拒绝后仍不产生合规最终消息，沿用 timeout/runner-error 语义，不能由 Harness 伪造答案。

## 5. 运行集成与证据

Python `DshRunner` 为每个带 database access 的 case 生成不可变的 run-scoped policy patch，内容只包括：

- 仓库内已固定并纳入 fingerprint 的插件入口；
- loopback query endpoint；
- 精确 task-visible resource 列表；
- 固定 allowlist 与 policy schema version。

patch 通过 argv array 和 `shell=False` 传给 DSH，并与现有 no-web patch、model-selection patch 保持确定顺序。
生成的 patch、插件内容 hash、policy schema/version 和最终候选绑定必须作为可审计 artifact 保存；不得保存
凭据或把 held-out prompt/GT 引入公开输出。

DSH session normalization、trajectory compression 和 optimizer-safe projection必须识别原生
`sql_probe`/`sql_submit`，保留二者的 intent 区别，同时复用现有 SQL query/result 脱敏和大小上限。历史
`pwsh -> sql-readonly` session 仍应可读取，不做隐式迁移。

## 6. 技术栈、项目结构与代码风格

Python 侧继续使用 Python 3.11+、Pydantic、PyYAML 和现有严格类型。DSH 插件使用最小 JavaScript ESM，
不引入 npm package、构建步骤或生成产物。

预期范围：

- `src/skill_evolve/runner/dsh.py`：workspace contract、run-scoped patch 和 runner binding。
- `src/skill_evolve/runner/dsh_plugins/`：静态 DSH SQL tool/policy ESM 资源。
- `src/skill_evolve/runner/contracts.py` 或专用严格模型：policy 配置与最终候选绑定。
- `src/skill_evolve/trajectory/`：原生 SQL tool 的标准化、压缩和投影兼容。
- `tests/test_dsh_runner.py`、`tests/test_dsh_session.py`、trajectory 定向测试：Python 合同。
- `tests/dsh/`：用 Node 内建 test runner 和 fake Cordis/tool runtime 测试插件，不连接模型或数据库。

外部输入先验证再写 patch；所有错误使用固定分类，不把 URL、响应 body、绝对路径或异常原文反馈给模型。

## 7. 测试与验证

实现和默认验证全部离线：

```powershell
uv run pytest tests/test_dsh_runner.py tests/test_dsh_session.py tests/test_trajectory_compression.py tests/test_trajectory_projection.py
uv run ruff check src/skill_evolve/runner src/skill_evolve/trajectory tests/test_dsh_runner.py tests/test_dsh_session.py
uv run mypy src
node --test tests/dsh/*.test.mjs
git diff --check
```

另使用当前已安装、manifest 固定版本的 DSH 执行一次无模型 `--dump-config`/synthetic plugin load 检查，证明
run-scoped patch 可加载、四个 allowlist 工具可见且无其他工具可见。该检查不得发起模型、数据库、Docker、
benchmark 或网络调用；环境没有兼容 DSH 时应明确报告未验证，不能伪造通过。

## 8. 验收标准

1. 带 database access 的 synthetic run workspace 不再包含 `sql-readonly.ps1`，DSH patch 注册
   `sql_probe`、`sql_submit`，两者的模型参数只有 `query`。
2. endpoint 不是模型参数，且非 loopback/非法 endpoint 在启动 DSH 前失败；插件和 runner 的错误输出不泄漏
   endpoint、绝对路径、响应 body 或凭据。
3. 第一次模型请求看到的工具目录恰好为 `read`、`grep`、`sql_probe`、`sql_submit`；现有普通 shell、写文件、
   discovery、delegation、goal 和 Web 工具不可见且不能执行。
4. `TASK.md` 列出当前 case 可见文件的精确相对路径；没有 context 或 subject 时不虚构路径。
5. `sql_probe` 成功不会结束探索；`sql_submit` 失败不会锁定；`sql_submit` 成功后所有后续工具调用在执行前
   被拒绝。
6. 最终 assistant SQL 与最后一次成功 submit 不一致、缺失或出现多个 SQL block 时受控失败；一致时继续走
   现有 evaluator，不把执行成功称为正确。
7. 成功的完全相同调用被拒绝；不同参数和前次失败的相同调用仍可执行；状态和缓存按 Agent/case 隔离。
8. session、compressed trajectory 和 projection 能区分 probe/submit；历史 `pwsh -> sql-readonly` evidence
   继续通过回归测试。
9. 没有 database access 的 DSH runner、fake runner、现有 no-web patch、模型选择与 benchmark evaluator 合同
   保持兼容。
10. 定向 pytest、Ruff、mypy、Node plugin tests、`git diff --check` 通过；无模型 DSH load check 有真实证据或
    被明确标记为环境未验证。

## 9. 边界

- **始终：**保持 disposable fixture、只读数据库角色、单 statement policy、argv array、`shell=False`、
  session redaction、候选 SQL 与 final message 的确定绑定。
- **先询问：**真实 DSH task/model、Docker、benchmark、并发工具调用、新 SQL dialect、新 npm 依赖、修改用户
  全局 DSH profile、自动 Skill/Harness 修改、版本号、commit 或 push。
- **绝不：**让模型提供 endpoint、通过 shell 回退执行 SQL、把 tool success 当 evaluator pass、由 Harness
  自动改写或伪造最终 SQL、在插件中读取 GT/expected query/credentials，或把 held-out 私有内容写入 Git、
  stdout、candidate store、optimizer input。

## 10. 非目标

- 不在本阶段让 optimizer 生成、选择、编辑或晋级 Harness Policy。
- 不修改现有 `SKILL.md` 内容或候选存储 schema。
- 不做语义相似 grep、resolved-fact 推断、embedding cache、模型式 tool-call judge 或自适应预算。
- 不新增通用 MCP server、远程 SQL service、第二数据库 dialect、并发 SQL 或跨 case observation cache。
- 不保证减少工具数一定提高 SQL 正确率；正式效果必须在后续获得授权的可比 A/B benchmark 中验证。

## 11. 开放问题

无。版本确定为 `v0.31`；无模型 DSH load check 是本阶段必须完成的本机验收。
