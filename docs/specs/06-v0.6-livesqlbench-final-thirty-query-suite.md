# 规格：LiveSQLBench Base-Lite 三十题最终 Held-out 评测集

> **阶段：**06 · **版本：**v0.6 · **状态：**已完成；首次真实 baseline 待新的明确授权
>
> **对应计划：**[实施计划](../plans/06-v0.6-livesqlbench-final-thirty-query-suite.md)

**目标版本：**v0.6（项目包版本保持不变）。

## 1. 目标

在保留 `livesqlbench-base-lite` 五题快速 smoke suite 的前提下，新增一个固定的、可复现的
LiveSQLBench Base-Lite Query-only 三十题最终 held-out 评测集。它只用于候选 Skill 版本冻结后的最终
评测，不能作为自进化 coding agent 的输入、调试数据或后续修改依据；按当前每题约 2--5 分钟的串行成本，
预计一次运行约 60--150 分钟。

## 2. 已确认范围

1. 数据源仅为本机已导入并严格验证的 LiveSQLBench Base-Lite 数据；只选择 `category = "Query"`
   的 SELECT-only 题目。
2. suite 固定包含三十个唯一 `instance_id`：`Simple`、`Moderate`、`Challenging` 各十题。
3. 题目选择只依据公开记录字段：`instance_id`、`selected_database`、`difficulty_tier`、公开 schema/context
   和公开 `conditions.order`；不得以 Gold SQL、GT test cases、Gold 结果或私有 dump 作为选择依据或提交物。
4. 三十题与既有五题 smoke suite（`alien_2`、`polar_10`、`gaming_1`、`archeology_5`、`cross_db_8`）完全不重叠。
5. 三十题的实际 ID 清单、各题 session log、逐题 outcome 和运行 artifacts 由独立 evaluator custody 保管，
   不进入 Git、repo data root、candidate store、candidate workspace 或优化 agent 的输入。对 optimizer 来说，
   held-out run 只可在版本冻结后由人类读取聚合结果，且结果不得触发下一轮 Skill 改写。
6. 通过显式注册的新 adapter ID
   `livesqlbench-base-lite-query-final-v1` 运行：

   ```text
   uv run skill-evolve benchmark run livesqlbench-base-lite-query-final-v1 <data-root> <dsh-manifest> --candidate <candidate-id>
   ```

7. 每题仍使用独立、可销毁 PostgreSQL fixture；DSH 仅得到该题公开 prompt/schema/context、已验证的
   `candidate/SKILL.md`（如指定）和既有本地只读 SQL capability。Soft-EX、只读查询、timeout/nonzero-exit
   的脱敏 session evidence 语义保持不变。
8. 评测器通过非秘密环境变量 `SKILL_EVOLVE_HELDOUT_ROOT` 定位独立的本地 custody root。该 root 不在仓库
   内，也不在 `.local/skill-evolve/` candidate store 内；未设置、不可解析或权限不符合要求时必须 fail closed。

## 3. 选择规则与公开合同

三十个 ID 的清单是 evaluator-owned 的本地、不可变 manifest，不是仓库代码拥有的静态 tuple；其路径、内容和
由其推导出的 case 身份不得通过 optimizer 的 workspace、CLI stdout、run report 或 Git 泄漏。manifest SHA-256
只可作为 evaluator 的安全聚合标识出现在初始化 receipt 与 held-out public result，不能成为 optimizer feedback，
也不得写入 Git。不提供 `--limit`、随机 seed、按难度动态筛选或从数据目录加载 Python/插件的入口。evaluator
加载时必须逐项验证：ID 在 public 与 GT bundle
都存在、公开类别和难度符合 manifest、所需 context/dump 均存在、并且所有数据路径仍在给定 `data-root` 内。

选择时优先覆盖不同 `selected_database`、并在每个难度中包含不同 `conditions.order` 情况；同一数据库的
重复数量必须在设计记录中如实列出。这样难度分层不会被单一 schema 或业务域主导。

held-out fingerprint 与 evaluator evidence 必须绑定：新 adapter ID、仅以安全聚合形式公开的 manifest hash、私有 evaluator
输入的现有 digest 边界、DSH/model 配置以及 candidate ID/SHA-256。对人类的最终报告只可输出候选身份、
总题数、三个 tier 的聚合分数、macro-average、总耗时和成本；不得在 stdout、run result、report 或任何
optimizer feedback 中写入 case ID、prompt、Gold SQL、GT test case、Gold result、私有 dump、凭据或未脱敏
session log。

结果除了原有安全的逐题 outcome 外，增加按 `Simple`、`Moderate`、`Challenging` 的通过计数和通过率，以及
三个 tier 等权的 macro-average；不得让 Moderate 的原始题数或某个数据库重复次数主导总分。

## 4. 非目标

- 不自动运行真实 DSH 或模型；首次无 Skill baseline 只能在实现、静态验证和 evaluator custody 配置完成后，
  由维护者再次明确授权后运行。
- 不实现自动 Skill 改写、自动 candidate promotion/rollback、早停、轮换开发分片或并发。
- 不新增 SQL dialect、第二数据集、依赖、CI、云存储或 DBHub MCP。
- 不移动、复制、提交或输出 LiveSQLBench GT、Gold、私有 dump、凭据、held-out manifest、held-out case ID、
  prompt、逐题 outcome 或 session 原文。
- 不修改现有五题 adapter 的 ID、选题、CLI 行为或既有 evidence 语义。

## 5. 技术基础、命令与代码风格

继续使用 Python 3.11+、Typer、Pydantic、PyYAML、psycopg、pytest、ruff 和 mypy，不增加依赖。新增选择
manifest 必须是严格 typed 的本地数据模型，使用 `snake_case`；不以未验证的 `dict[str, Any]` 保存 suite
状态，也不得从 manifest 动态 import 或执行代码。

验证命令：

```text
uv run skill-evolve benchmark validate livesqlbench-base-lite-query-final-v1 <data-root>
uv run skill-evolve benchmark fixture-check livesqlbench-base-lite-query-final-v1 <data-root>
uv run ruff check .
uv run mypy src
uv run pytest
git diff --check
```

预期改动位于 `src/skill_evolve/benchmark/`、`src/skill_evolve/cli.py`（若 adapter registry 已自动暴露则不改
CLI 解析）、`tests/`、`docs/specs/`、`docs/plans/` 与 `docs/design/`。所有 subprocess 继续使用 argv
数组与 `shell=False`。

## 6. 验收标准

1. 新 adapter 可被静态 registry 发现，旧 `livesqlbench-base-lite` 行为不变。
2. 新 suite 恰有三十个 Query case，每个难度恰十个，与 smoke 五题没有交集，并满足固定数据库覆盖规则；
   manifest 只在独立 evaluator custody 中可读。
3. 数据不完整、ID/类别/难度不匹配、dump/context 缺失、路径逃逸或不可信输入时，在启动 Docker、DSH 或模型前
   fail closed。
4. 新 adapter 的 fixture、runner、candidate 注入、Soft-EX 评测、超时/非零退出 session evidence 均复用
   已有安全边界；所有公开输出仍无 GT/Gold/秘密。
5. held-out report 只可报告 tier 计数、tier 成功率和 macro-average；fingerprint 可区分五题与三十题 suite，
   但不得暴露 case ID 或逐题结果。
6. 新增和现有相关测试覆盖静态选择、注册、公共指标、兼容性与数据校验；全部项目检查通过。

## 7. 实施前置条件与待确认事项

1. `.gitignore` 不是访问控制。维护者必须在运行前为 `SKILL_EVOLVE_HELDOUT_ROOT` 配置独立的操作系统权限、
   容器挂载或机器，使未来 optimizer 无法读取 manifest、held-out run artifacts 和本机公开数据根。
2. 首次 baseline 定义为相同模型、相同 held-out manifest、**不传 `--candidate`** 的一次 run；它需要在
   代码和本地 custody 配置完成后再次明确授权。DBHub 原始 candidate 的三十题 run 是独立、额外成本的后续
   实验，不包含在本阶段的自动工作中。
