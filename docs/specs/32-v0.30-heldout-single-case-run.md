# 规格：Held-out 单题诊断运行

> **阶段：**32 · **版本：**v0.30 · **状态：**已完成
>
> **关联阶段：**[阶段 06：Base-Lite 三十题最终 Held-out 评测集](06-v0.6-livesqlbench-final-thirty-query-suite.md)，以及 [阶段 31：Benchmark Runner Error 计为错题](31-next-runner-error-as-incorrect.md)。

## 1. 目标

为 evaluator 操作者新增一个显式的 held-out 单题诊断入口。操作者提供 held-out manifest 中的精确
`instance_id` 后，系统只向模型提交这一题，只启动这一题需要的只读 fixture，并把完整运行证据保留在
held-out custody 的独立 `single-runs/` 目录。

成功实现后，单题诊断可以用于复现和排查某一题的 runner、模型或 SQL 行为，而不必再次运行三十题
Final suite。单题结果必须明确标记为诊断结果，不能被解释为 Final 分数或 candidate 晋级证据。

## 2. 用户入口与命令合同

新增独立命令，避免把 case 选择能力扩散到普通 benchmark、Smoke、Evolution 或三十题 Final 命令：

```powershell
uv run skill-evolve benchmark run-heldout-case `
  <data-root> `
  <dsh-manifest> `
  --case <instance-id> `
  [--candidate <candidate-id>]
```

- `--case` 必须与当前已校验 held-out manifest 中恰好一个 `instance_id` 完全一致。
- 不接受题目 prompt、序号、模糊名称、数据库名、通配符、逗号列表或多个 `--case`。
- 不新增 `--all`、批量选择或随机选择；三十题 Final 继续使用既有 `benchmark run`。
- candidate 仍为可选；只有显式传入 `--candidate` 时才注入已验证的本地 candidate。
- 选择失败必须在启动 fixture、DSH 或模型前退出，且错误信息不得枚举或回显 held-out case 列表。

## 3. 产物目录与命名合同

当 `SKILL_EVOLVE_HELDOUT_ROOT=D:\skill-evolve-evaluator\heldout` 时，单题运行目录必须是：

```text
D:\skill-evolve-evaluator\heldout\single-runs\<UTC时间戳>-<instance_id>\
```

时间戳格式沿用现有 run 风格 `YYYYMMDDTHHMMSSZ`，例如
`20260910T012345Z-credit_8`。`instance_id` 已受 held-out manifest 的安全标识符校验约束，不允许路径
分隔符、`..`、空格或任意自由文本。目录必须以不可覆盖方式创建；同名冲突时 fail closed，不能复用、
清空或覆盖旧运行。

`single-runs/` 必须是已解析 custody root 的直接子目录，拒绝 symlink、junction/reparse point、路径逃逸
或与 repository/candidate store 的重叠。现有三十题结果继续写入 `heldout/runs/`，两者不得混用。

每个单题目录复用现有 held-out custody evidence 结构，包括环境指纹、run metadata、subject binding、
DSH invocation/model-selection artifact、脱敏日志、runner output、evaluation、attribution、result 与 report；
metadata 必须额外标记 run mode 为 `single_case_diagnostic`。完整 prompt、candidate SQL、逐题 verdict 与
原始 runner/session 证据只允许留在该 custody 目录。

## 4. 结果语义与公开边界

单题运行只产生一个 `CaseEvaluation`：

```text
exact case selection
  -> one-case fixture
  -> one DSH/model invocation
  -> one case evaluation
  -> custody-only diagnostic evidence
```

- runner 成功时沿用现有 Soft-EX evaluator；受控 `RunnerError` 沿用阶段 31 的脱敏错题语义。
- fixture/Gold/evaluator 无效仍 fail closed，不能改算为模型错题。
- 单题结果不得伪造三档 tier 分数、macro average、30 题分母、Smoke gate 或 Final score。
- stdout 只输出不含 case identity、prompt、GT、candidate SQL、逐题 verdict、session、凭据和 custody
  绝对路径的最小诊断 receipt；详细结果由 evaluator 在 custody 中查看。
- 单题 evidence 不进入 optimizer 输入，不创建、选择、晋级或回退 candidate，也不改写 held-out manifest。

## 5. 技术栈、项目结构与代码风格

沿用 Python 3.11+、Typer、Pydantic、PyYAML、psycopg、`uv` 和现有 PostgreSQL fixture/DSH runner；
不新增依赖、SQL dialect、并发或后台任务。

预期代码范围：

- `src/skill_evolve/cli.py`：新增独立 `benchmark run-heldout-case` 命令。
- `src/skill_evolve/benchmark/livesqlbench_heldout.py`：提供严格的单题精确选择和
  `single-runs` custody 子目录合同。
- `src/skill_evolve/benchmark/livesqlbench_heldout_run.py`：复用单 case 执行函数，新增单题 evidence
  与诊断 receipt 写入，不改变三十题 loop 的行为。
- `tests/test_livesqlbench_heldout.py`：使用 synthetic suite、stub fixture 和 fake DSH runner 覆盖命令、
  选择、调用次数、目录命名、隔离、失败及泄漏边界。
- `docs/heldout-evaluator.md`：在实现完成后记录操作方式与“非正式分数”限制。

代码继续使用严格类型与 `snake_case`，所有外部输入先验证再产生副作用。示例接口形状：

```python
def select_heldout_case(
    suite: HeldOutLiveSQLBenchSuite,
    instance_id: str,
) -> LiveSQLBenchCase:
    """Return one exact manifest-bound case or fail without listing identities."""
```

## 6. 测试策略与验证命令

只使用测试内 synthetic held-out 数据、stub fixture 和 fake runner；本阶段实现与验证不启动真实 Docker、
DSH、模型、数据库或 benchmark。

```powershell
uv run pytest tests/test_livesqlbench_heldout.py tests/test_benchmark_cli.py
uv run ruff check src/skill_evolve/benchmark/livesqlbench_heldout.py src/skill_evolve/benchmark/livesqlbench_heldout_run.py src/skill_evolve/cli.py tests/test_livesqlbench_heldout.py tests/test_benchmark_cli.py
uv run mypy src
git diff --check
```

重点测试：精确命中与未知 case、只调用一次 DSH、只建立一个数据库 fixture、candidate/no-candidate、
runner error、fixture invalid、时间戳目录、不可覆盖、symlink/path escape、三十题 `runs/` 不受影响，以及
stdout/公开 receipt 不含私有 case identity、prompt、GT、SQL、路径或异常原文。

## 7. 边界

- **始终：**先验证 custody、manifest、data digest、DSH manifest、model binding、candidate 和精确 case；
  只执行一个 case；以不可覆盖方式保存证据；保持 argv array 与 `shell=False`。
- **先询问：**真实模型/DSH/数据库运行、Docker、版本号、SQL dialect、并发、自动 Skill 修改、真实 held-out
  单题内容的终端展示，以及任何远端提交或推送。
- **绝不：**枚举 held-out case、接受 prompt 代替 ID、打印 GT/Gold/完整日志/凭据/custody 路径、把单题
  结果称为 Final 分数、让单题结果进入 optimizer/gate，或覆盖历史运行。

## 8. 验收标准

1. 操作者使用精确 `--case <instance-id>` 后，fake DSH runner 恰好被调用一次，run input 恰好包含该题，
   且其他 29 题不启动 fixture、runner 或模型。
2. 单题 evidence 只写入 `<heldout-root>/single-runs/<UTC时间戳>-<instance_id>/`；既有
   `<heldout-root>/runs/` 不创建或不新增目录，普通 workspace `runs/` 不写入。
3. 运行目录名只由标准 UTC 时间戳、连字符和 manifest 绑定的安全 `instance_id` 组成；任何冲突、链接、
   路径逃逸或 unsafe ID 均在写 evidence 前失败。
4. 未知或不在当前 manifest 的 ID 在任何 fixture/DSH/模型副作用前失败，错误不枚举有效 ID。
5. 单题完整 evidence 可在 custody 中审计；stdout/公开 receipt 不包含 case identity、prompt、GT、
   candidate SQL、逐题 verdict、原始异常、session、凭据或 custody 绝对路径。
6. 单题结果带有明确 `single_case_diagnostic` 标记，不生成 Final tier/macro score、Smoke gate、optimizer
   输入或 candidate 生命周期动作。
7. 现有三十题 held-out 命令、结果 schema、目录与计分行为保持兼容；相关离线回归测试通过。
8. 定向 pytest、Ruff、mypy 与 `git diff --check` 通过；没有执行真实 Docker、DSH、模型、数据库、
   benchmark 或网络调用。

## 9. 非目标

- 不提供 held-out case 列表、搜索、自动补全、模糊匹配或 prompt 预览。
- 不提供多题子集、重试队列、并行执行、批量回放、历史迁移或单题间比较报告。
- 不改变 Final manifest 选题、GT/Gold、Soft-EX evaluator、runner-error 计分或 DSH session 根配置。
- 不把单题诊断结果用于优化、训练、自动选 Skill、自动晋级或正式 benchmark 报告。
- 不在本阶段执行用户尚未指定题目的真实单题运行。
