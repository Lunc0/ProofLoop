# 规格：Codex Coding Agent 原子 Skill 编辑路径

> **阶段：**29 · **版本：**v0.27 · **状态：**已完成

## 目标

在现有 DeepSeek advice → EditPlan → materialize optimizer 之外，新增一条显式、并行存在的 Codex Coding Agent 路径。该路径把经过投影和脱敏的失败 evidence、parent `SKILL.md` 与只用于定位和权限判断的 SkillMap 交给 Codex CLI；Codex 直接产出完整的新 `SKILL.md` 和原子 edit 声明，系统随后完成来源绑定、确定性重放、权限校验和候选物化。

该阶段的成功标准不是证明修改在 benchmark 上更好，而是证明：coding agent 只能看到获准输入，只能写指定输出目录，其声明的每个 edit 都可独立应用到同一个 parent，全部 edits 的重放结果与完整输出逐字节一致，且现有 optimizer 路径没有被替换或改变默认行为。

## 已确认决策与前提

- Agent 固定为 Codex CLI，通过 `codex exec` 子进程调用，并复用主机上预先完成的 `codex login`。
- 使用细粒度 permission profile；不把普通 `--sandbox workspace-write` 当作 `input/` 只读、`output/` 可写的充分保证。
- 每次调用使用独立临时工作目录；系统不隐式采用默认共享临时目录，而是要求操作者显式提供与项目、candidate store 和 held-out custody 不重叠的专用受控根目录。该专用根可由管理员建立在受控临时卷中。
- agent 沙箱内的 shell、Web Search 和 MCP 网络访问全部关闭，且 approval policy 固定为 `never`。Codex CLI 控制进程仍可使用既有认证访问 Codex 模型服务；这不赋予 agent 执行的命令任何网络权限。
- 第一版只支持 `replace_block`，每次至少 1 个、至多 3 个 edit。
- 系统生成一个包含全部 edits 的 full candidate，以及每个 edit 单独应用到同一 parent 的 singleton candidate；第一版不生成 leave-one-out 候选。
- coding agent 是新路径。既有 DeepSeek advice、EditPlan、renderer、materialize 和 `evolution cycle` 默认路径继续保留。

## 范围

### 1. 显式的新入口

新增独立命令，不复用或重定义现有 `optimizer advise`、`optimizer plan` 和 `optimizer materialize` 的含义：

```powershell
uv run skill-evolve optimizer agent-edit <run-id>
uv run skill-evolve optimizer agent-materialize <run-id> --candidate-name-prefix <prefix>
```

`agent-edit` 只允许读取已完成且可优化的 Evolution run，调用一次 Codex CLI，并完成 agent 输出验证与 bound edits 发布。`agent-materialize` 不调用模型或 benchmark，只从已验证的 bound edits 生成 draft candidates。

现有 `uv run skill-evolve evolution cycle ...` 在本阶段不调用这两个命令背后的服务，也不新增隐式 backend 切换。

### 2. Agent 工作目录与输入

每次 `agent-edit` 创建全新的工作目录，至少包含：

```text
<workspace>/
  input/
    SKILL.md
    skill-map.json
    evidence.json
    manifest.json
  output/
```

`manifest.json` 是系统生成的非秘密闭集清单，绑定 run ID、parent candidate ID、parent Skill SHA-256、SkillMap SHA-256、evidence bundle SHA-256、允许引用的 evidence IDs、schema 和 policy 版本。它不得包含 held-out case ID、prompt、GT、逐题结果、原始 session、凭据或 custody 路径。

`evidence.json` 只包含现有公开投影边界允许的失败 evidence。输入复制完成后，系统记录 `input/` 内每个文件及输入集合的 SHA-256。

### 3. Permission profile 与进程边界

系统通过固定 CLI config overrides 注入并校验专用的细粒度 permission profile，其可观察权限结果必须是：

- workspace 根目录默认只读；
- `input/` 和 `.codex/` 只读；
- 只有 `output/` 可写；
- 不把 repository、runs root、candidate store、held-out、GT、custody 或其他进化代的 workspace 加入可读/可写根；
- agent shell 不能在 workspace 之外读写；
- agent shell 和 Web Search 不得联网；
- 不加载用户或仓库的 instruction files、MCP servers、plugins 或 skills；
- 不允许 approval、权限提升或 sandbox fallback。

启动器必须使用 argv 数组和 `shell=False`，设置 workspace 为进程工作目录，使用 ephemeral session，并传入忽略用户配置、忽略规则、跳过 Git 仓库要求、禁用 Web Search 和禁止 approval 的固定参数。启动器必须传递最小环境变量集合；认证只能通过 Codex CLI 既有认证位置复用，不能复制到 workspace、run artifacts 或 candidate store。

permission profile 或 Codex CLI 版本不支持上述权限时，调用必须 fail closed；不得退回普通 `workspace-write` 后继续执行。

### 4. Agent 正式输出

Codex 必须直接写入：

```text
output/SKILL.md
output/atomic-edits.json
```

stdout、stderr、JSONL 事件和自然语言成功声明均为不可信诊断信息，不可替代正式文件，也不可决定成功状态。诊断输出不得直接回显到公开 CLI；如保留，只能作为本地、受限、标记为 untrusted 的 run artifact。

agent 返回的声明采用 `atomic-skill-edit-declaration-v1`：

```json
{
  "schema_version": "atomic-skill-edit-declaration-v1",
  "edits": [
    {
      "operation": "replace_block",
      "target_block_id": "b1.2",
      "replacement_markdown": "## Validation\n...\n",
      "hypothesis": "要求提交前验证所有引用列存在",
      "evidence_refs": ["evidence-001-acde12345678"]
    }
  ]
}
```

每个 edit 必须引用至少一个属于本次 evidence 闭集的 ID。`hypothesis` 只用于审计和实验解释，不作为语义正确性证明，也不参与 renderer 决策。

### 5. 系统绑定的原子 edits

系统不得信任 agent 自行提供 parent hash、before hash、source range 或 edit ID。验证通过后，系统按声明顺序分配 `edit-001`、`edit-002` 等 ID，并发布 `atomic-skill-edits-v1`。每个 bound edit 至少包含：

- `edit_id`；
- `operation`；
- `target_block_id`；
- 原 parent 上的半开字节区间 `[resolved_start_byte, resolved_end_byte)`；
- 区间原始字节的 `expected_before_sha256`；
- `replacement_markdown` 与 `replacement_sha256`；
- `hypothesis`；
- `evidence_refs`。

顶层 source binding 至少包含：

- run ID 与 parent candidate ID；
- `parent_skill_sha256`；
- `skill_map_sha256`；
- `evidence_bundle_sha256`；
- block locator policy version；
- atomic replay policy version；
- Codex invocation receipt 的安全摘要绑定。

SkillMap 在该路径中只负责 block 定位、层级和 permission，不携带 defect cluster、functional module、structured rule 或 behavior assertion。`target_block_id` 只在被 parent Skill hash、SkillMap hash 和 locator policy 共同绑定时有意义。

### 6. 确定性验证与重放

系统在接受输出前必须按顺序完成：

1. 重新读取并校验 parent candidate、run subject 和输入 manifest 的 ID/hash 绑定。
2. agent 结束后重新计算整个 `input/` 集合的 hash；任一字节变化均拒绝本次结果。
3. 要求两个正式输出均为普通文件，位于真实 `output/` 下，不是 symlink、junction、reparse-point escape 或其他目录的硬链接别名。
4. 校验 `SKILL.md` 是 UTF-8、无 BOM、无 NUL，并保持 parent 的换行约定；系统不得在比较前自动格式化或标准化 Markdown。
5. 严格解析 declaration，拒绝未知字段、重复 edit、未知 operation、空 replacement、超出数量/字节预算、未知 evidence ref 和敏感内容。
6. 从本次 parent 重建 SkillMap，并校验 map hash 与 policy version。
7. 将每个 `target_block_id` 解析成原 parent 上的精确字节区间，并计算 before hash。
8. 拒绝 locked target、包含 locked 后代的祖先替换，以及当前安全策略禁止的 guarded/结构边界修改。
9. 拒绝重复 target、祖先/后代覆盖和任何字节范围重叠。所有 edit 必须只引用原 parent 中已有内容，不能依赖另一个 edit 新建的内容。
10. 将每个 edit 单独应用到同一个 parent，确认产生结构合法且非空变更的 Skill。
11. 将全部 edits 按原 parent 字节位置倒序应用，并要求结果与 `output/SKILL.md` 原始字节完全一致。
12. 生成并精确重放 full patch 与每个 singleton patch；任何不一致均拒绝全部 bound artifacts。

步骤 11 的字节等价同时证明完整 Skill 不包含 edits 未声明的变化。机械验证不证明 hypothesis 与 evidence 在语义上相关，也不证明 benchmark 会改善。

### 7. Run artifacts 与失败语义

coding-agent 路径使用独立 artifact namespace，不覆盖既有 `optimizer`、`optimizer_edit_plan` 或 `optimizer_materialization` 结果：

```text
runs/<run-id>/optimizer/coding-agent/
  invocation-receipt.json
  raw-output/
    SKILL.md
    atomic-edits.json
  bound/
    atomic-edits.json
    full.patch
    singleton-edit-001.patch
  receipt.json
```

只有全部验证通过后才能发布 `bound/`。缺失输出、进程失败、超时、输入篡改、权限配置无效、声明无效、locked 冲突或 replay 不等价都产生固定、非敏感 error code，并且不得创建 candidate。

临时 workspace 在安全输出复制、hash 校验和 receipt 发布完成后销毁。系统只接受 `raw-output/` 中由受控复制得到的两个正式文件，不从 stdout 恢复或补造文件。

### 8. Candidate 物化与血缘

`agent-materialize` 只接受状态为 validated 的 bound artifacts。它在写入任何 candidate 前校验全部候选名称、parent、patch 和 Skill 字节，并生成：

```text
<prefix>-full
<prefix>-edit-001
<prefix>-edit-002
<prefix>-edit-003
```

实际 singleton 数量等于 edit 数量。full candidate 应用全部 edits；每个 singleton 只把对应 edit 应用到同一个 parent。所有候选均为 immutable draft sibling，共享 parent candidate ID 和 source run ID；不得自动 select、benchmark、promote，也不得自动成为下一代 parent。

新增独立的 coding-agent provenance 合同，不把 atomic edits 伪装成历史 `OptimizerProvenance.edit_plan_sha256`。provenance 至少绑定：

- parent Skill、SkillMap、evidence bundle 与 bound atomic-edits hash；
- full 或 singleton 的 candidate role；
- singleton 对应的 `edit_id`；
- candidate Skill 与 patch hash；
- locator/replay policy version；
- 非秘密的 Codex CLI/model/invocation 标识。

candidate store 继续从每个最终 `SKILL.md` 生成并验证 candidate-owned SkillMap；coding-agent workspace 中的 parent SkillMap 不能直接复制成 child SkillMap。

## 非目标

- 不删除、替换、迁移或重解释现有 DeepSeek advice、EditPlan、renderer 和 materialization artifacts。
- 不在本阶段把 coding-agent 路径接入现有自动 `evolution cycle`。
- 不支持 `add_block`、`insert`、`delete_subtree`、原文片段定位、行级 patch 或依赖前一 edit 输出的串行 edits。
- 不生成 leave-one-out、edit 组合搜索或自动归因结论。
- 不自动运行真实 Codex、DSH、Docker、数据库 fixture、benchmark、selection、promotion 或 retirement。
- 不让 coding agent 访问 held-out、GT、custody、candidate store、repository、完整 session 或逐题 outcome。
- 不验证 edit 的语义正确性、evidence 相关性或 benchmark 改进。
- 不允许 agent 自行调用第二个 agent、MCP、plugin、Skill 或网络搜索。

## 技术与安全约束

- Python 3.11+、Pydantic strict/frozen contracts、Typer、`uv` 和现有 candidate/run store 约定继续适用。
- 所有 subprocess 使用 argv 数组和 `shell=False`，超时后终止完整进程树，不执行 agent 返回的命令文本。
- repository、held-out custody、candidate store 与 agent workspace 必须经过 realpath、祖先/后代、symlink/junction/reparse point 和重叠检查；路径关系不安全时 fail closed。
- agent 输入、输出、stdout 和 stderr 都是不可信内容；路径、JSON、大小、编码、hash 和敏感文本必须由系统重新验证。
- agent 正式输出和 bound artifacts 都有显式大小上限；不得依赖 provider token usage 推断缺失成本。
- 旧路径默认行为和已有 persisted artifacts 必须保持可读、可 materialize；新路径不得要求历史数据迁移。
- 测试只能使用 fake subprocess/fixture；任何真实 Codex 调用都需要单独、当次授权。

## 项目结构

预期按职责新增独立模块，确切文件拆分在规格批准后的 plan 中确定：

```text
src/skill_evolve/optimizer/coding_agent/  # launcher、workspace、contracts、binding、replay
src/skill_evolve/candidate/               # 新 provenance 与批量物化边界
src/skill_evolve/cli.py                   # 两个显式新命令
tests/                                    # fake CLI、权限、绑定、重放、候选生命周期测试
docs/plans/                               # 规格批准后创建阶段 29 计划
docs/design/                              # 实现与验证完成后创建阶段 29 记录
```

新模块不得通过条件分支侵入既有 DeepSeek client 或把 `EditPlan` schema 扩展成双重含义；共享的 hash、Markdown parser 或 candidate store 能力可以复用，但入口、contracts、artifact namespace 和 receipts 必须可区分。

## 验收标准

1. 现有 optimizer 三个命令与 `evolution cycle` 默认控制流、配置和 artifacts 保持不变；新命令使用独立 service、contract、receipt 和 artifact namespace。
2. 生成的细粒度 permission profile 使 `input/` 只读、`output/` 可写，workspace 外项目和私有根不可访问；能力不支持时 fail closed，不回退普通 `workspace-write`。
3. Codex CLI 使用独立 workspace、ephemeral session、禁止 approval、禁用 Web Search/MCP/plugin/Skill，并且 agent shell 无网络；认证不进入任何 artifact。
4. agent 结束后输入 hash 必须保持一致；输入篡改、软链接/目录逃逸或输出别名均被拒绝。
5. 系统只从 `output/SKILL.md` 和 `output/atomic-edits.json` 判断正式结果，stdout 的成功声明不能绕过文件或验证失败。
6. declaration 只允许 1–3 个 `replace_block` edits；系统本地生成 ID、字节范围、before/replacement hash 和 source binding。
7. 未知 block/evidence、before hash 不符、重叠或父子覆盖、locked/安全边界修改、空变更和结构无效均 fail closed。
8. 每个 edit 都能独立应用到相同 parent；全部 edits 的确定性重放结果与 agent 完整 Skill 逐字节相等，full/singleton patch 均可精确回放。
9. validated run 可显式生成一个 full 和 N 个 singleton immutable draft siblings；它们拥有独立 coding-agent provenance，且不会自动评测、选择、晋升或继续进化。
10. invalid agent output 在任何 candidate 写入前被拒绝；receipt 只保存固定非敏感状态/error code，不把私有 evidence、路径、凭据或 agent 原文输出到 CLI。
11. fake subprocess 的定向测试、Ruff、Mypy 和 `git diff --check` 通过；不执行真实 Codex、DSH、Docker、数据库或 benchmark。

## 开放问题

- Codex CLI 细粒度 permission profile 属于版本相关能力；最低支持版本固定为 0.138.0。低于该版本或无法解析严格配置时必须 fail closed。
