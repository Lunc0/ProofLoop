# 规格：DSH 轨迹压缩与 Evolution Coding Agent 输入

> **阶段：**08 · **版本：**v0.8 · **状态：**已完成
>
> **前置阶段：**[阶段 05：本地 Skill 候选版本库](05-v0.5-local-skill-evolution.md) · [阶段 06：最终 Held-out](06-v0.6-livesqlbench-final-thirty-query-suite.md) · [阶段 07：分层滚动评测器](07-v0.7-tiered-rolling-evaluator.md)

## 1. 目标

为 DSH append-only session log 建立一个严格、可复现的 **Rule-based Trajectory Compressor**。它把原始、已脱敏的事件流变成面向 Coding Agent 的低噪声 `dsh-trajectory-compressed-v1`：保留任务完成路径、工具调用、直接错误、候选输出和客观评测证据，同时删除流式传输噪声与内部 reasoning。

压缩器不判断 Agent 的根因、Skill 缺口或修改方式。Coding Agent 在取得一个或多个 Evolution 开发 case 的压缩轨迹后，负责失败归因、跨 case 模式分析、Skill 修改建议和新候选草案。

成功意味着：同一份已脱敏 session、同一 evaluator projection、同一 compressor policy 一定产生同一压缩 artifact；Coding Agent 可获得足以分析正确性与效率的开发证据，而 Final Held-out 的逐题身份、日志、GT/Gold 和结果永不离开 custody。

## 2. 已确认前提

1. **Evolution 是开发集**，也是 Coding Agent 优化的主要证据来源；其逐题压缩轨迹、受限 task context、候选输出和 agent-safe evaluator projection 可以进入 Coding Agent。
2. **Smoke 仅是 gate**。它可以保留审计 evidence，但不向 Coding Agent 提供逐题日志或压缩轨迹。
3. **Final Held-out 永不输出逐题信息**。它只产生既有 aggregate-only result，不成为 compressor 或 Coding Agent 输入。
4. `web_search` 是允许的评测工具。压缩器必须支持其确定性摘要；联网检索仍是环境比较键的一部分。
5. 内部 `reasoning-chunks` 和 assistant message 中的 reasoning block 不进入压缩轨迹。压缩器仅可保留 assistant 的公开 text、工具调用和工具结果等可审计行为证据。
6. Coding Agent 只产生诊断与新 `SKILL.md` 草案；草案必须经既有 candidate 生命周期创建为新的不可变 candidate。它不覆盖父 candidate，不自动 select、promotion 或 rollback。

## 3. 范围

### 3.1 Rule-based Compressor

压缩器必须：

- 读取单一、已脱敏、受大小/事件数限制的 DSH JSONL session，并严格验证 header、事件对象和必要字段。
- 以 `(turn, step, seq)` 建立稳定顺序，并使用 `(turn, call_id)` 将 `tool/call` 和 `tool/result` 全局配对；结果可跨 step 返回。
- 删除或折叠 `assistant/chunk`、`tool-call-chunks`、`text-chunks`、UI/transport 事件和内部 reasoning；缺少完整聚合事件时，仅以 chunk 作为明示的 fallback evidence。
- 产生按 step 聚合的公开 assistant text、tool call、tool result 和 source sequence；保留 `call_without_result`、`orphan_result`、未知事件类型和解析降级，而不静默丢失。
- 按工具 adapter 压缩 `read`、`glob`、`pwsh`、`sql-readonly`、`web_search` 与 generic tool output。
- 用多信号规则识别 tool 的直接失败和高置信原因，例如 `is_error`、结构化 status、exit code、`ok: false`、SQLSTATE 或版本化错误模式。它不输出 `root_cause`、`skill_gap` 或 Skill 修改建议。
- 检测客观 signal：重复文件读/工具调用/SQL、失败后恢复、超大输出、高工具调用、高 token、超时前最后行为和网络检索使用。
- 对 pass、task failure、runner timeout 与 evaluator/policy anomaly 都产出压缩轨迹；只有没有 assistant text、tool call、tool result 或候选输出的启动即中断轨迹可归为 `partial_insufficient`，不提交 Coding Agent。

### 3.2 Coding Agent 输入边界

Evolution 的 Coding Agent 输入包含：

- 当前 candidate 的 `SKILL.md`、candidate ID 和 SHA-256；
- 由可信 benchmark 输入提供的 task/schema/context，而不是从 session 中猜测或重新抽取；
- 一个或多个 `dsh-trajectory-compressed-v1`；
- 不含 GT/Gold 的 evaluator projection、环境/规则版本和优化约束；
- 可选的、已暴露 Evolution manifest 的摘要与此前 candidate 草案的公开 lineage。

所有由 session、工具、网页、错误或模型生成的文本都标记为 `untrusted_evidence`，只作为待分析数据，不能充当指令。Coding Agent 不可访问 custody 原日志、session root、Final、GT、Gold、私有 dump、凭据或绝对 custody path。

### 3.3 可复现的联网检索摘要

对允许的 `web_search`，压缩轨迹保留 query、稳定排序的标题/URL/snippet、有界结果数、检索时间、工具版本/配置 fingerprint 与规范化结果 hash。完整网页或原始响应留在 custody evidence，除非其本身属于可见的公开 Evolution task context。

联网检索导致外部内容随时间变化；含有不同 web tool 配置、检索结果 hash 或环境 fingerprint 的 Evolution 结果必须标为不可直接比较。

## 4. 不在范围内

- 不改变或实现 DSH 的运行时工具 allowlist；本阶段只把实际工具调用作为可审计 evidence。`web_search` 按已确认前提允许。
- 不对内部 reasoning、链式思维或 session 自由文本做 LLM 摘要、根因判断或心理状态推断。
- 不新增 SQL dialect、并发、网络服务、依赖、CI 或生产数据库访问。
- 不运行 Docker、真实 DSH、真实模型、baseline 或 Final 来验证本阶段。
- 不让 Coding Agent 自动修改现有 candidate、自动选择 champion、promotion 或 rollback。
- 不把 Smoke 或 Final 的逐题轨迹用作优化输入。

## 5. 数据保管与可见性

| 数据层 | Smoke | Evolution | Final |
|---|---|---|---|
| 原始/脱敏 session evidence | custody 审计 | custody 审计 | custody-only 审计 |
| 压缩 trajectory | 不向 Coding Agent 输出 | agent-visible 开发证据 | 不生成 agent artifact |
| 逐题 task / schema / SQL / evaluator projection | 不输出 | 仅已授权的开发材料 | 永不输出 |
| aggregate metrics | gate receipt | 可用于开发趋势 | aggregate-only |

一份 Evolution manifest 一旦其逐题 evidence 被送入 Coding Agent，即标记为 `exposed_for_optimization`。修改后的 candidate 不得再把该 manifest 上的重跑结果当作独立、未见数据的比较证据；后续比较必须使用新的、此前未暴露的 Evolution manifest。

下列字段必须在发给 Coding Agent 前删除或映射：API key、token、Authorization/Cookie、密码、包含凭据的连接串、主机用户目录、绝对 custody path、GT、Gold SQL/结果、私有 dump 和未脱敏原始日志。

Evolution 的公开任务、schema、候选 SQL、受限样例行、工具参数、错误文本与 stdout/stderr 可以保留，但必须有字段级字节上限、截断位置、内容 hash 和 `untrusted_evidence` 包装。压缩不以“删除一切数据库内容”为目标；它以不泄漏不可见材料并保持可分析性为目标。

## 6. 轨迹完成度与结果维度

`trace_completeness` 与 evaluator verdict 独立：

| `trace_completeness` | 定义 | Coding Agent 处理 |
|---|---|---|
| `complete` | 有可验证 `turn/end: completed`，并取得 final assistant text | 分析完整路径 |
| `partial_actionable` | 无终态，但已有公开 assistant text、tool call/result 或候选输出 | 分析截至中断时的效率/恢复路径 |
| `partial_insufficient` | 仅启动/step 边界等，不含可解释行为证据 | 不提交 agent；仅记录审计状态 |

timeout 必须同时记录 `runner_outcome`、`deadline_ms`、`last_observed`、`missing_terminal_events` 和 `trace_completeness`。它不是自动的 Skill 错误：`partial_actionable` timeout 是可能的效率改进信号；runner/evaluator 证据缺陷仍不得伪装为候选 SQL 正确性结论。

## 7. 压缩与规范化合同

### 7.1 事件保留

- **L0 删除：**已由聚合事件覆盖的 stream/chunk、内部 reasoning、无语义 UI/transport event。
- **L1 结构化压缩：**大文件 read、glob、大 SQL result、PowerShell stdout、web search results 和超长公开 assistant text。
- **L2 低压缩证据：**失败调用及前后 context、candidate final output、客观 evaluator projection、终态或 timeout 前最后行为。

`assistant/message` 只提取 `content` 中 type 为 `text` 的公开文本；不输出 type 为 `reasoning` 的 block。对工具 arguments/result、错误和网页片段保留数据边界与来源 sequence，但它们不能被 Coding Agent 当作可执行指令。

### 7.2 工具 adapter

- `read`：保留相对或角色化 path、range、长度、内容 hash、可见关键片段；schema 可额外产生 DDL 的 table/column/PK/FK 结构。
- `glob`：保留 pattern、稳定排序后的总数、前 N 个角色化 path、省略数和 hash。
- `sql-readonly`：保留 SQL、结构化成功/失败、columns、row count、稳定 sample rows、SQLSTATE/exit code 与直接失败类别。Gold 和不可见结果不得进入。
- `pwsh`：保留命令、exit code、受限 stdout/stderr、结构化错误；不得将任意环境变量或绝对目录直接输出。
- `web_search`：遵循第 3.3 节的 query、公开结果摘要和 hash 合同。
- generic tool：保留名称、参数的 canonical hash、状态、字节数和受限 evidence；未知格式不推断成功或失败。

### 7.3 直接失败与重复 signal

工具 `failed` 仅由版本化的高置信规则确认：显式 `is_error=true`、结构化 error/failed/timeout 状态、非零 exit code、结构化 `ok=false`、SQLSTATE 或明确错误模式。输出需包含 `direct_cause`、`category`、`confidence` 与 `evidence_fields`。

重复检测必须使用 exact hash 与可选的安全 normalized hash。SQL 第一版不得在 string literal、quoted identifier 或 comment 内折叠大小写/空白；若 tokenizer 不能安全规范化，只输出 `possible_duplicate`，不宣称语义重复。

## 8. `dsh-trajectory-compressed-v1` 概要

```json
{
  "schema_version": "dsh-trajectory-compressed-v1",
  "source": {
    "redacted_session_sha256": "...",
    "session_version": 0,
    "compressor_rule_version": "...",
    "compressor_policy_sha256": "...",
    "evidence_ref": "custody-only opaque reference"
  },
  "trace": {
    "trace_completeness": "partial_actionable",
    "runner_outcome": "timeout",
    "deadline_ms": 300000,
    "last_observed": {"turn": 1, "step": 16, "event_type": "tool/result"},
    "missing_terminal_events": ["turn/end", "final_assistant_text"]
  },
  "trajectory": [],
  "signals": [],
  "candidate_output": {},
  "evaluation": {},
  "compression": {
    "raw_event_count": 0,
    "raw_bytes": 0,
    "compressed_bytes": 0,
    "truncated_fields": [],
    "unhandled_event_type_counts": {}
  }
}
```

序列化必须使用 UTF-8、稳定 key 排序、严格 schema、固定数值/时间格式。所有阈值、错误正则、字段上限、N 值、采样/排序规则都属于 `compressor_policy`，其 canonical hash 必须写入 artifact。

## 9. 技术约束与预期边界

沿用 Python 3.11+、Typer、Pydantic、PyYAML、pytest、ruff 和 mypy；首版不添加依赖。实现应位于 `src/skill_evolve/` 的新 trajectory/diagnostic 边界中，具体模块名和 CLI 入口在规格批准后的实施计划确定。

输入 session、runner output、tool result、manifest、candidate metadata 和 evaluator projection 均视为不可信。解析必须限制文件大小、事件数、嵌套深度和单字段大小，拒绝不合法 JSON/类型并留下脱敏质量状态。子进程继续使用 argv 数组与 `shell=False`。

现有命令在实施后仍适用：

```powershell
uv run ruff check .
uv run mypy src
uv run pytest
git diff --check
```

在本规格获准、计划完成并另获真实运行授权前，不运行 Docker、DSH 或模型。

## 10. 测试与验收标准

实现后至少验证：

1. 同一 redacted session 与同一 policy 重复压缩得到字节相同的 canonical output hash。
2. 聚合 `assistant/message` / `tool/call` / `tool/result` 正确覆盖对应 chunk，缺聚合时 fallback 明确标注而非伪造。
3. call/result 可跨 step 配对；缺 result、孤立 result 与未知事件类型均显式输出。
4. `is_error=false` 且有结构化非零 exit code 或 `ok=false` 时正确识别直接 tool failure；stderr warning 加 exit code 0 不误报。
5. 对 pass、task failure、`partial_actionable` timeout 与 `partial_insufficient` timeout 分别产生规定的 completion/route 信息。
6. `read`、`glob`、`pwsh`、`sql-readonly`、`web_search` 的截断、排序、hash 与错误分类符合固定 policy。
7. 内部 reasoning、GT/Gold、凭据、绝对 custody path 和 Final 身份不出现在 Evolution Coding Agent artifact；Evolution 允许的公开证据仍可保留。
8. 从已暴露 Evolution manifest 产生的新 candidate 不会将该 manifest 的重跑标为独立未见比较证据。
9. 所有新增测试只使用合成 session、stub runner、合成 evaluator projection 和临时 custody；不调用真实模型、真实 DSH、Docker 或网络。

## 11. 边界

- **始终：**保持 GT/Gold/credential/session custody 隔离；保留 timeout/失败的脱敏审计证据；验证所有输入与输出；将 rule/policy/version 纳入 evidence；让 Coding Agent 输出成为新的候选草案而非原地改写。
- **先询问：**批准本规格、创建后续实施计划、调用真实 Coding Agent/模型、运行真实 DSH/Docker、改变 custody/ACL、增加依赖、并发、自动 candidate 选择或推送远端。
- **绝不：**把 Final 逐题信息、GT、Gold、私有 dump、凭据、原始内部 reasoning 或未脱敏 session 传给 Coding Agent；将 candidate 文本作为代码执行；以高权限角色执行 SQL；连接生产数据库。

## 12. 开放问题

1. Evolution 中的 agent-visible task/schema/context 以何种独立 artifact 交付，并如何记录其可见性 hash？
2. `web_search` 的完整响应在 custody 中保留多久，以及使用何种稳定检索结果/归档策略支持审计？
3. Coding Agent 的一次输入最多包含多少 Evolution case、每个 artifact 的 token 上限和跨 case 聚合格式为何？
4. Candidate 草案的人工审阅、导入、同 manifest 曝露标记和新 Evolution manifest 创建的具体工作流为何？
5. 现有普通 `runs/` evidence 如何迁移或镜像到适合 Evolution agent-visible artifact 的 custody 边界？
