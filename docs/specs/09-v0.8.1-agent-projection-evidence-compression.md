# 规格：Evolution 失败轨迹的依赖感知 Agent 投影压缩

> **阶段：**09 · **版本：**v0.8.1 · **状态：**已完成
>
> **前置阶段：**[阶段 08：DSH 轨迹压缩与 Evolution Coding Agent 输入](08-v0.8-dsh-trajectory-compression.md)

## 1. 目标

在不引入业务语义判断或 LLM 摘要的前提下，进一步压缩交给 Skill Optimizer 的 Evolution 失败 case session-log。新机制构建可复现的**结构证据依赖图**：它识别事件、工具、文件记录、SQL、candidate 与 evaluator 之间可确定的引用、覆盖和纠错关系，并输出只保留“做了什么、得到什么、是否影响最终答案”的 agent projection。

“通用”仅指跨 case 可复用的事件、工具、语法和依赖追踪规则；它不判断某个业务概念是否重要、不推断 Agent 的意图或根因，也不产生自由文本业务总结。

成功意味着：对于同一份已脱敏 Evolution session 和固定 policy，agent projection 字节稳定、严格有界，且只包含 `CaseEvaluation.passed == false` 的 case；Optimizer 能直接看到最终提交/提交尝试、公开 evaluator 结果、失败与纠错、以及与它们具有高置信结构依赖的上下文证据。原始日志、审计 hash、event 序号和完整 metadata 继续留在现有 custody/evidence 边界，不进入 Optimizer。

## 2. 已确认前提与假设

1. 本阶段是 **v0.8.1 维护性演进**，不是 v0.9；阶段编号 09 仅用于文档顺序。
2. Evolution 中仍只有 evaluator 判定 `passed == false` 的 case 产生 Optimizer 输入；Smoke 不产生逐题输入，Final 继续 aggregate-only。
3. `dsh-trajectory-compressed-v1` 的 canonical/audit 语义保持可复现；本阶段新增或演进的是面向 Optimizer 的精简 projection，不能把审计字段删除后仍冒充旧 schema。
4. session、工具输出、公开 assistant text、网页内容及错误文本都是不可信证据；可信 benchmark task/context 与 session-derived evidence 必须保持可辨别的来源边界。
5. 本阶段不选择或裁剪 `SKILL.md` 的相关条款；当前 subject/Skill 交付方式保持不变。
6. 未能安全解析的文件、SQL 或工具结果必须 fail closed：保留既有受限 evidence 或标为无法降级，不能基于猜测丢弃内容。

## 3. 范围

### 3.1 双层 artifact 与字段迁移

压缩链路分为两个视图：

```text
已脱敏 session
  → canonical audit trajectory / evidence index（custody）
  → dependency graph（custody）
  → agent projection（仅 Optimizer 可见）
```

agent projection 必须删除或外提以下审计字段：event type、seq、时间戳、call/result location、arguments/result/deduplication hash、artifact hash、逐字段重复的 `untrusted_evidence` 与截断标记。其外层必须一次性声明 session-derived evidence 为不可信，并保留 policy/version 的非敏感标识。

这些字段仍可在 custody artifact 中用于配对、去重、复现和审计，但 Optimizer 不可读取 custody artifact、其绝对路径或可还原索引。

agent projection 不得同时带同一工具结果的原始文本和语义等价摘要。对于可安全结构化的结果，只输出一种 typed evidence；对于无法安全结构化的结果，输出既有受限文本或 `unavailable`，不得伪造摘要。

本阶段的 Optimizer 输入 schema 升级为 `evolution-coding-agent-input-v2`。历史 v1 artifact 保持其原有可读性；新 run 不再以删减字段后的内容冒充 v1。

### 3.2 通用事件与工具规则

下列规则必须跨 case、无业务名称硬编码地工作：

- 删除已由聚合事件覆盖的 `reasoning/chunk`、assistant/tool text chunk、transport、heartbeat 和无语义 UI event。
- 按 `(turn, call_id)` 配对 `tool/call` 与 `tool/result`，再以稳定的 projection order 输出；Optimizer 只看已配对的单一 action/result，不看原始双事件元数据。
- 对 `glob`、目录枚举或等价 workspace discovery 调用，若后续已有具体 read/引用，折叠为结构化 `workspace_discovery` fact；失败、被后续直接引用或结果互相矛盾的调用不得折叠。
- 对重复的同一工具调用、同一数据范围验证和最终前验证，保留失败、最后/最精确的高置信证据与必要的前置关系；早期调用只保留最小结构 fact 或证据边。
- 失败工具调用必须保留 tool/action、关键安全参数、直接失败类别、受限错误上下文及高置信 corrective action。失败不能因后续成功而消失。

规则引擎只能输出枚举、结构化字段、原有公开文本的有界片段和可验证边；不得把多步事件重写成自然语言业务结论。

### 3.3 文件与上下文的依赖追踪

对已注册、可安全解析的公开文件类型，建立来源记录与后向直接引用：

- KB/JSONL 记录以稳定 record ID、标题/定义字段或其他 schema 规定的 key 标识；后续公开 assistant text、SQL、工具参数或 evaluator-safe detail 中的直接规范化引用可保留该记录及最小必要邻接字段。
- schema 使用安全的 Postgres token/DDL 提取，识别后续 SQL 明确引用的 table、column、PK/FK；被保留表的必要 FK 端点可作为一跳 closure 保留。
- file read 的大段正文被已选 record/DDL/FK 片段替代，并输出 source role、selected/omitted aggregate count 与选择原因枚举；agent projection 不输出 unselected record 的 identity 或正文。
- 没有高置信命中、格式不受支持、存在歧义或无法完成安全解析时，不得将内容称为“不相关”；只能使用受限 fallback evidence 或标记为 `not_downgraded`。

顶层 trusted schema/knowledge/column-meaning context 与 session 内对应 `read` 结果必须使用同一选择结果，避免把整份 context 与 read 正文重复交给 Optimizer。

**大白话示例：**Agent 读了 100 条 KB，后续 SQL、公开文本或最终提交只明确出现 `IRS`，则 agent projection 保留 `IRS` 对应的最小 KB 记录；其余 99 条不交给 Optimizer。若最终 SQL 只引用 `orders` 与 `customers`，则保留两张表所需的列与连接它们的 FK，而不重复交付整份 schema。这是“只留下后来真正用到的说明书页面”，不是判断某个业务概念是否重要；没有可靠直接引用时必须保守 fallback。

### 3.4 SQL 结果与后向覆盖

`sql-readonly` 的 agent projection 必须优先使用结构化 result：成功/失败、query 的受限结构、columns、row count、有限 sample 或明确 aggregate 值；不得同时复制 raw JSON/stdout 和同一结果的 summary。

#### 3.4.1 LiveSQLBench Base-Lite Query 的首版语法边界

官方 LiveSQLBench Base-Lite 同时包含 SELECT-only 与 Management task；本项目的 Evolution adapter 只评测 Query slice，并只允许 PostgreSQL 单条只读查询。因此 v0.8.1 不为 `INSERT`、`UPDATE`、`DELETE`、DDL 或其他 Management SQL 建立依赖规则。该边界遵循 [LiveSQLBench 官方说明](https://github.com/bird-bench/livesqlbench) 与本项目既有的只读 SQL policy。

首版 extractor 分两级处理，而不是把所有 PostgreSQL 语法都当成同一种高置信结论：

- **引用提取级：**必须安全跳过 string literal、quoted identifier、dollar quote 与 line/block comment；识别 `SELECT`、`WITH [RECURSIVE]`、CTE、derived/nested subquery、`FROM`、所有 `JOIN`、`LATERAL`、`WHERE`、`HAVING`、`GROUP BY`、`ORDER BY`、`LIMIT/OFFSET`、`DISTINCT`、`CASE`、cast、set operation（`UNION`/`INTERSECT`/`EXCEPT`）、aggregate，以及 `OVER (...)` window expression。它提取明确的 base table、qualified column、CTE/alias 关系和 clause/operation shape；CTE alias 不得误标为 schema table，无法消歧的 unqualified column 不建立 table-column 直接边。
- **sample 覆盖级：**仅处理无 CTE、无 subquery、无 set operation、无 window、无 `GROUP BY`/`HAVING` 的扁平 `SELECT … FROM/JOIN … WHERE …`。早期 sample 必须是同一 relation/join/filter token form 下的有限 `LIMIT` 查询；后续查询必须对 sample 中待降级的每一字段给出 `COUNT`、`MIN`、`MAX`、`SUM` 或 `AVG` 等明确 aggregate。若只覆盖部分字段，则仅降级已覆盖字段，仍保留其余字段的有界 sample。

`EXPLAIN` 可作为 DSH 只读探索证据保留 query shape，但不参加 schema/KB 选择或 sample 覆盖。`PERCENTILE_CONT`、`PERCENTILE_DISC`、`STRING_AGG`、`ARRAY_AGG`、复杂 JSON/array operator、递归 CTE、相关子查询和其他虽合法但超出上述高置信子集的 PostgreSQL 结构，最多参加引用提取；不得触发 sample rows 降级。

只有在 extractor 能高置信证明下列条件时，早期 sample rows 才可被后续 aggregate evidence 降级为 query shape、row count 和覆盖关系：

1. 引用的 relation/column 集相同；
2. filter、join 与 grouping 的 token-aware canonical form 相同；
3. 后续查询对相同范围提供明确 aggregate 结果；
4. 早期调用本身不是失败、唯一反例、最终 candidate 验证或 evaluator 直接关联证据。

不满足任一条件，或 SQL 含无法安全处理的语法时，保留现有受限 rows 并记录 `coverage: unknown`。此时 projection 使用 `sql_unparsed`/`sql_not_downgraded` 结构，保留受限 query、status、columns、row count 与既有 bounded sample，但不建立猜测的 schema/KB edge。本阶段不宣称 SQL 语义等价，也不在 string literal、quoted identifier 或 comment 内进行不安全规范化。

**大白话示例：**Agent 先在 `orders` 的相同筛选条件下抽样 20 行 `price`，后面又查询同一范围的 `MIN(price)`、`MAX(price)` 或 `AVG(price)`。后面的统计是更完整的正式证据，因此前面的 20 行可压成“曾抽样 20 行观察范围”；两条 SQL、row count 和覆盖关系仍保留。只要表、字段、筛选、join 或分组不同，或前一次查询是失败/反例/最终验证，就不能降级。

### 3.5 最终答案、提交尝试与 evaluator

agent projection 必须单独产生 P0 evidence：

- `candidate_output` 仅表示 runner/evaluator 实际收到的 candidate SQL；其来源仍是可信 runner contract。
- 当 session 有公开最终文本但 runner 没有 candidate SQL 时，输出独立的 `final_submission_attempt`，其中包含受限公开文本、稳定 projection order、严格 SQL fenced-block 提取状态及未提交原因；它绝不能被标为实际 candidate。
- evaluator 只输出现有 agent-safe verdict、candidate SQL、detail、usage 和公开规则版本。GT、Gold SQL/结果、私有 dump、expected query/result 与 Final 逐题信息不得出现。

### 3.6 优先级与压缩顺序

projection 依据固定优先级渲染，不根据业务实体名排序：

| 优先级 | 必须保留的结构证据 |
| --- | --- |
| P0 | evaluator、实际 candidate、final submission attempt、失败与 corrective action |
| P1 | 被 P0/P1 直接引用的 schema/KB/file record、必要 FK closure、关键工具证据 |
| P2 | 高置信 aggregate、约束/范围验证 |
| P3 | 可降级的探索 sample、workspace discovery |
| P4 | 仅 custody 的 hash、location、重复状态、未被使用内容 |

完整 session 必须先解析、配对并建立边，再进行后向选择和 projection；实现不得因为流式读取顺序而提前删除后来会被引用的内容。

## 4. 不在范围内

- 不加入业务知识、gaming/finance/ecommerce case 名称、手工知识条目、根因诊断或 LLM 总结规则。
- 不切分或挑选当前 `SKILL.md` 的相关条款。
- 不新增 SQL dialect、SQL parser 依赖、并发、网络服务、CI、自动 Skill 修改、candidate promotion/rollback 或远端推送。
- 不改变 evaluator verdict、Smoke gate、comparison key、candidate 生命周期、Final custody 或原始 session 的保留策略。
- 不运行真实 DSH、模型、Docker、网络、baseline、Evolution 或 Final；不把测试生成的逐题 session/结果提交 Git。

## 5. 技术约束、命令与预期结构

沿用 Python 3.11+、Pydantic、pytest、ruff 与 mypy，不新增依赖。SQL 与 DDL 仅可使用 fail-closed、token-aware 的既有/本地实现；引入第三方解析器或扩大 dialect 必须另行批准。

预期文件范围在实施计划中确认，暂定为：

```text
src/skill_evolve/trajectory/
  contracts.py             # audit 与 agent projection 的版本化合同
  compressor.py            # canonical audit 事实与安全 adapter
  dependency.py            # 无业务语义的证据节点与边
  projection.py            # P0-P4 选择及 agent-only 序列化
  policy.py                # 阈值、parser 版本、固定选择规则
tests/
  test_trajectory_compression.py
  test_trajectory_projection.py
  test_livesqlbench_rotation_run.py
docs/specs/, docs/plans/, docs/design/
```

风格继续使用冻结、严格 Pydantic 合同和 snake_case：

```python
class ProjectionEvidence(StrictTrajectoryModel):
    kind: Literal["tool_failure", "sql_aggregate", "schema_reference"]
    priority: Literal["P0", "P1", "P2", "P3"]
    outcome: Literal["succeeded", "failed", "unknown"]
    evidence: dict[str, object]
```

实施后的验证命令为：

```powershell
uv run pytest tests/test_trajectory_compression.py tests/test_trajectory_projection.py tests/test_livesqlbench_rotation_run.py
uv run ruff check .
uv run mypy src
git diff --check
```

在实现与无模型自动验证完成后，用户可在获授权的 custody 环境自行选择若干**已脱敏 Evolution** session，分别比较原始已脱敏日志、现有 v1 输入与 v2 projection 的本地字节数和证据完整性。该后验人工检查不设预先猜测的压缩率阈值，且不得将 case ID、prompt、session 正文、逐题结果或比较明细写入 Git、stdout 或 Optimizer 输入。

## 6. 测试与验收标准

1. 同一 redacted session、policy 和可信 context 重复生成 byte-identical projection；输入中只有位置/hash 不同但语义相同的 custody metadata 不改变 projection。
2. agent projection 不包含 hash、seq、timestamp、event type、call/result location、绝对 custody path、GT、Gold、凭据、原始 reasoning 或未选 record identity；相应 custody evidence 仍可支持审计配对与去重。
3. 成功工具结果不会同时包含 raw result 与等价 summary；失败结果保留直接错误和 corrective action 的结构关系。
4. 全通过 Evolution run 仍产生合法空 Optimizer 输入；混合 run 只包含 `passed == false` 的 case，且通过 case 不作为 omission。
5. KB/JSONL、schema/FK、glob 和 read 的直接引用选择对不同 case 名称/业务词有效；没有高置信命中或 parser 不支持时触发保守 fallback，不错误删除内容。
6. 只有严格满足第 3.4 节条件的 aggregate 才能降级早期 sample rows；filter、join、grouping、relation 或字段任一不匹配时不降级。
7. 已提交 SQL 与未提交的 final submission attempt 明确区分；格式错误的最终公开文本不会伪装成 evaluator candidate。
8. 结构化 workspace discovery、重复调用折叠和 P0-P4 排序稳定，且失败、冲突或直接引用的 discovery 证据不被折叠删除。
9. 所有测试使用合成 JSONL、stub runner、合成公开 context/evaluator projection 和临时 custody；不调用模型、DSH、Docker、网络或真实 benchmark 材料。

## 7. 边界

- **始终：**以固定 policy 和显式边生成 projection；将 session-derived text 视作不可信；保留失败、timeout、candidate/evaluator 的必要证据链；保持 Evolution/Smoke/Final 的可见性隔离。
- **先询问：**批准本规格、创建实施计划、引入第三方 SQL parser 或新依赖、扩大 SQL dialect、改变 custody/ACL、调用真实 Optimizer/模型、真实 DSH/Docker 或推送远端。
- **绝不：**把业务实体名写入压缩选择规则；把未提交的 session 文本当作实际 candidate；把 GT、Gold、Final 逐题信息、私有 dump、凭据、原始 reasoning、绝对 custody path 或 custody artifact 交给 Optimizer；让规则引擎做业务根因判断。

## 8. 开放问题

无。首版语法与 fallback 边界见第 3.4.1 节；若未来需要扩大 PostgreSQL 结构识别范围或支持其他 dialect，必须作为新规格变更并先获批准。
