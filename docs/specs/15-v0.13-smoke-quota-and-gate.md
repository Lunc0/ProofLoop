# 规格：Smoke 固定 Simple/Moderate 配额与 4/5 Gate

> **阶段：**15 · **版本：**v0.13 · **状态：**已完成
>
> **前置阶段：**[阶段 07：分层滚动评测器](07-v0.7-tiered-rolling-evaluator.md)

## 1. 目标

将未来新建的滚动 Smoke manifest 的五题难度配额从三轮 `2/2/1` 旋转改为固定的：

```text
Simple: 3
Moderate: 2
Challenging: 0
```

同时将 Smoke→Evolution gate 从必须 5/5 通过改为至少 4/5 通过。目的在于以更低难度、更稳定的五题门槛验证 candidate 是否具备进入 Evolution 的基本条件，同时保留 Evolution 的三层覆盖与既有的候选、证据、优化器隔离。

## 2. 范围

本阶段应当：

1. 仅修改新建 `smoke` rotation manifest 的配额选择和严格校验，使每份均恰有 3 个 Simple、2 个 Moderate、0 个 Challenging Query case。
2. 移除 Smoke 配额的三轮旋转行为；每次新建 Smoke manifest 使用同一 `3/2/0` 配额。
3. 保持 Evolution manifest 为 Simple、Moderate、Challenging 各 5 题，共 15 题。
4. 保持 reserve 初始化为三个 tier 各 5 题、Final 排除、同层/跨层选择边界、原子写入和 custody 隔离。
5. 当 Smoke 恰有 4 或 5 个 case `passed`，且不存在 `runner_invalid` 或 `evaluator_invalid` 时，为该 subject 写入 gate；3 个或更少通过、任何基础设施无效状态都不得写入 gate。
6. 让新 gate receipt 保存实际通过数和最小通过数 `4`，同时保持历史 5/5 receipt 的读取兼容。
7. 为新配额、4/5 准入、3/5 拒绝、基础设施无效拒绝、历史 gate 兼容与篡改/不足题数补充合成定向测试，并更新相关操作文档。

## 3. 历史 retirement 与数据边界

- 已存在的 Smoke/Evolution manifest、Smoke gate receipt、run evidence 与 custody 文件不修改、删除或重写；它们只保留为历史审计记录。
- 任何按历史 `2/2/1` 配额创建的 Smoke manifest 均不得再作为 Smoke run 输入；历史 Smoke gate 不得再放行 Evolution。
- 新 gate receipt 必须可证明采用 Simple 3/Moderate 2 与 4/5 policy；读取方必须拒绝把历史 gate 当作新 policy gate，且 receipt 不记录 case ID、题目、GT、Gold、session 或凭据。
- 不改变 adapter ID、CLI 参数、candidate ID/hash binding、评分、比较键或 optimizer 输入合同；为区分退休的历史 Smoke policy 与新 policy，可仅升级新建 manifest/gate receipt 的 schema version。
- 新配额只影响本阶段实施后的 `benchmark create-rotation-manifest ... --kind smoke`。

## 4. 非目标

- 不跳过、伪造或将 Smoke gate 变为可选；仅将其通过阈值从 5/5 调整为至少 4/5。
- 不删除历史 custody 数据，也不将历史 Smoke manifest 或 gate 迁移、重签名或伪装成新 policy 产物。
- 不改变 Evolution 或 Final 的题量、难度配额、选择规则或 custody。
- 不运行真实 DSH、模型、Docker、Smoke、Evolution、Final 或 held-out；不创建真实 manifest、gate 或 candidate。
- 不新增 benchmark、SQL dialect、并发、依赖、云服务、自动 Skill 修改、晋级或回退。

## 5. 实现约束

- 使用 Python 3.11+、既有 Pydantic/pytest/ruff/mypy 与现有 rotation custody 合同；不新增依赖。
- 继续拒绝 case ID、seed 或题池由调用者指定，继续在 Docker、DSH 或模型启动前 fail closed。
- 所有持久化的 manifest 与 receipt 保持不含 GT、Gold、凭据、原始 session、held-out identity 或私有路径。
- 新 manifest 的 quota 校验必须精确验证 Simple 3、Moderate 2、Challenging 0；不足候选或材料异常时不得留下部分 manifest。
- Smoke gate 的通过数必须从已验证 case evaluation 派生；不得由 CLI 参数、调用者输入或未经验证的 runner 文本声明通过。


## 7. 验收标准

1. 连续创建至少三个新的 Smoke manifest 时，每一份的 tier 计数均为 Simple 3、Moderate 2、Challenging 0，不再出现三轮配额旋转。
2. 每份新的 Smoke manifest 仍恰有 5 个唯一 case，仍排除 Final 与 reserve case，并保留现有 hash、路径和原子写入校验。
3. Evolution manifest 仍为每 tier 5 题；Final 与其 custody 行为不变。
4. 4/5 和 5/5 的 Smoke 在没有基础设施无效状态时写入可验证的新 gate；3/5、`runner_invalid` 或 `evaluator_invalid` 不写入 gate，也不能启动 Evolution。
5. 历史 manifest/gate 不被改写但不能再启动 Smoke 或放行 Evolution；新 receipt 可以证明采用了 3/2/0 与 4/5 policy，而不泄露 case 资料。
6. 合成测试覆盖新配额、候选不足、4/5/3/5、基础设施无效、历史 gate、篡改/路径边界及 Evolution 回归；`uv run ruff check .`、`uv run mypy src` 与 `git diff --check` 通过。
7. 验证过程不调用真实模型、DSH、Docker、数据库或评测集。

## 8. 计划期验证命令

获批计划并完成实现后，仅执行无模型、无 Docker 的定向验证：

```powershell
uv run pytest tests/test_livesqlbench_rotation.py tests/test_livesqlbench_rotation_run.py
uv run ruff check .
uv run mypy src
git diff --check
```

## 9. 边界

- **始终：**保留至少 4/5 的 Smoke→Evolution gate、三层数据隔离、候选 hash binding 和最小化输出。
- **先询问：**批准本规格后的实施计划、运行任何真实 DSH/模型/Docker/评测，改变 custody/ACL，或推送远端。
- **绝不：**伪造 Smoke gate、覆写历史 manifest/evidence、让 Final/held-out 进入优化输入，或将新 Smoke 结果当作 candidate 晋级结论。

## 10. 已确认决策

1. 已确认：新 policy 对后续所有可运行 Smoke 生效；历史 `2/2/1` manifest 与 gate 退休，只保留为审计记录。
2. 已确认：`3/2` 固定表示 Simple 3、Moderate 2。
3. 已确认：仅在至少 4/5 passed 且没有 runner/evaluator 基础设施无效状态时通过 Smoke gate。
4. 已确认：Evolution 维持 15 题、Simple/Moderate/Challenging 各 5 题。
5. 已确认：按总通过数判定 4/5，不额外规定 Simple 或 Moderate 的最低通过数。
